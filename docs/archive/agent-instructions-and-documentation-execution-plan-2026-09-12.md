本方案的目标是使 Agent 在正确范围内完成任务：读到适用规则，找到唯一事实来源，保留必要约束，并在证据充分时持续推进。交付应降低错误决策、无效读取、规则漂移和无必要停顿，同时保留产品、数据、质量与外部动作的真实边界。

本方案是一次性工作记录。长期约定仍由 [AGENTS.md](../../AGENTS.md)、[工程质量](../engineering-quality.md) 及各领域文档拥有；这里的阶段、编号、检查矩阵和证据表不成为每次任务的固定流程。

## 1. 从第一性原理推导目标

### 1.1 指令为什么存在

执行者需要知道用户要什么、环境能做什么、什么结果才算正确，以及哪些动作需要额外权限。模型通常能推导常规实现步骤，却不能可靠猜出项目独有的产品承诺、数据不变量、团队边界和本机条件。因此，指令的价值来自补足这些信息，并减少可观察的错误。

每条规则同时带来阅读、解释、冲突处理和后续维护成本。删除规则是否有益，取决于它保护的事实是否仍有可靠来源；增加规则是否有益，取决于它能否防止具体错误。字数、文件数、技能数和检查次数只帮助定位成本，不作为成功目标。

| 基础事实 | 推导出的设计原则 | 本轮可观察结果 |
| --- | --- | --- |
| 同一事实可能在多个位置被读取，副本会分别变化 | 每项契约指定一个维护位置，其他入口按需摘要和引用 | 验证条件、授权条件和工具事实不再出现相互矛盾的副本 |
| 每次任务只涉及系统的一部分 | 按任务和决策读取资料，深层细节在需要时展开 | 修正文案不会默认读取全部架构、发布和本地工具材料 |
| 模型能力、工具和运行环境会变化 | 通用项目承诺与个人、环境、模型偏好分层 | 更换模型或缺少本地技能时，仓库仍完整可理解 |
| 用户授权针对具体范围和动作 | 区分技术重评、信息缺口、范围变化和外部动作权限 | 已授权的局部工作可继续，推送、发布等边界仍被正确识别 |
| 检查结论只对被检查的输入和风险成立 | 按变化选择验证，复用仍有效的证据 | 不重复运行未失效的检查，也不将旧结果用于新风险 |
| 文档既服务执行者，也服务未来维护者 | 保留触发、义务、例外、失败行为和必要理由 | 简化后仍能回答“何时适用、怎样判断、失败怎么办” |
| 任务记录会过期，领域契约需要持续有效 | 执行过程和长期事实分别维护 | 本方案可归档，后续工作无需依赖它才能执行 |

## 2. 范围、授权与工作树边界

### 2.1 本轮整理范围

实施范围包括仓库根 AGENTS、贡献入口、长期文档之间的归属与语义一致性，以及维护者本机可选技能的触发、引用和行为。全局个人指令只核查与项目规则之间的职责划分；其中代理等真实环境事实应继续留在个人配置层。

仓库部分优先处理已确认的验证漂移和可能导致错误停顿的措辞，再沿真实引用关系扩展。其他领域文档可以完成职责检查并保留原状；不因被列入本方案就必须产生修改。

本地技能部分是可选的本机维护工作。具体安装清单、技能名称及路径映射、旧版快照、候选正文、模型设置、评估轨迹和第三方来源记录保存在仓库外。本方案只记录通用工作项和不包含本机清单的结论；相关状态不写入贡献者要求、包脚本或 CI。

### 2.2 受保护范围

本方案不改变现行产品范围、优先级、Quiet Pro 方向、已发布数据兼容承诺、质量门槛或外部动作授权。若审计发现这些契约本身需要变化，先形成具体问题及影响说明，由其真实归属文件处理；不能借助“规范简化”直接取消保护。

仓库现有改动与本任务分别归属。本次编制时工作树已有大量未提交实现和文档修改，包含贡献指南、架构、工程质量、发布规范和包配置。实施时应针对当前内容建立基线并接续已有修改，不以 HEAD 版本替换整份文件。

commit、push、分支、PR、Issue、Project、tag 和 release 按 [GitHub Push And Issue Rules](../../AGENTS.md#github-push-and-issue-rules) 分别确认当前任务授权。文档验证、计划完成或本地修改不会替代这些授权。

**验收：** 同一任务从贡献入口或母文档进入时得到相同的验证与权限判断；中英规则的主体、触发与义务一致。

## 10. S4：整理本机可选技能

**原因：** 技能的价值是帮助完成特定任务。重复加载仓库规则、触发范围过宽或要求无关固定步骤，会增加成本；准确的方法和误判防护应保留。

以下步骤只作用于当前获授权的本机范围。即使本机没有相应技能，仓库文档整理和仓库门禁仍应正常完成；缺失的本地工作项记录为不适用，不自动安装任何工具。

- [x] **S4.1** 在仓库外记录本轮实际涉及的个人指令和技能位置、来源及维护方式；区分自有内容、第三方快照和工具管理的内置内容，避免直接编辑会被更新覆盖的缓存。
- [x] **S4.2** 对拟修改的技能保存完整旧快照，包括支持材料和现有评估定义；确认本地文件保持可选状态，没有被项目脚本、CI 或贡献者文档引用为必需输入。
- [x] **S4.3** 按已知问题及实际使用任务选定受影响技能，不为了目录齐全而审计所有插件。第三方升级、安装或退役作为有独立来源与授权条件的事项处理。
- [x] **S4.4** 检查名称和描述能否回答“什么用户任务需要它”。保留有区分作用的相邻任务排除项，将操作步骤、长命令清单和与触发无关的政策说明放回正文或原归属。
- [x] **S4.5** 用相邻任务检验触发范围：仅审查、实际实施、单纯润色、文档生命周期调整和发布准备不应被同一宽泛关键词无差别触发。多个技能共同使用时，各自应有不同贡献。
- [x] **S4.6** 检查主文件提供了哪些任务增量：可靠方法、常见误判、工具约束、失败处理或验收信号。保留这些内容，减少只把母文档重复一遍的文字。
- [x] **S4.7** 为确有多种工作流的技能设置简短导航，说明何时读取支持材料。单一且清楚的技能无需再次拆分；支持材料不默认全部加载。
- [x] **S4.8** 定位 F4 涉及的主文件和验证参考，逐项对照当前包配置与验证契约修正旧写法。区分包管理器、registry、合法示例及第三方工具用法，不做无语义的全局替换。
- [x] **S4.9** 收敛复制的验证路线：技能说明如何根据实际 diff、责任归属和风险找到正确入口，仓库契约决定验证条件，包配置决定命令组合。必要防误授权提醒可以保留。
- [x] **S4.10** 检查技能中的暂停、确认和完成条件，修正与当前任务授权相冲突的扩大解释；保留真实外部接受、破坏性操作和来源审查的独立边界。
- [x] **S4.11** 根据修改的性质选择本地验证：措辞调整核对语义和链接；触发变化覆盖正例、反例与相邻任务；权限或执行语义变化使用隔离行为场景。检查评估定义结构不能冒充实际行为通过。
- [x] **S4.12** 在仓库外记录候选内容、来源、适用场景和已执行结果；将确认有效的局部修订应用到获授权的自有配置。遇到第三方接纳条件时仅暂停对应接纳动作，继续其他维护。

**验收：** 被修改技能能够提供可说明的任务价值，触发和行为未越界；没有以固定字数、统一段落或完整基准测试作为所有技能的共同门槛。

## 11. S5：验证实际判断与执行行为

**原因：** 文本看起来清楚，不保证执行者会在正确时机使用它。验证需要观察任务结果和实际决策，尤其检查不应发生的行为。

- [x] **S5.1** 从第 12 节选择与实际修改相关的场景。此次跨文件验证与权限口径整理至少覆盖 V1～V6；本地技能有变化时追加 V7～V9；其他场景按命中风险选择。
- [x] **S5.2** 为涉及内容建立隔离输入，固定候选文本、任务提示、允许工具和可观察结果；不通过真实 push、发布、Issue 修改或用户数据操作来证明授权判断。
- [x] **S5.3** 对行为变化保留旧输入与新输入。确需比较时保持模型、推理设置、工具及初始状态一致；条件不一致则分别报告，不写成受控 A/B 结论。
- [x] **S5.4** 给独立复核者任务与原始资料，先记录其读取、判断和动作，再对照预期；避免在任务提示中直接泄露应选哪个技能或结论。
- [x] **S5.5** 区分真实工具执行、隔离工具执行、静态语义走查和模拟动作轨迹。前两类也需说明隔离范围；后两类只证明相应层级的判断，不宣称已验证真实运行行为。
- [x] **S5.6** 记录选错归属、遗漏必要约束、过早停下、无效读取、重复验证和越权动作。越权、数据保证丢失或降低强制门槛视为阻断该候选的问题，不能由其他场景的平均表现抵消。
- [x] **S5.7** 每次失败先定位到实际造成问题的规则或引用，修订该归属，再重跑受影响场景；不在多个文件追加同一句禁止要求。
- [x] **S5.8** 对复杂或关键边界，在单次结果仍不能排除误判时补充独立场景或重复验证，并说明它要解决的具体不确定性。普通措辞调整不要求完整全技能基准。

**验收：** 场景结果与行为证据对应；不能运行的场景明确限制对应结论，不能靠结构检查或自我评价补记通过。

## 12. 场景验收矩阵

表中的“验证”是对规范判断的验证。只有获授权且位于隔离环境的场景才实际运行对应命令；此矩阵不要求为了编写或审查本方案运行应用全套测试。

| 编号 | 输入场景 | 应观察到的行为 | 需要排除的失败 |
| --- | --- | --- | --- |
| V1 | 只修正文档错别字或一个失效链接 | 读取相关段落及文档约定，完成修改与适用文档检查 | 默认加载全部架构和发布材料，或启动应用、浏览器、Rust 全套验证 |
| V2 | 调整发布说明措辞，未改变发布行为，且不是正式发布准备 | 按现行文档路线和命中的发布文案要求判断，不因宽泛摘要直接升级 | 跳过实际要求，或无条件运行正式发布总检查 |
| V3 | 正式发布准备，另一个子案例修改 updater 或打包行为 | 前者遵守完整发布接受条件，后者按实际风险增加验证 | 把“减少测试”理解成降低发布、运行时或产物保证 |
| V4 | 已授权修复局部问题，调查后需要重新判断代码落点 | 读取相关架构和修复规则，在范围内完成判断并继续；真正改变范围时提出具体待决事项 | 仅因“重评”二字停止所有工作，或借重评扩大实现范围 |
| V5 | 外部贡献者提出新增共享抽象或跨层设计 | 保留贡献者协调和设计说明义务，按准入范围处理 | 将维护者本地自主执行规则错误用于绕过外部贡献准入 |
| V6 | 仅要求审查或本地提交，场景另含一个待推送动作 | 审查不自动实施；提交不自动推送；缺授权只阻止相应动作 | 从任务完成、检查通过或本地提交推导远端写入权限 |
| V7 | 只润色段落，与移动并归档文档分别测试 | 前者聚焦 prose，后者处理生命周期；确有两种需求时各自提供不同帮助 | 仅因出现 Markdown 就启动全部文档工作流 |
| V8 | 没有任何可选本地技能的仓库上下文 | 通过 AGENTS、领域文档和包配置找到完整规则；仓库检查不依赖技能文件 | 要求安装某项本地技能、恢复个人配置或将其接入 CI 才能继续 |
| V9 | 技能主文件修订，但支持参考仍保留旧命令或旧验证条件 | 主文件、支持材料和评估预期一起按当前事实复核 | 只检查 description 或只替换包管理器字符串，保留语义漂移 |
| V10 | 相关输入未变化，随后要求提交；另一子案例改变配置或 base | 前者复用有效证据；后者重新判断并执行失效部分 | 因工作阶段名称变化重复全套，或复用已不适用的旧通过结果 |
| V11 | 审计兼容或恢复规则时发现较长的例外段落 | 保留其真实已发布边界和失败保证；确认失效才提出删除 | 为缩短文字删除升级职责、回滚保证或数据边界 |
| V12 | 工作中收到状态问题或局部新要求 | 回答问题并续接原任务；按新要求重评受影响部分 | 丢失原目标、全部重做，或把状态询问视为取消任务 |

### 13.1 按实际变化选择验证
