## 3. 一句话定义

这次修复要让挂件在 100%、125%、150% 和 200% Windows 缩放下始终获得与 CSS 设计尺寸一致的逻辑视口，并在不同分辨率、左右吸附、窗口复用和跨显示器切换时保持完整、清晰、可操作。

## 4. 问题定义

### 4.1 用户可见问题

当前挂件在 125% 缩放下可正常使用，但从 150% 开始，挂件托盘、锚点、对象槽或操作按钮会发生裁切。分辨率从 1280×720 提升到 3840×2160 并不能消除问题。

### 4.2 当前实测基线

已完成以下隔离诊断：

- 原生窗口工作区边界检查：432 个用例全部通过

- 覆盖状态：带对象展开、仅操作展开、折叠
- 覆盖侧边：左侧、右侧
- 覆盖缩放：100%、125%、150%、200%
- 覆盖分辨率：1280×720、1366×768、1600×900、1920×1080、2560×1440、3840×2160

### 4.3 已排除的错误方向

- 分辨率不是裁切的决定因素
- 工作区贴边算法没有把窗口整体放到屏幕外
- 125% 不是当前用户可见故障点
- 不是某个按钮单独设置了错误宽高
- 不是通过增大屏幕分辨率就能解决的问题
- 不是需要重新设计挂件视觉密度的问题

## 5. 第一性原理

### 5.1 像素不是一种单位

这条链路中至少存在三种坐标语义：

1. CSS 像素：前端布局使用的逻辑单位
2. 逻辑窗口单位：Tauri 窗口构建 API 接收的 DPI 无关尺寸
3. Windows 物理像素：显示器工作区、窗口外框位置和原生物理尺寸使用的设备像素

任何一个数字如果没有明确单位，都可能在 100% 下看似正确、在高 DPI 下失真。

### 5.2 设计真值必须只有一份语义

挂件当前设计尺寸是逻辑尺寸：

| 状态 | 逻辑宽度 | 逻辑高度 |
| --- | ---: | ---: |
| 带对象展开 | 228 | 48 |
| 仅操作展开 | 184 | 48 |
| 折叠 | 64 | 48 |

前端 token 中的 `48px`、`36px`、`38px` 等值都是 CSS 逻辑像素。原生窗口必须为这些逻辑尺寸提供足够的物理像素，而不能把同一个数字直接解释成固定物理像素。

### 5.3 正确模型

设：

- `L`：设计逻辑尺寸
- `S`：目标显示器缩放因子
- `P`：Windows 物理尺寸
- `V`：WebView 最终可用 CSS 视口

正确关系是：

```text
P = round(L × S)
V ≈ P ÷ S ≈ L
```

因此 48 逻辑像素高度应得到：

| 缩放 | 目标物理高度 | 最终逻辑视口 |
| --- | ---: | ---: |
| 100% | 48 | 48 |
| 125% | 60 | 48 |
| 150% | 72 | 48 |
| 200% | 96 | 48 |

### 5.4 当前错误模型

当前 Rust 常量被直接用于 `Size::Physical`，因此物理高度始终是 48：

```text
P = 48
V ≈ 48 ÷ S
```

实际结果为：

| 缩放 | 固定物理高度 | 有效 CSS 高度 |
| --- | ---: | ---: |
| 100% | 48 | 48 |
| 125% | 48 | 约 38 |
| 150% | 48 | 32 |
| 200% | 48 | 24 |

125% 时，38px 托盘和 36px 锚点刚好仍能放入约 38px 视口；150% 时视口只有 32px，裁切成为必然结果。

### 5.5 分辨率为何不改变结论

屏幕分辨率决定工作区总共有多少物理像素，但挂件窗口本身仍被固定为 48 个物理像素高。只要缩放因子不变，挂件的 CSS 视口尺寸就不变。因此 720p 与 4K 在同一缩放下会得到同样的挂件裁切结果。

### 5.6 这次修复必须维持的不变量

- [x] CSS/逻辑尺寸是唯一设计真值
- [x] 逻辑尺寸只在目标显示器边界转换一次物理尺寸
- [x] 工作区、窗口边界和原生位置计算始终使用物理像素
- [x] `anchorY` 始终是 0 到 1 的无量纲比例，不随 DPI 转换
- [x] 新建窗口与复用窗口得到相同的最终物理边界
- [x] 左右吸附使用缩放后的物理宽度
- [x] 顶部、中部和底部定位使用缩放后的物理高度
- [x] DPI 换算只进行一次，不允许重复乘除缩放因子
- [x] 取整只发生在逻辑尺寸转物理尺寸的边界
- [x] 跨显示器时使用挂件所在显示器的缩放因子
- [x] CSS 不通过缩小控件来掩盖原生窗口尺寸错误

## 10. 目标技术设计

### 10.1 逻辑尺寸模型

- [x] 把现有宽高常量明确命名为逻辑单位，例如 `*_LOGICAL_WIDTH` 和 `*_LOGICAL_HEIGHT`
- [x] 用一个小型值对象表达逻辑尺寸，例如 `WidgetLogicalSize`
- [x] 根据 `expanded` 与 `show_object_slot` 只解析逻辑尺寸，不在这一步读取显示器
- [x] 保持三种状态的逻辑尺寸分别为 228×48、184×48、64×48
- [x] 不为了“单一来源”引入跨 Rust/CSS 的生成系统
- [x] 用测试保护 Rust 常量与当前 CSS 契约，不建立超出本问题的配置基础设施

### 10.2 逻辑尺寸转物理尺寸

- [x] 新增纯函数，将逻辑尺寸与 `monitor.scale_factor()` 转为物理尺寸
- [x] 每个维度使用 `round(logical × scale_factor)`
- [x] 结果至少为 1 个物理像素
- [x] 函数命名必须显式包含 `logical`、`physical` 或 `scale` 语义
- [x] 不允许调用者再次乘以缩放因子
- [x] 不在 CSS 或前端重复这次换算

目标换算表：

| 状态 | 100% | 125% | 150% | 200% |
| --- | --- | --- | --- | --- |
| 带对象展开 | 228×48 | 285×60 | 342×72 | 456×96 |
| 仅操作展开 | 184×48 | 230×60 | 276×72 | 368×96 |
| 折叠 | 64×48 | 80×60 | 96×72 | 128×96 |

### 10.3 物理工作区边界

窗口物理边界必须按以下公式计算：

```text
physical_width = round(logical_width × scale_factor)
physical_height = round(logical_height × scale_factor)

left_x = work_x
right_x = work_x + work_width - physical_width

max_y_offset = max(0, work_height - physical_height)
y = work_y + round(anchor_y × max_y_offset)
```

- [x] 左侧窗口左边缘等于工作区左边缘
- [x] 右侧窗口右边缘等于工作区右边缘
- [x] `anchorY = 0` 时窗口顶边等于工作区顶边
- [x] `anchorY = 1` 时窗口底边等于工作区底边
- [x] 工作区小于窗口时使用饱和减法，避免无符号下溢
- [x] 负坐标显示器仍保持正确结果
- [x] 显示器位于主显示器上方或左侧时不把坐标钳制到零

### 10.4 新建与复用窗口一致性

复用窗口：

- [x] 使用已经换算后的物理尺寸调用 `Size::Physical`
- [x] 使用物理工作区计算得到的位置调用 `Position::Physical`

新建窗口：

- [x] builder 的 `inner_size` 直接接收设计逻辑尺寸
- [x] builder 初始位置只进行一次物理到逻辑转换
- [x] 构建完成、显示之前再应用一次统一的物理边界函数
- [x] 新建路径不自行复制第二套尺寸公式
- [x] 窗口第一次可见帧已处于最终尺寸，避免 1 帧跳变

`park_widget_window`：

- [x] 继续允许使用 1×1 物理像素停车尺寸
- [x] 停车尺寸不进入正常挂件尺寸模型
- [x] 重新显示时必须完整应用目标显示器的当前物理边界

### 10.5 目标显示器解析

目标显示器顺序应为：

1. 调用方明确提供的 `preferred_monitor`
2. 已存在挂件窗口当前所在显示器
3. 主窗口当前所在显示器
4. 主显示器

- [x] 新建挂件时仍可从主窗口或显式首选显示器选择初始显示器
- [x] 复用挂件时优先使用挂件自身显示器
- [x] 用户拖到另一显示器后，不因主窗口仍在旧显示器而被吸回
- [x] 停车状态无法解析挂件显示器时安全回退到主窗口或主显示器
- [x] 不把显示器身份持久化到数据库

### 10.6 运行时缩放变化

- [x] 在 `widgetRuntimeGateway` 中增加当前挂件窗口缩放变化监听的薄封装
- [x] React hook 只负责订阅和解除订阅
- [x] 具体刷新时序由 `widgetWindowController` 管理
- [x] 展开状态发生缩放变化时，使用当前 placement 和展示状态重新应用布局
- [x] 折叠且未拖拽时，重新读取窗口矩形和目标显示器后强制应用布局
- [x] 折叠且正在拖拽时，只记录“需要刷新”，等待拖拽结束后执行

## 19. 风险与缓解

### 19.1 双重缩放

风险：builder 使用逻辑尺寸后，又对同一路径重复应用缩放，导致窗口过大。

缓解：

- [x] 新建后统一应用物理边界
- [x] 测试精确断言每档物理尺寸

### 19.2 错误显示器

风险：挂件已经在副显示器，但 Rust 继续采用主窗口显示器缩放。

缓解：

- [x] 已存在 widget 的当前 monitor 优先
- [x] 异构 DPI 双屏往返测试
- [x] 负坐标显示器测试

### 19.3 事件循环

风险：scale changed 触发布局，布局触发 moved，moved 再触发布局。

缓解：

- [x] 复用 `applyingRuntimeLayout` 闸门

- [x] 交互测试断言调用次数

### 19.4 拖拽被打断

风险：跨屏时 DPI 事件立即调整窗口，破坏 Windows 原生拖拽。

缓解：

- [x] 拖拽期间只记录 pending

### 19.5 首帧闪烁

风险：builder 初始尺寸与构建后物理尺寸不同，透明窗口显示一帧错误大小。
