## 1. 目标与第一性原则

工具到期产生的是一个需要告知用户、可能需要用户处理的事实。事实是否成立，不应取决于主窗口是否打开；如何吸引注意力，也不应改变提醒本身的业务含义。

本次将三个责任分开：

| 责任 | 回答的问题 | 实现约束 |
| --- | --- | --- |
| 工具业务 | 什么到期了，哪些操作有效，处理后进入什么状态 | 继续由 Rust 工具运行时与 repository 决定 |
| 提醒呈现 | 在哪里显示，是否唤起主界面，如何取得焦点 | 由应用窗口编排决定，每条事件只有一个呈现目标 |
| 通用偏好 | 用户选择哪种通知方式和提示音 | 本地持久化；后台运行时也能读取；不依赖设置弹窗存活 |

由此得到以下验收原则：

1. 软件通知与提醒弹窗复用相同的提醒内容和业务按钮；差异在窗口承载、位置和激活行为。
2. 软件通知到来时，主窗口维持原来的显示、最小化、隐藏或已释放状态，用户当前工作的窗口不失去前台焦点。
3. 用户主动点击通知中的按钮可以与通知交互，但不会因此无条件拉起主窗口。
4. 同一事件不能同时出现在通知窗和主窗口弹窗，也不能由两个窗口各播放一次声音。
5. 呈现成功不等于业务完成；窗口销毁、重建、订阅重连不触发确认完成、延时或开始下一阶段。
6. 设置选择后直接提交。界面显示的成功状态必须对应已保存且已应用的偏好，失败应可见、可恢复。

产品范围遵循[产品原则](../product-principles-and-scope.md)，owner 遵循[架构](../architecture.md)，视觉与交互遵循 [Quiet Pro](../quiet-pro-component-guidelines.md)。本文只保存本次设计与执行步骤，不替代长期 owner。

```text

通知
┌──────────────────────────────────────────────┐
│ 通知方式              [软件通知 | 提醒弹窗]   │
│ 提示音                [默认              ▾]  │
└──────────────────────────────────────────────┘
```

### 2.2 通知与弹窗

| 行为 | 软件通知 | 提醒弹窗 |
| --- | --- | --- |
| 显示载体 | Patina 自己的独立通知窗口 | Patina 主窗口内现有提醒弹窗 |
| 位置 | 桌面角落，避开任务栏 | 现有弹窗位置 |
| 主窗口 | 不主动显示、恢复或创建 | 沿现有生命周期显示、恢复或创建 |
| 出现时的前台焦点 | 保留在用户当前工作的窗口 | 按现有提醒弹窗方式处理 |
| 内容与按钮 | 复用现有提醒界面，直接完成业务操作 | 保留现有内容与业务操作 |
| Windows 系统通知 | 不使用 | 不使用 |

默认通知方式采用讨论中的“软件通知”。现有定时提醒、使用限制、番茄计时、自由专注均进入同一分流机制；自由专注手动结束产生的阶段提醒也须覆盖，不能只处理后台定时事件。

### 2.3 本次不扩展的能力

不加入通知中心、历史通知列表、自动消失计时、多个通知卡片堆叠、通知位置选择、全屏免打扰设置、音量滑条、自定义音频导入或试听按钮。不重新设计三类提醒内容，不增加“查看后再处理”的中转步骤。

此前讨论中的 8 秒自动收起和 340–360 px 卡片宽度没有成为最终方案，不得作为本次实现要求。尺寸以复用现有界面并适配实际工作区为准。

## 4. 实施参数与证据边界

以下常规实现选择保持第 2 节已确认的产品范围。真实硬件和主观试听的未覆盖项独立保留，不以算法或浏览器验证替代。

| 问题 | 建议基线 | 收敛条件 |
| --- | --- | --- |
| 提示音资源 | `default / bell / clear / none` 对应“默认 / 轻铃 / 清脆 / 无”；三种 PCM 由项目源码本地合成 | 无外部录音或额外许可；波形格式、差异和幅度已测试，真实输出及主观试听见 H9 |
| 通知显示屏幕 | 事件首次呈现时取前台工作窗口所在屏幕，失败回退主屏工作区 | 单屏原生定位及不同 DPI、负坐标、任务栏工作区计算通过；物理混合 DPI 见 H9；显示期间不随前台变化追逐移动 |
| 同时到期 | 一个通知窗口按稳定顺序逐条处理 | 现有动作完成后推进，不遮挡正在编辑的二级选择，不引入通知中心 |
| 修改方式时已有提醒 | 已显示提醒留在原载体；之后首次呈现的提醒使用新偏好 | 不重复显示、不重播、不将待处理事件当作已完成 |
| 提示音播放时机 | 有效提醒首次显示成功后播放一次，两种呈现方式使用同一偏好 | 重绘、重连、二级选择和显示重试不重复播放 |
| 队列容量与恢复 | 每个业务来源保留当前有效事件，移除固定 32 条截断；不扩张为通用持久化收件箱 | 40 来源、同来源更新和删除后撤回的 Rust 测试通过；定时提醒按待确认事实恢复，其余类型保持原恢复边界 |
| 通知窗创建失败 | 每次等待 ready 最长 10 秒，一条提醒最多自动尝试三次；工具页和设置内提供错误及重试 | 三次 renderer 崩溃、停止重建、手动恢复已通过原生测试；不自动转为弹窗或系统通知，业务状态仍待处理 |

## 5. 实际 owner 与数据流

### 5.1 owner 分配

实现沿既有 domain、repository、app、platform 和 feature 边界落位，没有建立跨 feature 的通用通知框架。

| 责任 | 实际落点 | 边界 |
| --- | --- | --- |
| 通知偏好类型、合法值和默认值 | Rust `domain/tool_notifications`；前端 `shared/types/toolNotifications.ts` | 使用稳定 ID，不保存翻译文本或音频任意路径 |
| 偏好读写 | `data/repositories/tools/notification_preferences`，应用经 `data/tool_notification_store` 访问 | 复用 settings 表与现有事务习惯；没有新增 schema |
| 提醒业务与呈现状态 | `engine/tools`；纯状态规则放 domain | engine 保有业务真相；不创建原生窗口 |
| 偏好与通知窗口 IPC | `commands/tool_notifications` | DTO 验证、真实 caller guard、映射到领域动作 |
| 事件分流、窗口生命周期 | `app/tools.rs` 接收事件，`app/tool_notifications.rs` 协调，`app/tool_notifications/native.rs` 管理窗口 | 唯一分流点，不把窗口行为塞入 repository |
| 非激活显示、工作区与 DPI | `platform/windows`，优先已有窗口能力 | 不复制 Mini 整套生命周期；复用的是平台能力 |
| 通知窗口前端入口 | `src/app/tool-notification/ToolNotificationShell.tsx` | 只装配主题、语言和必要工具内容 |
| 提醒内容与动作 | `src/features/tools/components/` 及对应 service | 主窗口与通知窗共享同一业务内容；外壳可以不同 |
| 通知偏好 UI | `ToolsSettingsDialog.tsx` 与 tools 样式 | 不在全局 Settings 再提供第二个编辑入口 |
| IPC 适配 | `src/platform/runtime/toolNotificationGateway.ts`，feature 经 `toolPresentationStore` 消费 | feature 不直接调用 Tauri 或 Windows API |
| 声音播放 | `platform/windows/notification_sound.rs` | 应用协调器调度，与 tracking 音频会话探测职责分开 |

### 5.2 数据流

```text
工具事实提交 → 有效提醒进入 Rust 队列
                    ↓
         应用呈现协调器读取已保存偏好
                    ↓
       软件通知窗口  或  主窗口提醒弹窗
                    ↓
         同一提醒内容 / 同一领域操作
                    ↓
       Rust 校验当前事件及任务状态后提交
                    ↓
       更新快照、撤回失效展示、推进下一条
```

设置路径为：控件选择 → typed patch → Rust 校验与持久化 → 更新运行时偏好 → 返回权威快照并通知其他消费者。只提交工具通知字段，不能顺带提交全局 Settings 的未保存草稿。

### 阶段 A：冻结行为与接口

产出：能逐项测试的行为表和 owner 落点，避免界面先完成但窗口语义仍不确定。

- [x] A1. 重读第 2 节确认范围及当前源码；记录实施基线，保留工作区其他改动。
- [x] A2. 列出四类提醒的触发、有效身份、展示内容、可用动作及处理后状态；覆盖自由专注手动结束路径。
- [x] A3. 核对三类现有弹窗的按钮、Escape、遮罩关闭、二级返回和错误语义。业务动作维持现状；窗口销毁不得复用业务确认回调。若需改变 Escape 语义，单列具体差异后再决定。
- [x] A4. 明确偏好字段、序列化格式、默认值和事件结构；通知方式只允许两个值，提示音只允许已登记 ID。
- [x] A5. 定义呈现归属、当前事件 ID、状态修订或等价过期校验。显示、取回、执行、失效和推进必须引用同一事件身份。

通过条件：每个动作都能说明“谁可调用、针对哪条提醒、成功改变什么、失败保留什么”。

### 阶段 B：偏好持久化与立即保存

产出：设置在重启、后台运行和窗口重建后保持一致。

- [x] B1. 在领域层定义通知方式及提示音值；字段缺失时采用声明的默认值，读取旧库不改写旧任务参数。
- [x] B2. 在 tools repository 增加精确读写，只使用已有 settings 存储能力；校验备份导出、恢复白名单和归一化规则是否覆盖新键。
- [x] B3. 写入采用字段 patch。串行提交或显式版本校验保证快速操作不会让旧请求覆盖新选择，两个控件也不能互相覆盖。
- [x] B4. 提供 main-only 保存入口；后台运行时在启动和偏好更新时取得权威快照，不从 WebView localStorage 读取通知行为。
- [x] B5. 选择后立即提交，提交中给相应控件 busy / disabled 反馈。失败恢复最后已确认值，并在弹窗内显示可理解错误；不显示虚假的保存成功。
- [x] B6. 设置弹窗关闭后，已发出的提交仍由稳定 service 完成；再次打开读取权威状态。关闭不会撤销已保存设置，也不会导致卸载后丢失错误结果。
- [x] B7. 区分写入失败与已写入但运行时应用失败；后者执行重同步并明确状态，不能简单把控件回滚到与数据库不同的值。
- [x] B8. 覆盖非法值、缺省值、部分 patch、快速切换、提交中关闭、重开、重启及备份恢复；恢复后通知方式和提示音均与恢复结果一致。

### 阶段 C：建立唯一呈现分流

产出：尚未引入新窗口时，事件归属与处理不变量已可独立验证。

- [x] C1. 将 `app/tools.rs` 的无条件拉起主窗口改为按权威偏好分流；工具到期计算和事务提交保持在原 owner。
- [x] C2. 定义 main 与 notification 的定向展示快照或事件；主窗口只渲染分配给自己的提醒，不能继续直接展示全部 `tools-alert`。
- [x] C3. 前端先建立订阅再读初始状态，以修订号或等价机制合并；旧读取、旧窗口回调、重复事件都不能覆盖较新状态。
- [x] C4. 处理成功后由 Rust 推进并通知所有相关视图；一处完成后其他视图撤回旧提示。按钮连点与重复 command 不重复延时或启动。
- [x] C5. 删除任务、修改任务或下一阶段已启动时，旧通知退出或刷新为有效状态；拒绝旧动作，不能复活旧任务。
- [x] C6. 设置变化只影响之后首次呈现的提醒。已显示通知不迁移到主窗口，不因重载换方式或再次响铃。

- [x] C8. 定时提醒重建仍以 `pending_confirmation` 为准；分别验证其他提醒的原有恢复能力，明确其边界，不新增未经约定的永久通知历史。

### 阶段 D：独立通知窗口与权限

产出：主窗口完全不参与显示时，通知仍可呈现和处理。

- [x] D1. 新建固定 label 的通知窗口入口，并在 `App.tsx` 明确分流；通知窗不挂载 AppShell、Dashboard、全局页面请求或 Mini 内容。
- [x] D2. 提供最小 bootstrap：当前分配的提醒、必要主题与语言信息。工具目标图标等按需提供，不能为复用 UI 直接授予全部数据读取权限。
- [x] D3. 在 `build.rs`、permission set、capability、handler 注册和 IPC checker 中同步登记精确权限。未知窗口默认拒绝；Mini 保持现有只读工具边界。
- [x] D4. 为通知窗提供绑定当前 alert ID 的窄动作入口，允许当前提醒所需的确认、延时、下一阶段及返回桌面等动作。不得直接放开支持创建、编辑、删除全部任务的通用 command。
- [x] D5. 服务端校验真实窗口 label、当前分配身份和领域版本；伪造其他 alert ID、过期事件、非法音色或全局设置写入一律拒绝。
