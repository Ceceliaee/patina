# 分类页性能修复与对比执行方案

状态：分类菜单修复完成并归档，2026-10-08；全仓性能门槛的独立失败已转交具名待办，尚未解决。

用户已授权执行、勾选归档，并在完成后开展对抗式审查。以下勾选包括已执行、不采用、不适用和明确转交；各项文字与第 10 节说明实际处置。目标是减少分类页打开、搜索、关联和保存时的前端阻塞，并给出可复现的修复前后对比。勾选以实际执行与下文处置记录为准，不表示提交或发布已获授权。

## 1. 第一性原理与正确结果

一次交互的完成时间包含数据读取、派生计算、React 更新、布局和绘制，以及保存时的持久化等待。这些阶段可能重叠，不能把分别测得的耗时直接相加解释总耗时。用户真正等待的是输入发生后，正确结果可见且界面恢复可操作的时间。

设应用数量为 N，关联数量为 L，可见卡片数量为 V：

- 每张卡片都扫描 N 个应用，会把一次页面更新的候选处理放大到约 N²；关闭的菜单不需要完整添加候选列表。
- 关联标记必须及时显示，但这不等于每张卡片都需要构造完整应用索引、解析所有候选名称。
- 全量挂载 N 张卡片会让节点数、布局与更新成本随 N 增长。只有消除重复计算后，才判断是否需要限制挂载范围。
- 数据查询快不能证明界面快；模拟保存快也不能证明真实 SQLite 写入快。
- 优化必须保留完整目录、搜索结果、关联规则、草稿与保存语义。少显示数据或延迟正确结果不算性能收益。

正确结果：关联菜单关闭时不为每张卡片计算全量添加候选；打开时使用最新草稿；搜索、关联和保存保持现有行为，并在相同输入和环境下取得可解释的性能改善。

长期依据：[架构](../architecture.md)、[工程质量](../engineering-quality.md)、[修复边界](../issue-fix-boundary-guardrails.md)、[Quiet Pro](../quiet-pro-component-guidelines.md)。命令与既有预算分别以 [package.json](../../package.json) 和性能脚本为准。

## 10. 执行结果与证据

### 基线及测量方法

基线为 `c9ab02ad94e54c94fd0ae030404097c7c2d5e182` 加本次性能修复前的工作树，包含此前微信关联、图标、详情、滚动边界和依赖修复。基线和候选均保留独立生产构建、tracked diff、菜单源码 hash、锁文件 hash 与测量脚本 hash，没有切换或覆盖已有工作树。

新增入口：`pnpm run perf:classification-browser before` / `final`。本机原始数据位于 ignored 的 `artifacts/classification-performance/{before,after,final}/measurements.json`，生产产物在各自 `dist/`，对比表为同目录的 `comparison.html` 和 `comparison.json`。这些是本机测量产物，不是仓库长期依赖。

环境：Windows `10.0.26100`、i5-13400F、Node `24.21.0`、浏览器协议报告 `Chrome/154.0.8037.98`，1280×820、比例 1。两侧锁文件与 harness hash 相同。基准使用真实页面和生产构建，Tauri/SQL 为确定性模拟边界；目录含两个固定本地 SVG 图标，其余应用使用默认展示。循环经过无关联、关联一项、保存、解除和再次保存，包含主项名称初始化。匿名、分类、自定义名称的组合由功能回归承担，没有把每种组合都做成独立性能分布。

热场景预热两次后采样 20 次；首次导航分别启动五个隔离 profile。首次导航不包含整个应用进程启动耗时，profile 冷也不等同于操作系统磁盘缓存冷。修复前 1,500 项只记录了一次首次导航，之后 CDP 调用超时，中止该规模；该失败保留，不追加自动重跑或提高门槛。修复前共记录 808 个样本，修复后 1,076 个样本且零失败，样本数包含预热。

### 结果

| 动作 | 修复前中位数 | 修复后中位数 | 修复前 / 后 P95 | 中位数改善 |
| --- | --- | --- | --- | --- |

### 实现与阶段 C 决定

生产代码只调整 `LinkedAppMenu`：关闭或禁用菜单时，应用索引与添加候选使用空目录；添加候选只在添加状态计算。成员标记、成员回退及根集合保留原有逻辑。没有新缓存、memo、共享抽象、数据库改动或列表结构修改。

阶段 B 达到分类菜单的行为与局部性能目标，因此阶段 C 的 memo、分批和窗口化实现不采用；全仓性能条件的独立失败另列于下文。剩余 1,500 项全量挂载仍有明显成本，作为分类页面 owner 下的已知规模限制记录，不宣称任意规模瞬时响应。后续如明确要求改善该规模，应另行测量并评估列表交互边界，不让本次局部修复自动扩展为列表重构。

因此“所有既有性能门槛通过”这一原定接受条件未满足。本次仅完成分类 owner 的局部修复与对比，不作全仓性能通过或发布就绪结论。年度组合趋势的后续定位、修复与验收转入[数据页性能待办](./data-combined-trend-performance-followup.md)，由数据页 read model owner 承担，待办保持未勾选。主计划归档不表示该问题已解决。
