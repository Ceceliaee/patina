# Patina 文档治理执行方案

2026-11-18 制定，2026-11-19 实施 · 已完成并归档 · 范围为 Patina 桌面仓库、受影响的本地 Agent 工作流，以及 Patina Web Sync 的协议文档与入站引用。

## 1. 从第一性原理确定文档职责

一次开发会结束，参与者也会更换。下一位维护者或 Agent 接手时，源码可以告诉他系统现在怎样运行；他还需要知道哪些行为是对用户的承诺，哪些决定可以自行改变，以及什么结果足以证明改动正确。这些需要跨任务传递的知识，就是长期文档存在的理由。

- **按未来的用途决定写什么。** 会影响后续判断的产品意图、职责边界、失败保证、兼容条件及其必要理由，写进对应专题。能直接从 schema、manifest 或命令入口准确取得的细节，链接到定义。单次故障的经过和测量留在工作记录；去掉事件背景仍然成立的约定才提炼进正文。
- **按谁负责改变事实决定写在哪里。** 同一承诺若散在几处，更新时容易出现相互矛盾的答案。每项承诺由一个专题维护，其他入口引用它。根 `AGENTS.md` 负责协作和授权，本地 skill 辅助重复操作。贡献者仅凭仓库也应能找到正式依据。
- **按读者要做的判断决定怎么写。** 标题使用读者会搜索的词。能直接讲清的约定直接陈述；歧义会导致不同操作时，再用简短示例说明。必要顺序来自行为依赖、权限或安全条件，其余方法由执行者选择。

验收时，让没有参加原讨论的维护者或 Agent 从正常入口查一项约定，看他能否说明它何时适用、怎样核实、将来要去哪里修改。案例和文章形式按这个用途取舍。

本轮沿用 DSH 的事实归属、按任务分层和读者走读方法。Agent 指引参照 OpenAI 现行文档，具体采用范围由 Patina 的任务和权限决定。历史出处见[原采纳表](../archive/2026-10-26-reference-driven-documentation-governance-plan.md#21-采用适配与不采用)；设计依据见 [DSH 文档规范](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/docs/AGENTS.md)、[OpenAI 的仓库指令说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)与[技能说明](https://learn.chatgpt.com/docs/build-skills)。

**交付边界。** 目标是 1 份文档治理规范、7 份专题、一个根 Agent 入口和可独立维护的本地工作流。保留产品行为、协议字段、发布授权和验证强度。讨论过的数据外发、草稿与冲突处理，在能确认既有承诺时归入对应专题；新增产品承诺另作产品决定。编写本方案与实施、提交、推送和发布分别计。

### 哪些做法值得写成规则

迁移一条“必须先做……”的指令前，先问：**如果换一种做法，具体会破坏 Patina 的哪项承诺、越过谁的授权，或使哪项结果无法验证？** 能指出后果，就把需要保护的结果、适用条件和必要顺序写清。例如验证安装包签名必须先于安装。若多种做法同样满足约定，排查顺序、方案比较、任务拆分和工具选择交给执行者。确有帮助的经验可以作为例子；纯粹规定思考过程的文字直接删去。

下表中的场景仅作为实施者检查文档可用性的样题。走读时可选用等价情境，验收看读者能否找到正确依据。OpenAI 的 skills 文章讨论了过宽触发和过细步骤；模型指南说明了过度验证与不必要停顿怎样产生。[Skills 与提示写法](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) · [原先参考的模型指南](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra#prompting-best-practices) · [现行模型指南](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)

## 3. 长期文档的迁移与验收

以下文件名均相对 `docs/`。每项完成条件包括内容落位、相关引用可达、表内行为经走读确认。重叠章节先提取各自独有的承诺，再合并正文。

| 目标文件 | 来源与唯一职责 | 验证方式 |
| --- | --- | --- |
| `documentation.md` · 文档治理 | 新建。承接根指令的文档准入、唯一出处、读者任务、拆合、链接、工作与归档规则。说明写作时怎样保持原义，通用工程表述与风险选测链接 `quality.md`。 | 从贡献指南和根指令分别找到同一节。给出“只调整实现”“修正错误说明”“变更用户承诺”三个案例，分别得出保持原文、修正原文、更新权威正文和消费者的结论。 |
| `product.md` · 产品与优先级 | 合并 `product-principles-and-scope.md` 和 `roadmap-and-prioritization.md`。分开写范围准入、已准入事项排序、打断或延后条件。持有本地优先、隐私和用户可观察的产品承诺。 | 比较“新增低频展示”和“记录丢失”两个候选，读者能分别说明是否准入以及谁优先；匿名记录的已保存身份、既有历史和新增活动的语义与原文一致。 |
| `architecture.md` · 系统架构 | 保留文件名。用常驻宿主、共享 GPUI 窗口进程、隔离探测、数据流和模块依赖组织正文。保留写入归属、权限边界、恢复路径及新增代码的落点。 | 顺着“关 Mini 后重开”找到窗口、录制和已提交数据各自的负责人；顺着备份恢复找到持久化边界。对照实现路径及既有定向用例，检查每条链接和所有权。 |
| `quality.md` · 工程质量与修复 | 合并 `engineering-quality.md` 和 `issue-fix-boundary-guardrails.md` 中属于工程质量的约定。写清 Patina 的正确性要求、风险相关的验收证据、性能比较口径、审查与工程表述要求。Agent 根据实际代码、影响范围和用户要求决定如何定位、修复、组织工作和选测。 | 用标签文案修正和旧数据恢复分别走读。前者能直接定位并核对改动；后者能说明怎样验证恢复失败时原数据仍然可用。两例都以可观察结果判断是否充分。 |
| `ui.md` · 界面设计 | 从 `quiet-pro-component-guidelines.md` 迁入。保留 Quiet Pro 的布局、组件、主题、交互状态、焦点和无障碍规则。共享原型指向 QuietPro，页面特有行为指向相应窗口。 | 从“配色保存失败”查到草稿、可用操作和焦点约定，能分辨本窗口预览与已提交设置。对照实际 GPUI 消费者与原生用例；未实际运行的场景只记为文档走读。 |
| `localization.md` · 本地化 | 保留文件名与译者入口。持有消息参数、资源生成、回退和 XLSX 交接的使用说明。具体 key、类型、语言列表归 schema 和资源目录。 | 用“修改有参数的文案”和“交接译者工作簿”分别走读。找得到输入、检查、可观察结果和错参处理；变更命令示例时用合成输入验证。 |
| `release.md` · 版本与发布 | 从 `versioning-and-release-policy.md` 迁入。持有版本策略、changelog、旧备份读取窗口、安装升级、签名、资产、失败续跑与跨仓发布签收。当前代码版本归 Cargo manifest。 | 分别走读已有 tag 的失败续跑、已发布资产的不可变约束、旧备份与存储位置升级的不同条件。用合成文档验证改名后的版本声明检查，无需触发真实发布。 |

## 4. 治理规则、出处与验证

表中“出处”是未来维护时应修改的地方。第 3 节拥有的产品或工程事实继续留在对应专题；本文只记录迁移和验收责任。

| 规则 | 唯一出处 | 验证方式 |
| --- | --- | --- |
| 哪些变化需要更新长期文档，如何选读者、分拆或合并 | `documentation.md` | 写一个普通实现修复和一个改变公开承诺的反例。从入口得出不同的文档处理结果。 |
| 每条事实的权威正文、允许的摘要和跨仓副本 | `documentation.md` 定归属原则，专题定自身事实 | 从两个入口追踪同一事实，均到达同一处。检索独特条款，找到的第二份全文须有明确的交付或生成需要及一致性验证。 |
| 执行计划、证据、结项、归档与链接修复 | `documentation.md` | 按已完成、放弃并说明原因、转交具名责任方三种结果演练。未完成且无人接手的事项保持开启；归档链接仍可读。 |
| 通用工程文字的技术准确性 | `quality.md` | 从旧文抽查含“必须”、例外、失败恢复和停止条件的实际条款，对比新文的责任方、时机、义务、例外和结果。产品文案用本地化规则。 |
| 文档命名、路径引用和改名迁移 | `documentation.md` | 名称能让读者从任务词定位；从实际引用页打开新文件及章节，查 Markdown、纯文本路径、脚本、测试和跨仓引用。 |
| 仓库任务权限、协作节奏与对外操作边界 | 根 `AGENTS.md` | 给出“讨论”“制定方案”“本地提交”“推送指定目标”四种输入，逐项写出允许动作。检查 skill、测试通过或已归档都不能替代授权。 |
| 公开身份和编辑安全 | 根 `AGENTS.md` | 保留公开维护者署名、身份和私有信息处理、UTF-8 编辑及安全路径示例。检查链接目标、示例和变更文本，中文能正确解码。 |
| 对贡献者的 PR 准入、提交规则和材料要求 | `CONTRIBUTING.md`，模板采集，Rust 准入工具执行 | 中英文、PR 模板、准入实现与测试同义。用普通文档与改变治理规则的 PR 模拟输入，各自得到约定结果。 |
| 验证应覆盖受影响的行为，未验证的结果如实说明 | `quality.md` 定义证据要求；xtask 与 Cargo 定义命令行为 | 在已有验收要求内，用能暴露该回归的检查验证结果。涉及性能结论时比较等价场景的测量，涉及失败恢复承诺时观察失败后的持久化状态。 |
| 本地 skill 的可选性和授权界限 | 根 `AGENTS.md` | 仅用 Git 跟踪的文件走完文档维护路径；CI 与构建的输入独立于本地 skill。 |
| skill 的触发描述、工作方法、案例和本地行为验证 | 本地 skill 自身；仓库规则链接到上述出处 | 按改动选择案例。扩宽触发时检查相邻任务是否误入，改变权限措辞时检查越权请求，纯链接改名检查解析结果。区分静态走读与实际执行。 |

- [x] **根入口瘦身。** 保留按任务读取、授权与继续执行、公开身份、可选本地状态、Git 与外部 PR、编码安全等现有保护。文档生命周期指向 `documentation.md`，工程验收指向 `quality.md`，提交细则指向贡献指南。同步清理根指令和相关本地 skill 对旧修复分类的要求，核对各自的任务入口仍可用。
- [x] **校验唯一归属。** 对上述每行记录命中的新章节及一次观察结果。规则发生冲突时回到原始承诺裁定；新章节仍无法表达的差异留在工作记录，不能靠补一份 skill 说明解决。

## 5. 相关 skills 的本地实施

三个主要工作分别是文档维护、工程文字审查和 skill 自身维护。代码审查、UI 审查、简化与验证选择等工作流也是路径和章节的消费者。实际安装清单、触发配置和评测记录留在本地，仓库贡献者按根指令和专题文档即可完成任务。

- [x] **文档维护。** 令工作流先辨别读者、任务、权威出处和生命周期，再按需加载事实核验、归档或引用修复材料。用“归档已完成方案”验证命中，用“只改一条界面译文”验证能转到本地化入口。
- [x] **工程文字审查。** 令工作流处理陈述准确性、重复、失败语义和例外保留。用“压缩含两项恢复例外的说明”核对条款仍完整；只评审的请求应给出审查意见，工作区内容保持原样。
- [x] **skill 自身维护。** 令工作流处理触发条件、来源、精确适用范围和退出条件。用“更新 skill 的路由”与“修改发布规范”区分触发；用“只做来源调查”验证没有安装、运行外部 helper 或远程写入。
- [x] **消费者和重叠。** 核对本地工作流的触发、链接和工具来源。桌面验证入口以 Cargo 与 xtask 为准，清理仍引向旧 `package.json` 的指引。用“改写并归档一份工作单”检查组合后的效果：正文仍准确，归档位置正确，重叠的 skill 能复用已取得的证据。报告只需交代影响读者决定的结果、失败或待定事项。
- [x] **独立性。** 分别从有本地辅助的环境及仅含跟踪文件的视角回答同一任务，得到相同的正式依据和权限边界。用 `git ls-files -- .agents skills-lock.json` 核对无被跟踪的本地资产，结合忽略规则和 CI 输入确认结果。本地未安装的工作流记为不适用。

## 6. 路径、工具与跨仓交付

- [x] **入站引用。** 从两仓各自根目录查旧文件名、旧锚点、纯文本节号和机器读取路径。覆盖现行 README、双语贡献指南、根指令、PR 模板、活动方案和归档中的链接。未跟踪工作及本地辅助要单独检查。历史中准确描述旧名称的文字可以保留；仍可点击的链接应有有效目的地。避免把不同旧章节都重定向到同一新文件首页。
- [x] **文档检查器。** 更新 [xtask 文档验证](../../xtask/src/docs.rs) 对发布规范的定位。用违反当前版本单一来源的合成 `release.md` 验证能拒绝，再用正常示例验证能通过。核对文件、锚点、UTF-8 和现有顶层数量上限仍按原义检查；8 份是本次设计结果。
- [x] **PR 准入。** 更新 [Rust 准入实现](../../xtask/src/ci/intake/body.rs)、[对应测试](../../xtask/src/ci/intake/tests.rs)与 PR 模板，让 `quality.md` 和承接治理条款的 `documentation.md` 都能触发相应证据要求。普通文档只有文档检查时可接受；治理改动缺专项证据时拒绝、补齐时接受。保留已有完整验证路径。
- [x] **跨仓镜像。** 在桌面和扩展两个工作区分别读清已有改动。以桌面接收契约为准，比对并保留双方有效内容，两边落到 `docs/web-sync-protocol.md`。同步扩展根指令、架构、商店提交和发布规范中的引用，以及实际存在的工作单链接。统一 CRLF/LF 后逐字比较，核对方法、端点、字段和成功条件。若发现真正的协议语义分歧，记录双方行为和责任方，单独处理受影响条款，再继续已独立的工作。
- [x] **可恢复的实施顺序。** 以一个专题及其消费者为一批完成移动、检查器更新和链接验证。单侧失败时记录已完成的本地变更并修正另一侧；跨仓项在两边可达且核对相同时勾选。保留用户已有修改，不用整仓恢复、发布或远程写入来验证改名。

| 走读任务 | 预期能给出的答案 | 失败信号 |
