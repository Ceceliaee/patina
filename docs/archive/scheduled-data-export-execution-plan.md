## 1. 第一性原理

### 1.1 用户真正需要的结果

用户需要的不是“定时点击一次导出按钮”，而是在不反复进入界面的前提下，稳定得到可供阅读、分析或归档的周期数据文件。因此，功能成立必须同时满足以下条件：

- [x] 每个导出文件对应一个明确、完整且不会漂移的本地日历周期。
- [x] 文件使用用户主动保存的导出格式与字段集合，而不是运行时偶然读取到的界面状态。
- [x] 同一计划、同一周期最多产生一个有效最终文件。
- [x] 崩溃、重启、睡眠、时区变化和目标目录异常不会造成静默丢失、重复文件或未知文件被覆盖。
- [x] 用户能够明确知道计划是否启用、何时执行、最近是否成功以及失败原因。
- [x] 手动导出保持原有行为；增加自动能力不能降低已有功能的可用性。

### 1.2 定时导出不是什么

- [x] 它不是备份：导出文件不能作为 Patina 的完整恢复介质。
- [x] 它不是增量同步：文件之间不合并，也不维护跨设备状态。
- [x] 它不是云任务：当前只写入用户选择的本地目录，不上传 WebDAV 或其他远端服务。
- [x] 它不是任意 cron：只支持产品明确提供的每日或每周频率。
- [x] 它不是通用自动化平台：不提前抽象可承载备份、导出和未来任意任务的通用调度框架。
- [x] 它不复用手动导出的时间范围；自动任务只导出上一个完整自然日或上一完整自然周。

### 1.3 必须始终成立的不变量

- [x] `period_start_ms < period_end_ms`，且导出查询使用半开区间 `[start, end)`。
- [x] 每日周期由本地日历边界计算，不用固定 `86_400_000` 毫秒推导。
- [x] 每周周期固定为 ISO 周：周一 00:00 至下一周一 00:00。
- [x] 已领取运行的周期起止时间、格式和字段快照不可被后续设置变化改写。
- [x] 同一 `plan_generation + period_start_ms + period_end_ms` 在数据库中唯一。
- [x] 最终文件发布前必须完成写入和格式校验。
- [x] 不删除、不替换来源未知的同名最终文件。
- [x] 只有成功发布并可核验的文件才能把运行标记为成功。
- [x] 一次只能领取该计划最新的一个到期完整周期，不回放所有历史漏跑周期。
- [x] 计划被修改、恢复操作改变数据库或计划重新建立时，旧代运行不能污染新代计划。

## 2. 已确认的产品决策

### 2.1 入口与弹窗层级

- [x] 在现有“数据导出”一级弹窗标题区域右上角增加 `CalendarClock` 图标按钮。
- [x] 图标按钮与定时备份入口使用相同尺寸、视觉强度和交互状态。
- [x] 按钮 tooltip 与无障碍名称均为“定时导出”。
- [x] 不改变现有数据导出一级弹窗的宽度、高度或主体布局。
- [x] 点击图标后打开“定时导出”次级弹窗；关闭次级弹窗后返回原有导出上下文。
- [x] 一级弹窗继续负责手动时间范围、格式和字段的编辑。
- [x] 次级弹窗不重复展示“导出格式”和“配置字段”控件。

### 2.2 配置捕获规则

- [x] 打开次级弹窗时，读取一级弹窗当前的导出格式与已选字段。
- [x] 用户点击“保存”时，把当时的格式和字段作为计划快照持久化。
- [x] 保存计划后，用户在一级弹窗继续修改手动导出设置，不得静默修改已保存计划。
- [x] 用户再次打开定时导出并保存，才用新的格式与字段创建新一代计划配置。
- [x] 手动导出的时间范围始终不进入定时计划。
- [x] 字段列表保留用户确认时的顺序；空列表、未知字段或重复字段必须被拒绝或规范化后再保存。

### 2.3 频率与周期

- [x] 频率提供“每天”和“每周”。
- [x] 每天计划配置执行时间，导出前一个完整本地自然日。
- [x] 每周计划配置星期与执行时间，导出上一完整 ISO 自然周（周一至周日）。
- [x] 每周任务即使选择周五执行，导出的仍是执行前已经完整结束的上一自然周，而不是向前滚动七天。
- [x] 桌面宽度下，计划控件保持单行：
  - [x] 每天：`频率 [每天]  时间 [02:00]`
  - [x] 每周：`频率 [每周]  星期 [一]  时间 [02:00]`
- [x] 只有在窄视口无法保证可读性时才允许安全换行，不横向溢出或截断关键操作。

### 2.4 文件保存规则

- [x] 当前只支持本地目录。
- [x] 计划拥有独立持久化的目标目录，不依赖手动文件保存器最近访问位置。
- [x] 默认目录由 Rust/平台层解析为专用导出目录，前端不得硬编码 Windows 用户路径。
- [x] 目录显示为文件夹图标加普通只读文本，不伪装成可编辑输入框。
- [x] 通过“更改目录”打开目录选择器。
- [x] 保存配置前验证目录存在、确为目录且可写。
- [x] 执行时如果目录已丢失、断开或不可写，任务明确失败；不得静默改写到其他目录，也不得在意外根路径创建目录。
- [x] UI 展示路径时移除 Windows `\\?\` 扩展路径前缀，但持久化与执行仍使用平台规范化后的真实路径。

### 2.5 文件命名与共存

- [x] 每个完整周期追加一个独立文件，不把不同周期合并到同一文件。
- [x] 每日命名形如 `patina-activity-20260808.csv`。
- [x] 每周命名形如 `patina-activity-20260803-20260809.csv`。
- [x] 扩展名与已保存格式严格对应：`csv`、`md`、`parquet`、`sqlite`。
- [x] 文件名日期使用周期的本地逻辑日期，不使用任务实际运行日期。
- [x] 不提供“保留最近 N 份”，也不自动清理旧导出文件。
- [x] 同一代计划的同一周期重复触发时必须幂等，不额外生成 `(1)`、时间戳或随机后缀最终文件。

### 2.6 漏跑、重试与空数据

- [x] 应用因关闭、休眠或更新错过执行点后，只补最新一个已经到期的完整周期。
- [x] 不逐个补齐全部历史周期，避免重启后突发大量 I/O 和重复数据。
- [x] 临时失败采用有上限的重试；永久配置错误、路径冲突和权限错误不进行无意义的密集重试。
- [x] 一个完整周期内没有活动记录时，仍生成对应格式的合法空结果并视为成功。
- [x] 空数据成功必须可区分于“查询失败”或“写入失败”。

### 2.7 UI 状态与操作

- [x] 次级弹窗标题为“定时导出”，标题旁显示与字号和标题比例协调的 `BETA` badge。
- [x] 右上角只保留启用开关，不增加多余关闭按钮。
- [x] 底部只保留“取消”和“保存”。
- [x] 禁用状态下仍可编辑计划；保存时持久化但不调度执行。
- [x] 启用且存在真实数据时，可展示下次执行、最近成功、最近失败或正在执行状态。
- [x] 不渲染只有破折号的占位状态行；没有事实就不显示该状态。
- [x] 错误文案使用可行动的中文说明，不直接暴露 SQL、Rust 调试信息、凭据或无意义错误链。

## 5. 领域模型与日历语义

### 5.1 计划配置模型

- [x] 定义 `ScheduledExportConfig`，至少包含：
  - [x] `enabled`
  - [x] `cadence: daily | weekly`
  - [x] `weekday`（每日为空、每周必填）
  - [x] `local_time_minutes`
  - [x] `target_dir`
  - [x] `format: csv | markdown | parquet | sqlite`
  - [x] 有序 `selected_fields`
  - [x] `plan_generation`
  - [x] `schedule_anchor_at_ms`
  - [x] `updated_at_ms`
- [x] 计划读取模型包含可选的 `next_run_at_ms`、最近成功、最近失败和当前运行摘要。
- [x] 领域层拒绝未知频率、未知格式、非法星期、非法时间、空字段和重复字段。
- [x] 每次影响导出结果或调度槽位的保存都递增 `plan_generation` 并更新锚点。
- [x] 单纯读取或重复保存完全相同值是否递增代际需由测试固定；优先避免无意义递增。

### 5.2 周期计算

- [x] 每日周期通过“上一完整本地日期”的两个本地午夜分别解析为 epoch 毫秒。
- [x] 每周周期先求最近已经完整结束的 ISO 周，再分别解析周一和下一周周一的本地午夜。
- [x] 不用 `start + 24h` 或 `start + 7 * 24h` 计算结束点。
- [x] DST 春季跳时日允许实际时长为 23 小时。
- [x] DST 秋季回拨日允许实际时长为 25 小时。
- [x] 新加坡等无 DST 时区仍通过同一日历算法，不另设脆弱分支。
- [x] 保存和执行时使用系统当前 IANA/平台时区解析；已领取运行持久化精确 epoch 边界。
- [x] 运行被领取后即使用户改变系统时区，该运行的范围、文件名逻辑日期和内容保持不变。
- [x] 新时区只影响后续尚未领取的槽位，并通过计划代际/锚点避免跨时区重复领取。

### 5.3 到期与漏跑算法

- [x] 先根据频率、星期、时间和当前本地时区计算最近一个到期调度槽位。
- [x] 再确认该槽位对应的导出周期已经完整结束。
- [x] 槽位不得早于 `schedule_anchor_at_ms`，防止首次启用立即回补任意历史周期。
- [x] 查询同代、同周期运行记录；成功则不再领取，运行中则不重复领取，可重试则遵循退避。
- [x] 存在多个错过槽位时只选择最新一个，不循环创建全部历史运行。
- [x] 禁用计划时不领取新运行，但保留历史运行摘要用于诊断。
- [x] 保存新代配置后，旧代未发布运行不得继续向最终目标发布。

### 5.4 文件名与运行键

## 7. 安全文件发布流水线

### 7.1 阶段模型

- [x] 运行阶段至少为：`claimed → written → validated → published → succeeded`。
- [x] 每个不可逆边界前后都持久化足够信息，使重启后能够判断已发生什么。
- [x] 最终文件发布前只操作本运行拥有的唯一暂存文件。
- [x] 暂存文件必须与最终文件位于同一目录，以获得同一文件系统内的原子重命名语义。
- [x] 暂存文件采用独占创建，不能碰撞后覆盖其他进程文件。

### 7.2 写入

- [x] 根据运行快照构造 `ExportDataRequest`，复用现有四种导出器与字段语义。
- [x] 数据库查询继续使用异步只读池/WAL 能力，不长时间占用写事务。
- [x] 编码、压缩或同步文件 I/O 如会阻塞 Tokio runtime，迁移到 `spawn_blocking` 或明确的阻塞边界。
- [x] 不引入覆盖手动导出全局锁；定时任务使用运行领取锁，必要时增加规范化最终路径级保护。
- [x] 记录导出行数和暂存文件大小。
- [x] 写入结束后刷新缓冲；在平台支持且成本合理时同步文件元数据，再进入校验阶段。

### 7.3 格式校验

- [x] CSV：验证文件可读取、表头与已选字段顺序一致，空数据仍有合法表头。
- [x] Markdown：验证文档结构可解析，字段标题与顺序一致，空数据仍是合法文档。
- [x] Parquet：重新打开并验证 schema、列顺序和行数。
- [x] SQLite：重新打开数据库，执行完整性检查，并验证表 schema、字段和行数。
- [x] 计算暂存文件 SHA-256 和大小，持久化后才进入发布阶段。
- [x] 校验失败时不得留下最终文件；只清理本运行拥有的暂存文件。

### 7.4 原子发布与冲突

- [x] 发布时只允许“最终文件不存在”的原子重命名。
- [x] 不直接复用当前“先删除旧文件再重命名”的替换逻辑处理定时导出。
- [x] 最终路径已存在时先进入对账：
  - [x] 若台账证明它是同一运行已经发布的文件，且大小/哈希/格式匹配，则幂等标记成功。
  - [x] 若无法证明所有权或内容不匹配，标记 `target_conflict`，保留现有文件和本运行诊断信息。
- [x] 不删除未知最终文件，不自动重命名未知文件，也不生成带随机后缀的新最终文件。
- [x] 发布成功后持久化 `published`，再完成最终成功记录。
- [x] 只有数据库已确认成功后才清理已无用途的暂存路径字段。

### 7.5 崩溃恢复矩阵

- [x] `claimed` 前崩溃：没有运行所有权，不产生文件；下次可正常领取。
- [x] `claimed` 后、写入前崩溃：重启后按退避重试或清理无文件记录。
- [x] 写入中崩溃：识别并清理本运行未完成暂存文件，不碰其他文件。
- [x] `written` 后、校验前崩溃：重启后重新校验或重写，结果仍唯一。
- [x] `validated` 后、重命名前崩溃：重启后复核暂存文件哈希并继续发布。
- [x] 重命名成功、数据库尚未记录 `published` 时崩溃：重启后用目标路径、大小、哈希和周期快照对账并标记成功。
- [x] `published` 后、`succeeded` 前崩溃：重启后只补数据库成功状态，不重新导出。
- [x] 目标文件被用户删除：历史成功保留；后续是否重建同周期必须由明确策略决定，默认不因历史文件删除而自动重跑已成功周期。
- [x] 目标文件被用户修改：不自动覆盖；需要诊断时呈现文件不一致，不把它误判成新成功。

## 8. 调度运行时

### 8.1 生命周期

- [x] 应用启动时加载配置和未终结运行，先对账，再计算下一唤醒时间。
- [x] 配置保存后通过 `Notify` 或等价机制立即唤醒调度循环，不等待旧定时器自然结束。
- [x] 禁用计划后唤醒循环并取消新的领取；正在写入的任务按照明确取消边界安全终止或完成。
- [x] 运行循环异常退出时由现有 runtime task 管理模式记录并按有界策略重启。
- [x] 应用退出时不强行终止在最终发布临界区的文件操作；退出协调保证台账可在下次对账。

### 8.2 重试策略

- [x] 将错误分类为可重试与永久失败，而不是对所有错误统一重试。
- [x] 可重试示例：短暂数据库不可用、暂时文件锁、瞬时 I/O 中断。
- [x] 永久失败示例：非法配置、目录不存在、不是目录、权限拒绝、目标文件冲突、格式快照非法。
- [x] 磁盘空间不足采用低频有界重试，并在 UI 中明确提示释放空间。
- [x] 重试采用有上限退避并持久化 `retry_at_ms`，应用重启不重置为密集循环。
- [x] 达到尝试上限后保留最近失败；下一完整周期仍可按计划重新尝试新的运行。

### 8.3 并发边界

- [x] 同一周期的并发 tick 只能领取一次。
- [x] 手动导出与定时导出写不同路径时可以并行，不用全局互斥阻塞用户操作。
- [x] 两个操作指向同一规范化最终路径时，定时发布必须安全冲突而非覆盖。
- [x] 数据库恢复、池重启或迁移期间，定时任务只能失败并重试，不得绕过数据层直接访问不稳定连接。
- [x] 追踪数据写入保持可用；大范围导出不持有 SQLite 写锁。

### 8.4 恢复与导入的交互

- [x] “覆盖恢复”成功后禁用定时导出并旋转计划代际，避免恢复后的旧数据被自动写入原目标目录。
- [x] 恢复流程清理或终止恢复前尚未发布的运行所有权，但保留可审计记录。
- [x] “合并导入”不修改定时导出配置。
- [x] 恢复后重新启用计划时以新的锚点开始，不补跑恢复前的历史槽位。
- [x] 为覆盖恢复与合并导入分别增加集成测试。
