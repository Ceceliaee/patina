## 1. 从产品价值推导工程目标

用户需要的是可信、可理解、可控制且长期低打扰的时间记录。由此推导六条约束：

| 起点 | 推导 | 本轮可观察结果 |
| --- | --- | --- |
| 时间一旦过去，通常无法重新采样 | 原始事实与提交边界比展示速度更重要 | 失败不推进已提交状态，恢复不补记停机时间，派生表可从事实重建 |
| 页面是用户理解记录的入口 | “读取失败”不能被表达成“零活动” | 加载、成功为空、失败、旧快照刷新失败各有确定行为 |
| 同一数据必须能解释一致 | 数据含义需要唯一归属，页面不能各自修正上游 | Dashboard、History 汇总、Data 和导出在相同口径下可对账 |
| 每份独立可变状态都可能不同步 | 简化应减少状态来源、分支和跨层知识 | 删除无生产消费者路径；Data 每项状态只有一个负责模块 |
| 常驻工具每天重复承担资源成本 | 需要同时约束延迟、后台 CPU、全进程内存和资源回收 | 本轮以隔离本地运行的固定场景、短时样本和生命周期反例验证；正式运行和长期样本列范围外 |
| 自动检查只证明实际执行的对象 | 检查代码、执行代码和交付代码必须可追溯 | 入场检查与下游任务绑定不可变提交；结果能由反例推翻 |

优化顺序由 [产品范围](../product-principles-and-scope.md)、[路线图](../roadmap-and-prioritization.md) 和 [工程质量](../engineering-quality.md) 约束。结构落点见 [架构](../architecture.md)，多阶段修复见 [边界守则](../issue-fix-boundary-guardrails.md)，交互与文案分别见 [Quiet Pro](../quiet-pro-component-guidelines.md) 和 [本地化](../localization.md)。这些文档持有长期契约，本方案只持有本轮任务与证据。

### 2.2 加权 90+ 的结果定义

每个维度由五项组成，每项 20 分。最终只评价当前可实际执行的本地代码检查、自动化、隔离 Windows Tauri、SQLite、浏览器和短时性能/资源验证。正式安装与发布资产、ARM64 运行、需额外远端授权的 Actions 演练、8 小时实跑、人工读屏/真人任务、物理 DPI/跨屏及实际睡眠/时区等外部或人工环境验收，按用户指示列为范围外未验证；它们不构成扣分或达标障碍，也不取得已通过的分值。

分项按上述适用范围重新判断，仍记录本地可验证而尚缺的证据和实际未达指标。性能第五项改为本地可验证的资源生命周期与测量可信度，不继续使用已排除的 8 小时验收作为评分前提。最初 77.8 分及过程中 87.6 分属于较宽的旧范围，保留为历史判断；最终分数的范围变化与实现收益分开说明，不将二者差额全部算作代码改善。

| 维度 | 五项评分内容，每项 20 分 |
| --- | --- |
| 架构 | 事实与写侧归属；状态和生命周期归属；IPC/持久化边界；唯一实现及兼容退出；修改影响范围与可验证性 |

单项评分参考：0～9 表示存在明显缺陷或缺少实现；10～14 表示成功路径成立但边界保护不足；15～17 表示有真实 owner 和有效反例测试，但关键运行场景仍缺证据；18 表示已覆盖主要风险；19 表示本轮验收全部满足、边界清楚且没有实质缺口；20 还要求复核者挑战关键假设后未发现需要处理的问题。测试数量、文件变短、文档齐全本身不直接得分。

## 5. S1：让入场校验与执行代码保持一致

**第一原则：** 成功结论只对被检查的输入成立。移动引用、PR 正文变化与不可信产物都不能自动继承旧结论。

**负责位置：** [pr-intake.yml](../../.github/workflows/pr-intake.yml)、[verify.yml](../../.github/workflows/verify.yml)、[check-pr-intake.ts](../../scripts/check-pr-intake.ts)、[prIntakeGate.test.ts](../../tests/prIntakeGate.test.ts)。

推荐在可信的下游上下文中增加一次统一的“解析并校验提交”步骤，输出唯一已验证 SHA，供所有 job 消费。该步骤使用可信 base 的 intake 实现重新验证固定候选；已有上游成功仅作为触发条件。这样即使 PR 在排队期间从 A 更新为 B，B 也必须独立通过可信校验。若能够可靠取得上游实际校验的 A，也可以继续固定 A；不得把事件里的 merge SHA、当前 PR head 和被校验 head 混为同一对象。

- [x] **S1.1** 画清 push、workflow_run、手动 PR 验证三条路径：事件来源、可信 workflow、政策源码、候选 head、base、正文、权限与缓存。
- [x] **S1.2** 核对 GitHub 事件/API 字段的实际语义，明确完整 SHA 的来源及仓库、PR、run 的关联验证；列表为空、多个关联或身份不符时明确失败。
- [x] **S1.3** 在可信步骤中固定候选 SHA、base SHA 和用于 scope 判断的 PR 正文快照；只获取 Git 对象和元数据，不先运行候选仓库脚本或安装依赖。
- [x] **S1.4** 从可信 base 执行 intake，对上述固定输入验证；上游 artifact、PR 输出变量和作者声明不能单独作为“已验证”凭证。
- [x] **S1.5** 只在校验成功后输出已验证的完整 SHA。前端、两个 Rust 架构和 runtime job 全部 checkout 此 SHA，并在首个安装/执行步骤前核对本地 HEAD。
- [x] **S1.6** 手动入口同样解析并校验固定提交；输入 PR 编号仅用于定位，不能成为跳过 intake 的开关。push 路径继续绑定 push 事件的提交。
- [x] **S1.7** 检查 packageManager、安装脚本、checkout 凭据、token 权限和 cache 读写发生的位置。执行 PR 代码的任务使用最小权限，不能访问发布密钥或把不可信缓存提升为可信发布输入。

### 10.2 本轮验收目标

下表是本计划的优化目标，不是当前仓库已经承诺或实现的预算。基准机沿用 S0 环境；新增机器只增加可比对照。目标需在优化前冻结，实施后由相应测试/benchmark 持有可执行值，本文记录本轮结果。

| 场景 / 指标 | 本轮目标 | 原因 |
| --- | --- | --- |
| 常见点击、筛选的可见 busy/选中反馈 | p95 ≤ 100 ms | 用户应及时确认输入已被接受 |
| E0/R1 进程冷启动至可信 Dashboard 内容 | p95 ≤ 1500 ms，max ≤ 2500 ms | 包含真实初始化与数据读取 |
| R1 热 History 有意义内容 | p95 ≤ 150 ms | 高频回看应快速响应 |
| R1 Data 首次切入至完整内容 | p95 ≤ 500 ms | 包含查询、计算、图表提交 |
| R1 七日→全年可信内容 | p95 ≤ 400 ms | 约束常见长范围切换 |
| R3 全年视图读取至完整内容 | p95 ≤ 800 ms，max ≤ 1500 ms | 三年历史不应线性拖慢当前年度读取 |
| 当前同规模全年组合模型基准 | p95 ≤ 150 ms | 相对审计约 263 ms 的最差轮 p95，减少主要计算成本 |
| F60/F600/F3600 稳定原生投影 | 同一小时同一应用目标 1 行；行数不随碎片数线性增长 | 行数压缩必须来自真实维护器 |
| R1/R3 稳定小时读取 | 不随范围外事实总量全表扫描；返回量受所需桶和来源控制 | 防止历史增长拖累局部查询 |
| 主窗稳定闲置，追踪正常 | 全进程私有内存 p95 ≤ 300 MiB | 管理真实进程树资源 |
| 主窗和挂件均已使用后的稳定状态 | 全进程私有内存 p95 ≤ 400 MiB | 计入 WebView2，而非只计主进程 |
| 用户开启低耗后台并进入稳定托盘状态 | 全进程私有内存 p95 ≤ 150 MiB | 明确可选资源释放的收益 |
| 稳定闲置，追踪正常、无备份/重建任务 | 全进程平均 CPU ≤ 单核 1%，p95 ≤ 单核 3% | 避免用多核归一化掩盖后台成本 |
| 挂件快速再次唤出 / 低耗后台恢复主窗 | p95 ≤ 150 ms / 1000 ms | 资源优化必须保留恢复体验 |
| 包体 | 满足当前机器预算；无无关启动成本增长 | 既有预算不能因逼近上限自动扩大 |

如果保留原生粒度被证明是准确性所必需，S4 必须提供另一种达到同等容量收益的实际方案并复评，不能把 600 行测试直接豁免为通过。其他目标调整也须保留旧目标、原因、影响和新测量，不以“CI 已绿”替代论证。
