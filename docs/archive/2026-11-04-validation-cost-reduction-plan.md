状态：已完成并归档。创建/完成日期：2026-11-04。

本文是本次工作的执行单。维护者已授权按本方案实施和验证；不包含提交、推送或发布授权。勾选项表示已完成，条件未触发的项目单独注明。长期验证规则仍由[工程质量](../engineering-quality.md#5-默认验证门槛)拥有，命令组合由[package.json](../../package.json)拥有。

## 1. 目标与判断依据

目标是减少一次局部修改完成之前与其风险无关的操作，同时保留发现真实回归的能力。完成后，保存一个自由专注选项，应能验证保存、恢复和异常回退后结束本地工作，而不必顺带执行其他工具或全站场景。

从第一性原理看，验证需要回答三个问题：改动可能破坏什么事实；什么观察能发现这种破坏；为取得这个观察，需要执行哪些代码和准备哪些环境。检查数量、命令长度和报告篇幅本身都不能增加可信度。

据此作出以下取舍：

1. **范围由因果关系决定。** 修改某个选项的存储逻辑，需要覆盖读取、写入和使用它的界面；其他页面只有共享行为受影响时才进入验证范围。
2. **重复执行必须有独立价值。** 性能重复采样可以揭示波动；在输入、配置和执行语义相同的情况下再次做类型检查，通常没有新增证据。
3. **产品检查和检查器自测保护不同对象。** 修改译文需要证明译文和生成结果有效；修改校验器才需要证明它能拒绝错误输入。
4. **回归保护重于规定操作顺序。** 必须判断测试能否发现实际错误，但不应让所有小修都经历同样的先失败、再修改步骤。
5. **局部完成和整体验收各有用途。** 局部验证支持日常开发；CI、发布和实际跨模块变化保留完整验收。局部结果不冒充整体结果。

这些判断用于本次删减和调整，不新增日常审批、验证台账或统一报告要求。

## 2. 已核实的现状与边界

以下是方案编写时的静态检查结果，实施前只需核对相关输入是否变化，不必重新开展全仓审计。

| 问题 | 当前事实 | 风险或成本 | 目标 |
| --- | --- | --- | --- |
| 局部性能变化触发整套基准 | 工程质量要求相关变化运行 `perf:stable`；该脚本执行七类基准，每类五次 | 一处局部变化会触发 35 次基准子进程调用，包括无关模块 | 局部选择已有对应专项；整体性能验收保留整套采样 |

| 小修固定先红后绿 | 小修规则要求先写失败测试或先确认已有测试失败，再修改 | 简单展示修正也可能为了操作顺序反复恢复代码 | 保留有效回归保护，按风险决定是否必须复现失败 |

## 4. A：让性能验证匹配实际影响

### 修改位置

主要修改[工程质量](../engineering-quality.md#风险追加与桌面验收)与 [PR 模板](../../.github/pull_request_template.md)。性能专项已有独立入口，默认不修改基准实现。

### 执行步骤

- [x] 阅读 `stable-benchmark-suite.ts` 和对应叶子脚本，区分每类基准观察的行为、环境和阈值。核实叶子入口不是无断言的演示命令。
- [x] 将“性能敏感的 read model、SQLite 查询或导航路径统一追加 `perf:stable`”改为“运行受影响行为的性能专项”；整体性能变化或正式整体性能验收再使用 `perf:stable`。
- [x] 同步 PR 模板中的性能检查说明，让局部任务能记录实际执行的专项命令，不因未运行整套而产生错误要求。
- [x] 保留 `perf:stable` 的七类基准、五次重复采样、失败退出和预算检查。局部只跑一类不能被报告为整套基准通过。
- [x] 对需要判断波动的局部性能优化，保持可比环境与必要的重复采样；不把“只跑一类”误解成“只运行一次”。优先复用现有专项，不为本次规则调整新增调度框架。

以下仅为本次路由核对示例，长期命令清单仍以 package scripts 为准：

| 修改的行为 | 相关现有入口 | 不自动追加的入口 |
| --- | --- | --- |
| 历史读模型 | `pnpm run perf:history-read-model` | 分类、概览、启动基准 |
| SQLite 查询计划 | `pnpm run perf:sqlite-query-plan` | 无关页面浏览器基准 |
| 启动装配 | `pnpm run perf:startup-bootstrap` | 没有共享影响的业务模块基准 |
| 多模块共用的数据读取或启动基础 | 按消费者选择，确需整体观察时用 `pnpm run perf:stable` | 不用单个叶子结果宣称整体性能无回归 |

### 验收

- [x] 对照三个场景检查规则：单模块查询优化选择对应专项；跨模块公共性能变化保留整体验证；不涉及性能行为的选项持久化不因“持久化”一词触发基准。
- [x] 若只改规则，运行文档检查和政策场景核对即可，不为证明规则删减再跑 35 次基准。
- 不适用：未修改性能运行器；保留原采样、预算与失败传播。

完成条件：局部性能变化有明确且可执行的相关入口，整套基准的保护能力不变。

## 6. C：消除完整链中的重复应用类型检查

### 必须保留的行为

- `check:types` 单独运行时，仍检查应用源码及测试/工具代码。
- `build` 单独运行时，仍先验证应用类型，再生成生产产物。
- `check:frontend` 单独运行时，仍保留原有构建与体积检查语义。
- `check` 必须同时包含应用类型、测试/工具类型、生产构建和 bundle 预算，任一失败都返回失败。

### 执行步骤

- [x] 展开当前 package script 调用关系，核实两次应用 `tsc` 的配置、源码、参数和中间步骤是否会改变受检输入；若发现两者保护不同事实，先说明差异，不直接删除。
- [x] 在 `package.json` 增加一个仅封装 `vite build` 的叶子命令，例如 `build:assets`。它只供组合复用，名称明确表明其不包含类型检查。
- [x] 将 `build` 组合为 `tsc && pnpm run build:assets`，保留独立 build 的类型保护。
- [x] 保持 `check:types` 以及独立 `check:frontend` 的契约不变。
- [x] 将 `check` 尾部原来的 `check:frontend` 调用换为 `build:assets` 与 `check:bundle`；前面已运行 `check:types`，因此尾部不再间接执行第二次应用 `tsc`。
- [x] 确认 `check:full`、`release:check` 和 CI 仍通过既有聚合入口取得完整保护，不新增绕过型 CI 开关。
- [x] 检查测试治理和外部 PR 准入对命令图的约束，分别处理“测试仍可达”和“命令组合发生授权变化”两件事。

目标调用关系：

```text
check:types     → 应用 tsc + 测试/工具 tsc
build:assets    → vite build
build           → 应用 tsc → build:assets
check:frontend  → build → check:bundle
check           → check:types → 其余既有检查 → build:assets → check:bundle
```

新增的是一个可复用命令叶子，不增加开发者需要执行的步骤。

### 准入兼容注意事项

[外部 PR 命令图检查](../../scripts/check-pr-intake.ts)当前要求旧检查步骤和可达脚本保留，不能假定删除重复执行会自动通过该比较。该保护用于阻止外部贡献静默降低门槛。

- [x] 用当前比较逻辑检查目标命令图，记录删除重复 `tsc` 以及聚合引用变化的具体判定。
- [x] 这是维护者已授权的验证政策调整，不为让本次差异自动放行而添加通用豁免、label 绕过或任意去重规则。
- [x] 优先保留对未来外部 PR 的原有严格比较；新基线仍需拒绝删除唯一类型检查、测试或 bundle gate。仅当实际执行路径要求代码调整时，才修改对应判断并补精确反例。

### 验收

- [x] 检查完整脚本展开结果：应用类型检查一次，测试/工具类型检查一次，生产构建和 bundle gate 均存在。
- [x] 运行 `pnpm run check:test-governance:self-test` 和 `pnpm run check:test-governance`，确认测试入口完整、无孤儿和重复 owner。
- 不适用：准入比较逻辑保持不变；已用新命令基线验证移除唯一类型、测试或 bundle 检查仍被拒绝。
- [x] 用可恢复的隔离 fixture 验证类型错误会让独立 `build` 和完整链失败；测试/工具类型错误会让完整链失败；成功不能由 `||`、吞掉退出码或固定返回值伪造。
- [x] 负向验证不在其他任务的产品文件里制造错误；优先使用临时副本或现有 fixture，结束后清理本次创建的资源。
- [x] 在稳定候选的最终聚合运行中确认构建和预算通过。需要验证独立 `build` 契约时可单独执行一次，但不要把这种实施期验证变成每个普通任务的新门槛。

完成条件：完整链少一次等价应用类型检查，所有独立命令的既有承诺和失败传播仍成立。
