# Patina 质量改进执行单

目标是在保持现有产品行为和兼容承诺的前提下，争取把综合评价从 **8.4/10** 提升到 **9.0/10 或以上**。优先投入那些能防止用户打不开数据库、恢复出错误数据或看到错误统计的改动。若剩余机会只有拆文件、增加测试数量或提高指标，按实际分数收尾。

本单以 2026-11-05 审查的 `81406df7` 为基线。勾选表示该步骤已有下方对应的执行结果；环境限制和移交事项单列。架构与验证沿用[架构规范](../architecture.md)、[工程质量](../engineering-quality.md)和[稳定期修复守则](../issue-fix-boundary-guardrails.md)。

## A · 覆盖恢复中断后仍能启动（P1，优先）

**成立条件。** 启动程序一旦看见正式恢复标记，就应能读到完整的回滚文件名。原库移动前中断，原库仍可打开；移动后中断，由标记恢复原库；提交点之后重启，应打开已提交的新库。当前实现直接创建正式文件，再写入文件名。审查中模拟了两步之间退出，原库完整性为 `ok`，启动恢复函数却连续两次拒绝空标记。[标记与文件切换](../../src-tauri/src/data/sqlite_pool/restore.rs) · [启动入口](../../src-tauri/src/data/sqlite_pool.rs)

- [x] 用表覆盖中断位置：准备标记时、正式标记发布后但原库移动前、原库已移动但候选库尚未安装、候选库已安装但提交前、提交后尚未清理回滚文件。每格写明下次启动应打开哪一个库，以及哪份文件仍须保留。
- [x] 在现有 Rust 恢复测试中，先让旧代码复现“正式标记已创建、内容为空”的启动错误。另用子进程或确定性的文件操作故障点，在标记发布边界停止并从正常启动入口重开；不要依赖碰运气的 sleep。
- [x] 在现有标记 owner 内，用同目录的独占临时文件写完整名称、刷新并关闭，再以 Windows 支持的原子操作发布。检查目标已存在、刷新失败、重命名失败的处理；只有发布成功才允许移动原库。启动时忽略未发布的临时文件。
- [x] 单独处理旧版本已留下的空/残缺正式标记。只有能证明原库完整、且文件布局唯一指向“尚未切换”的状态，才进入安全恢复路径；有回滚候选、路径异常或身份矛盾时保全文件并给出可操作的诊断。覆盖旧的有效标记、非法路径及回滚文件受锁三种输入。
- [x] 对每个中断点连续启动两次，检查业务记录、`PRAGMA integrity_check`、候选库/回滚库归属和可写连接池的发布时间。保留现有“标记删除失败不得发布候选池”用例。用 `pnpm run test:rust:focused --filter sqlite_pool::restore` 确认非零用例通过。

## B · 运行中备份的专注计时应守恒

**成立条件。** 合并后的任务以暂停状态等待用户恢复，并保留截至备份时刻已经发生的进度。备份之后经过的时间不能计入。现有代码在清除开始时间时直接复制原始累计值；“开始后运行 10 分钟、尚未暂停”的自由专注可合并成 0 分钟。[快照准备](../../src-tauri/src/data/backup/snapshot/restore.rs) · [自由专注时钟](../../src-tauri/src/domain/free_focus.rs) · [番茄钟合并](../../src-tauri/src/data/repositories/tools/backup_restore.rs)

- [x] 构造三份源数据：刚运行 10 分钟的自由专注、已消耗一部分的休息倒计时、运行中的番茄钟。指定开始、备份和恢复三个不同时间。另设一个此前暂停后又继续的任务，检查已累计部分只加一次。
- [x] 从同一源制作快照，走实际准备和合并入口。先断言暂停状态，再断言精确毫秒数；验证目标库已有的运行任务仍有且仅有一个活动时钟。保留现有先暂停再备份的用例作为对照。
- [x] 在合并的候选库或读取阶段使用现有备份截止时刻，把任务交给各自的计时 owner 结算。自由专注分别计算累计和休息剩余，番茄钟复用现有阶段剩余时间算法。只结算运行中任务；覆盖空开始值、时钟倒退、剩余时间降到零。
- [x] 用相同快照合并两次，确认任务数、进度和删除标记稳定。对覆盖恢复单列对照用例，避免合并专用的暂停策略改变既有覆盖恢复语义。[自由专注仓储和测试](../../src-tauri/src/data/repositories/tools/free_focus.rs) · [番茄钟任务和测试](../../src-tauri/src/data/repositories/tools/pomodoro_tasks.rs)

## C · 重复提醒推进后仍是同一条提醒

**成立条件。** 用户创建的是一条规则，名称、计划时间、启停状态和下一期时间都可以变化。把同一份旧快照合并回已经推进一期的目标库，目标库的当前状态应胜出；同时创建的两条不同提醒都应保留。[提醒状态推进](../../src-tauri/src/data/repositories/tools/timed_reminders.rs) · [当前合并判重](../../src-tauri/src/data/repositories/tools/backup_restore.rs)

- [x] 通过创建入口建立每日提醒，备份第一期，在目标库确认提醒使其推进到第二期，再合并旧快照。断言仍是一条、到期时间仍为第二期、旧期不会再触发。用改名和延时再覆盖一次可变字段。
- [x] 查清当前 schema 和备份记录携带哪些稳定身份。分别检验源库内部 ID 跨库碰撞、创建毫秒相同、两个独立提醒同名同时间。用这些反例淘汰会错认或吞掉用户提醒的匹配规则。
- [x] 若现有字段能无歧义标识同源实体，在工具仓储内完成判重。若确需持久化新身份，先写明新库创建、原库升级、旧快照首次合并、重复合并的映射和冲突规则，再按[发布升级边界](../versioning-and-release-policy.md)实施迁移。对不可判定的旧记录，明确保全策略及残余重复风险，不按猜测删除或覆盖。
- [x] 对当前与旧 schema 分别验证：同源重复导入两次、跨库独立提醒并存、目标已暂停或取消、事务中途失败后重试、重启后实际触发次数。确认身份映射和提醒写入同一次提交。[现有重复提醒测试](../../src-tauri/src/data/repositories/tools/timed_reminders/tests.rs)

## D · 下载的文件须匹配所选定时备份

**成立条件。** ZIP 自身完整证明文件可读，索引中的归档摘要标识用户选中的那一份。两个有效的 Patina 归档也可能内容不同。目前定时上传保存摘要，下载预览没有比较它。[WebDAV 索引和下载](../../src-tauri/src/data/remote_backup.rs) · [界面确认入口](../../src/features/settings/hooks/useRemoteBackupState.ts)

- [x] 用本地 WebDAV 夹具生成两个各自有效、内容不同的 ZIP。索引登记 A 的摘要，下载 URL 返回 B。经真实下载命令验证旧实现会交付 B 的预览；同名路径和有效 ZIP 是这个用例的必要条件。
- [x] 在原生下载 owner 内，把预览计算出的归档哈希与该索引条目保存的摘要比较。对于有摘要但格式错误或不匹配的条目，移除本次临时下载并返回明确错误，界面不可进入恢复确认。沿用现有的“预览到执行”哈希复核，保护确认后文件被替换的情形。
- [x] 明确旧条目和手动备份缺少摘要时的已发布兼容行为；区分缺字段和字段损坏。测试有效摘要、错摘要、损坏归档、兼容条目、失败后再次下载和临时文件清理。涉及新用户文案时按[本地化规范](../localization.md)处理。
- [x] A–D 合入同一候选版本后运行 `pnpm run test:tauri-runtime-smoke --group data-recovery`。核对真实 IPC 下载、预览、确认、合并/覆盖及重启数据；确认注入错误的步骤没有修改目标库。[已有 WebDAV 原生场景](../../tests/tauriWebDavRuntime.ts)

## E · 让短区间网页统计的成本与请求相称

- [x] 固定一天或一小时的请求、该范围内的命中行、100 个域名和预期结果，只增加窗口外的旧事实。对 1 万、10 万两档记录完整命令耗时、前置汇总 VM 步数和查询计划；区分冷启动、首次页面加载和重复刷新。计时代码使用普通构建，和覆盖率采集错开。
- [x] 沿 History 网页范围、Data 网页聚合及其分块请求分别列出返回字段的实际消费者。查明哪些操作需要全域目录，哪些只需要近期成员，哪些必须取得组内历史最优图标。记录快照修订号、跨块一致性、并发写入和重试责任。
- [x] 优先试验按命中域名或组读取，复用已有局部读取能力。用跨天重叠片段、长尾域名、范围外成员拥有最佳图标、并列时按域名决胜、匿名/禁用成员、独立例外与规则变更做新旧结果对照。若缩小范围会改变答案，先保留原语义。
- [x] 如索引读取仍不足，再比较按可信修订复用元数据的成本。列清规则修改、记录删除、图标更新和恢复后何时失效，以及首次构建成本。只有测量证明有必要才引入持久派生状态，并沿用现有 Rust 数据 owner 和失效/重建边界。
- [x] 用同一夹具复测。重复短区间请求应避开每次重做全历史窗口汇总；分别报告首次和热路径的 p50、p95、最大值与 VM 步数。若成本只是转移到首次读取或写侧，报告该代价。用同版本结果一致性和串行 `pnpm run perf:stable` 验收；未获得净收益时撤回试验。
