## 1. 从第一性原理定义目标

### 1.1 产品测量的对象

Patina 自动追踪测量的是符合产品规则的桌面活动时间。应用会话表达这段时间属于哪个前台应用；网页片段进一步表达浏览器活动时间属于哪个网页。收到网页 URL、标题或扩展心跳，本身不能证明从上次观察到现在一直存在有效网页活动。

因此：

1. 系统前台事实和追踪状态决定时间是否有效。
2. 扩展提供网页身份及其活动状态，不能自创桌面计时规则。
3. 网页有效区间必须受到对应浏览器有效活动区间约束。
4. 页面汇总、时间轴和详情消费这些事实，不能分别重新解释 AFK、暂停或恢复；固定事实上的计算和显示改动由配套详情方案负责。

应用会话本身也需要验证。网页没有超过浏览器，并不能证明两个数字都正确：如果浏览器把排除应用或停机空档计入，网页受其约束仍可能一起多记。因此先验证应用归属和有效区间，再验证网页对浏览器区间的包含关系。

轻量工具测量用户主动启动的运行时间或到期时间，产品语义不同。本方案不修改正计时、倒计时、番茄钟、提醒器和累计使用提醒的规则或实现。源活动事实修正可能自然影响既有消费者，但不纳入工具侧改造。

### 1.2 用区间表达不变量

采用毫秒时间戳和左闭右开区间 `[start, end)`。设 `R` 为统计范围，`B_b` 为浏览器 `b` 的有效应用区间集合，`W_d,b` 为域名 `d` 在该浏览器中的有效网页区间集合：

```text
W_d,b ∩ R ⊆ B_b ∩ R
网页有效时长 = 合法网页区间经裁剪、去除重复后的区间长度之和
同一浏览器所有网页的有效区间总量 ≤ 该浏览器有效活动总量
```

比较时必须固定日期、时区、数据来源、纳入规则和快照截止时刻。跨浏览器合并的网站总量不能只与一个浏览器比较；应用分类是应用活动的重新分组，网页时长不能再次叠加到应用总量。

历史数据来源或排除规则不一致时，应明确可比较的集合，不能直接截断总量使数字相等。

对同一设备的原生自动追踪，另有以下约束；导入数据按既有来源政策单独处理：

- 应用会话只能覆盖符合既有前台、AFK、持续参与、暂停及排除规则的活动。
- 从可追踪应用 A 切到已排除应用 B，必须结束 A；B 的使用时间不能归给 A。
- 已确认的停用和停机区间不补记；缺失观察只能按明确的保守恢复策略处理，不能推定为持续活动。
- 一个有效时刻最多属于一个原生活动应用；会话归属以持久化成功的身份为准。
- 状态转移失败不能被记为已完成；内存活动身份、数据库会话和对外状态必须能够重新对账。

### 1.3 正确的数据流

```text
系统事实 / 扩展观察
  → 追踪状态与网页归属决策
  → 有效活动区间
  → 原子持久化与派生状态失效
  → 按统一范围读取
  → 分类、汇总、时间轴与详情
  → 最后进行显示取整
```

事件实际生效时刻不等于异步处理时刻。最后聚焦窗口不等于当前系统前台；连接状态不等于网页仍有计时资格。相同 URL 或标题不能证明暂停、失联和休眠期间存在连续活动。展示连续性可以影响分组，不能填补没有活动事实的空档。

## 2. 已验证的实现证据

### 2.1 网页与应用边界差异

- `engine/web_activity/mod.rs` 检查追踪状态、AFK 和浏览器可执行文件候选集，但没有核对网页来源与前台浏览器是否对应，也没有使用活动会话边界或采样新鲜度。
- `app/web_activity_bridge.rs` 收到活动变化事件后启动异步同步；同步重新读取当前快照，不消费事件携带的结束时间。
- `engine/tracking/transition.rs` 的 AFK 转换可回溯到最后输入时刻；网页结束使用同步处理时刻，两者边界不同。
- `app/web_activity.rs` 启动恢复用当前时间结束旧网页片段；应用会话恢复优先使用已保存的 tracker heartbeat。
- History 网页汇总和 Rust 网页分析把未结束片段延伸到读取时刻；网页累计提醒也直接累加该片段。
- 扩展源码的隔离模拟确认：失焦不发送状态变化，周期回调仍可发送最后聚焦窗口的标签页；内部页面和私密页面不发送旧网页失效通知。
- 正常切到非浏览器应用存在网页停止路径，不能据此认定每次切出都会持续计时。

## 3. 范围

### 纳入

- 应用与网页的有效活动边界、浏览器归属与网页有效状态。
- 普通应用切入排除目标、失败后归属恢复、缺失心跳恢复及活动快照同步的实现修复。
- 暂停、AFK、持续参与结束、锁屏、休眠、采样失效和异常恢复。
- 向 History、Data、Dashboard 和详情提供一致的活动有效截止与事实变更通知；这些消费者用于验证源记录正确性。
- Patina 与伴生扩展在现有协议内的活动判定、发送顺序及既有输入回归；协议变更仅按第 4.1 节条件评估。

### 不在已确认范围内

- 后台媒体播放计时和普通应用追踪策略变更。
- 固定记录的去重、分组空档、详情最短时长筛选、取整与展示文案；这些改动归配套详情方案。
- 推测性历史数据清洗。
- 将导入历史自动纳入实时累计提醒。
- 轻量工具的计时、累计、停止、提醒与到期行为，以及工具侧代码改造。
- 远程写入、提交、推送和发布。

## 4. Owner 与不变量

| 结果 | Owner | 不变量 |
| --- | --- | --- |
| 有效应用区间 | `engine/tracking` | 有效结束时刻由追踪决策产生，不能由异步消费者的执行时间代替 |
| 应用切换与失败恢复 | `engine/tracking/runtime`、`transition`；事务由 Rust `data` 承担 | 排除目标不能使前一个应用继续累计；失败不推进已提交状态，恢复核对真实会话身份 |
| 网页活动生命周期 | `engine/web_activity` | 网页仅能在对应浏览器有效活动期间累计；过期状态不能跨暂停或恢复继续使用 |
| 浏览器标签页状态 | Patina Web Sync background | 活动标签页与实际窗口聚焦状态一致；无可记录网页时使旧状态失效，保留私密元数据过滤 |
| 持久化事实与汇总 | Rust `data` | 写入、结束和派生读取遵循同一边界；恢复不补记停机时间 |
| 事实消费边界 | tracking/web activity 提供有效截止，各 feature 消费 | 不在页面重新判断 AFK；固定区间后的整理与显示由详情方案承担 |
| 协议契约 | 两仓 `docs/web-activity-protocol.md` | 默认沿用现有协议及 Firefox 可选字段语义；只有必要变更成立时评估跨版本接收边界 |

### 4.1 最小修复路径与条件决策

先在 tracking owner 修复原生区间，再让网页复用经过验证的应用事实。排除场景应区分“前台切入一个已排除目标”和“设置修改要求停止某个指定应用”：前者需要结束此前实际开放的会话，后者仍须保护不相关的活动应用。不能直接把所有按 exe 结束的 API 改成无条件结束。

默认先复用现有应用会话、网页字段、有效结束事件和运行状态，修复入口校验、结束时刻、失效处理与查询截止。写入时仍须防止 HTTP 预检查之后会话发生变化，但这不直接要求新增数据库字段。

AFK 回溯可能越过多个已经切分的网页片段。必须验证现有证据能否准确界定应处理的片段，不能只关闭最后一个未结束片段，也不能把时间重叠或 exe 相同当成修改未知历史的充分证据。

数据库结构和外部协议分别判断，不能因为其中一项需要变化就默认扩大另一项：

| 路径 | 进入依据 | 执行结果 |
| --- | --- | --- |
| 现有结构与协议内修复（默认） | 当前已确认行为缺口及其反例 | 直接修复原 owner，运行应用、网页和恢复回归；满足契约后结束该问题，不追加结构改造 |
| 新增持久化信息（条件） | 完成可独立验证的最小修复后，仍有反例证明准确归属、多片段回溯或崩溃恢复缺少必要信息；说明现有字段和状态为何无法补足 | 才比较字段、关系表等最小方案，并记录 owner、恢复成本和受影响的已发布数据；未成立则不新增结构或 migration |
| 外部协议变更（条件） | 接收端校验、现有协议表达和发送端修复后，仍有反例证明必要活动/失效信息无法表达，且不能在明确误差内满足契约 | 才设计最小状态变化，核对隐私与真实支持客户端；未成立则保持现有协议，不建立兼容分支 |

条件决策须记录反例编号、缺失的信息、已验证的最小方案、不能满足的契约及预计变更文件。若反例仍无法解决，应如实保留未完成状态，不能以“不改结构”为由降低正确性要求，也不能用尚未证明的风险预先建设兼容层。

仅在结构变更被选定后，migration 才用于升级已有用户数据库。它不授权新旧两套计时实现。仅在确有已发布协议或数据边界需要时，才保留最小适配，并写明支持对象、存在理由和退出条件；全部输入进入同一个计时实现，不创建 `V2`、`New` 等平行链。

### 4.2 明确拒绝的修复方式

- 在 History/Data 使用 `min(网页总量, 浏览器总量)` 掩盖错误区间。
- 把未经验证的原生应用总量当作绝对正确的上限，忽略应用自身的错误归属和恢复空档。
- 在错误分支只改内存状态或吞掉错误，却不重新核对持久化会话。
- 将面向指定应用的排除设置 API 全部改成无条件结束当前会话。
- 为网页复制普通应用的 AFK、持续参与或暂停规则。
- 仅提高扩展上报频率，继续允许旧网页状态无限有效。
- 只比较 `browserKind` 就声称解决多窗口、多配置和全部旧客户端归属。
- 把历史网页自动关联到时间上最近的浏览器并修改时长。
- 修改已发布 migration SQL 来替代新增 migration。
- 未证明现有结构或协议不足，就预先新增关联表、迁移、兼容壳或双读双写路径。
- 顺手改造轻量工具或创建全产品通用计时器框架。

## 5. 执行阶段

以下步骤已获准实施。阶段内按顺序推进，只有退出条件成立才进入依赖它的下一阶段。
