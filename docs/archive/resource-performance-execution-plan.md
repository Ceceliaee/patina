## 1. 目标与第一性原理

Patina 的必要工作是观察活动、可信地保存时间、按需展示数据。优化目标是在这些结果不变的条件下，减少重复工作、无效唤醒和不再使用的资源，并改善用户等待时间。

资源成本按以下关系分析，而不是只比较任务管理器的一个数字：

| 资源 | 成本来源 | 优先追问 | 可接受的优化方向 |
| --- | --- | --- | --- |
| CPU | 调用频率 × 单次成本，加上序列化、调度和渲染 | 输入是否变化？结果是否被使用？能否少做一次？ | 消除重复查询、合并请求、复用派生结果、降低无效唤醒 |
| 内存 | 同时存活的对象、缓存、运行时和图形资源 | 谁持有？何时失效？释放后是否回到稳定平台？ | 限制保留量、缩短无用生命周期、减少跨边界复制 |
| 线程 | 运行时工作池、SQLite worker、Windows/COM 和 WebView2 | 线程是否工作、阻塞或不断新增？ | 先定位创建与等待原因，再调整对应 owner |
| 句柄 / GDI / USER | 获取次数与释放次数的差额，以及固定运行时成本 | 是常驻资源、临时峰值，还是循环后残留？ | 明确所有权和释放路径，验证失败及取消路径 |
| I/O | 查询、事务、日志和检查点 | 无变化时是否仍提交？写入能否合并？ | 减少空操作和重复提交，保持持久化与恢复保证 |
| 交互延迟 | 主线程连续工作、排队、布局绘制和 IPC | 用户等待发生在哪段调用链？ | 减少关键路径工作，先测量再考虑分块或 Worker |

本专项遵守以下约束，具体长期规则由对应母文档拥有：

- [产品原则](../product-principles-and-scope.md)与[优先级](../roadmap-and-prioritization.md)：追踪正确性和数据安全优先。
- [架构](../architecture.md)：平台事实归 platform，计时行为归 engine，持久化归 data，页面读模型归 feature；app 与 command 保持薄编排。
- [工程质量](../engineering-quality.md)：测量场景、验证层级、性能预算与体验保护。
- [修复边界](../issue-fix-boundary-guardrails.md)：按实际 owner 和风险选择最轻实现；新共享抽象或跨层端口需要先重新判断边界。
- [Web Activity 协议](../web-activity-protocol.md)：网页资格、观察有效期、匿名和标题隐私契约。
- [Quiet Pro](../quiet-pro-component-guidelines.md)：维持窗口、焦点、加载与交互状态。

不预设“CPU 必须降低某个百分比”或“线程必须少于某个数”。先建立受控基线与波动范围，再判断收益。没有测出收益的复杂方案可以被否决，否决本身是有效阶段结果。

### 2.2 证据限制

- 上述是既有会话的被动观察，没有固定用户操作或后台负载，不能称为受控空闲基线。
- 安装版、开发版的数据、构建模式与窗口状态不同；工作区还存在其他任务的未提交修改，不能作为 A/B 优化对照。
- 五秒 CPU 样本是区间平均；短尖峰可能被平滑。整机折算只用于统一口径，不保证与任务管理器显示完全一致。
- 工作集合计会重复计入共享页；私有提交不是物理驻留，也不是 JS heap。
- 五分钟平稳不能排除长期泄漏；新增窗口或缓存预热的增长也不能直接判为泄漏。
- settings 扫描的耗时复现使用内存 SQLite 与 JS JSON 解析，只证明查询形状和规模趋势，不代表真实 Rust 热点成本。
- 四组基准通过不等于完整 `perf:stable`、真实 WebView2 交互或长期运行验证通过。
- 尚未获得 CPU 调用栈、JS heap retaining path、句柄类型差分或受控发布构建数据。

## 3. 范围、顺序与阶段出口

每阶段以“复现成本 → 确认 owner → 最小改动 → 正确性验证 → 同条件测量 → 保留或撤回”为闭环。先完成 A、B，再推进候选项；不要同时修改全部候选后只测一个总结果。

| 阶段 | 内容 | 默认顺序与出口 |
| --- | --- | --- |
| A | 固定环境与正式基线 | 必做；产物、数据、场景和统计口径可重现 |
| B | 定位 CPU、内存、线程、句柄及 I/O 来源 | 必做；每个候选有机制证据和成本证据，或明确尚未确认 |
| C | Widget 隐藏工作抑制 | 首批候选；隐藏调用减少，恢复状态和交互无回归 |
| D | tracking 规则缓存 | 首批候选；稳定输入不重复扫描，隐私设置立即按契约生效 |
| E | 读模型与网页过期调度 | 分两个独立改动；空操作减少且不会漏维护或错过截止 |
| F | 心跳提交与应用名称解析 | 分两个独立改动；恢复边界不变，提交或文件读取减少 |
| G | 页面长任务与平台查询实验 | 仅在 B 定位后实施；否则记录延期理由 |
| H | 综合回归、长时观察与收尾 | 必做；收益可复现、风险有证据、未做项有处置 |

本专项不改变默认计时精度、统计归属、匿名语义、Web Activity 协议、窗口视觉方向或后台优化默认开关；不清理用户历史来改善基准。未经测量，不缩减 Tokio 工作线程数，也不强制清理系统工作集。

## 5. 阶段 B：把占用归因到真实 owner

### B1. CPU 与调度

- [ ] 将高 CPU 时间段关联到进程类型，区分 Rust、renderer、GPU、browser 与 utility。
- [ ] 对可复现的热点获取短时 CPU 调用栈；先确认本机诊断工具和权限可用，记录采集配置及符号可用性。不可用时明确保留“尚未归因”。
- [ ] 对 Rust 热点区分 SQLite、JSON、前台查询、COM、版本信息和调度等待；对 renderer 区分 JS、样式/布局、绘制和重复 IPC。
- [ ] 在真实 owner 或测试端口计数调用次数、耗时与排队，不记录标题、URL 或 token；诊断代码应低开销且有移除/保留判断。
- [ ] 区分“异步任务数量”与“OS 线程数量”；对异常线程增长追踪创建、结束、超时后的存活及等待原因。

### B2. 内存与资源生命周期

- [ ] 窗口完成预热后记录平台值；重复同一操作并等待明确释放完成，再比较下一轮，不用固定短 sleep 假定回收完成。
- [ ] 如 renderer 残留递增，在隔离诊断中比较 heap snapshot 的对象和 retaining path；同时检查图像、图形资源与 native 内存，不能只看 JS heap。
- [ ] 如 Rust 残留递增，检查有界缓存、Arc/事件订阅持有、未完成任务和返回值复制；用计数与分配来源验证，不能仅凭全局 Map 的存在判泄漏。
- [ ] 如句柄/GDI/USER 递增，取得类型或来源差分，检查成功、失败、取消、超时和重建路径的释放。
- [ ] 复核 [Windows guards](../../src-tauri/src/platform/windows/handles.rs)、前台探测防重入、图标提取并发上限和窗口 generation 防护；保护已有边界。

### B3. SQLite 与 I/O

- [ ] 统计稳定场景内规则查询、心跳 UPSERT、网页过期 UPDATE、read model 维护的实际频率和耗时。
- [ ] 在匹配 schema 与数据分布的隔离库运行 `EXPLAIN QUERY PLAN`；记录 SQLite 版本、统计信息与索引，区分覆盖索引扫描和事实表全扫描。
- [ ] 分别测空闲、活动写入、dirty 积压、恢复重建时的连接排队与事务时长。
- [ ] 输出候选结论：已确认成本、仅确认重复机制、未复现或不值得优化；按成本、风险与实现复杂度调整后续顺序。

## 9. 阶段 F：减少提交与同步文件读取

### F1. 合并同轮到期的 tracking 时间戳写入

入口：[时间戳持久化状态](../../src-tauri/src/engine/tracking/runtime/loop_state.rs)、[tracking 数据端口](../../src-tauri/src/engine/tracking/ports.rs)、[tracking 数据实现](../../src-tauri/src/data/tracking_runtime.rs)。

**处置：否决本轮合并。** 当前 heartbeat 在设置读取和采样业务执行之前持久化，successful sample 在可信采样完成后推进。把两次写入合并到后者会延后活性记录，把合并放到前者会提前确认成功采样。尚无 I/O 归因证明值得更改该恢复边界，因此保持两个原有时间点及端口，下列合并实施步骤不执行。

- [ ] 计数成功与失败采样时两个时间戳的独立提交，检查既有事务和调用顺序，先判断是否确有可合并的同轮写入。
- [x] 确认 heartbeat 表示运行循环活性、successful sample 表示最后可信观察；采样失败不能推进后者，两个实际调用阶段不能直接视作一个原子事实。
- [ ] 若新增数据端口确有必要，先完成边界判断，在 data 实现单次事务；engine 只传本轮应持久化的值，不承接 SQL。
- [ ] 两项同时到期时原子提交，只有一项到期时仅写该项；状态中的 persisted 时间只在对应提交成功后推进。
- [ ] 合并不延长原有恢复窗口；若因等待采样结果影响 heartbeat 时序，需要重新证明 watchdog 与恢复保证。
- [ ] 注入 begin、第二次写入和 commit 失败，验证回滚、重试、独立语义、数据库重开与时钟回拨。
- [ ] 用确定性恢复 fixture 比较崩溃前后封口；不得借真实用户活动会话做破坏性退出实验。
- [ ] 比较提交次数、WAL/I/O 与 CPU；撤回收益不明显且增加恢复复杂度的方案。

### 13.3 规则基准与资源结果

首次 `perf:tracking-policy` 使用实际 Rust/SQLx 读取与解析路径，debug、内存 SQLite；baseline 为逐次直接读取，candidate 为缓存读取。下表单位为每 600 次模拟采样的总壁钟毫秒；P50/P95 来自五个实验总耗时，样本少时 P95 等于最大值，不是单次采样延迟。该次有质量检查干扰，不能用于承诺真实安装版占用。

| 域名覆盖数 | 直接读取 mean / P50 / P95 | 缓存读取 mean / P50 / P95 | 平均总耗时减少 |
| --- | --- | --- | --- |
| 100 | 211.14 / 205.18 / 246.60 | 44.34 / 44.69 / 47.57 | 79.00% |
| 1,000 | 1,835.75 / 1,679.31 / 2,118.38 | 355.16 / 332.82 / 445.71 | 80.65% |
| 10,000 | 17,795.87 / 17,883.80 / 18,611.56 | 3,537.69 / 3,570.30 / 3,652.37 | 80.12% |

在规则与应用不变的一秒采样条件下，五秒缓存把每类查询的理论次数从 600 次减少到 120 次；数据库表暂不可用时仍能命中已成功读取的未过期缓存，用行为测试验证命中不访问数据库。缓存到期或失效后失败会立即采用保守值，恢复后下一次调用重新读取。应用切换、规则提交会提前结束复用，这个 80% 不能外推到所有工作负载。

新增 600 秒 debug 诊断采样正常结束，121 个样本、无不可读进程。主进程线程 32–36、句柄 438–484、GDI 25–32、USER 43–52；主进程私有提交 15.29–18.16 MiB。进程树私有提交 208.00–274.80 MiB、线程 202–249、句柄 3,492–3,978。窗口创建和销毁发生在采样期间，末值变化不是泄漏斜率，也不是候选改善量；仍保留长期验收缺口。

最终缓存实现另行串行复测；本任务未同时运行构建或其他性能检查，但普通机器后台负载仍存在。每组五对，输入、模式、单位和分位数定义同上。原始结果为 `policy-serial-final.log` 与 `policy-serial-final-summary.json`。
