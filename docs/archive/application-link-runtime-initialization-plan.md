## 1. 目标与第一性原理

应用关联改变的是记录的统计归属，而不是记录本身。既然用户已经保存了关联，同一份原始记录和同一份已保存设置，应当得到相同的统计结果，不应取决于用户是否刚进入分类页、是否在本次启动中重新保存过设置。

用三个对象描述本次问题：

- `R`：原始活动记录，保留原程序身份、时间边界和标题控制范围。
- `L`：用户保存的应用关联关系，成员映射到主程序。
- `V`：统计视图，由现有读模型根据 `R`、`L` 和其他分类设置派生。

正确结果应满足 `V = F(R, L, 其他设置)`。进程重启可以清空内存缓存，但不能改变输入相同时的统计结果。因此，首次生成可信统计前，运行时必须获得持久化的 `L`；后续刷新必须用最新成功加载的关系替换旧关系。

本次恢复以下可观察结果：保存 `wechatappex.exe → weixin.exe` 后，完整退出并重启应用，首次打开今日排行即可看到合并后的微信；不需要先进入分类页或重新保存。解除关联后重启，两者恢复独立展示，总有效时长不因关联或解除而变化。

长期行为以[产品原则](../product-principles-and-scope.md)、[架构](../architecture.md)、[修复边界](../issue-fix-boundary-guardrails.md)和[工程质量](../engineering-quality.md)为准。本文只保存本次执行步骤与证据，不建立新的产品规则。

## 5. 失败定位与恢复

| 观察到的失败 | 下一步 |
| --- | --- |
| 关系已读到但排行仍分列 | 检查快照应用先后顺序、实际统计输入身份与内存状态；不先改聚合算法 |
| 仅重新保存后正常，重启仍失败 | 检查新进程执行的初始化入口、构建版本和 profile，确认测试没有复用旧进程 |
| 解除后仍合并 | 检查空映射是否真正替换旧状态，以及读模型刷新是否使用旧快照 |
| 读取失败却出现正常“无关联”结果 | 查找吞错默认值与 ready 状态推进，恢复错误传播及重试边界 |
| 修复后总量变化 | 比较原始记录和有效区间；关联应只改变分组，不能改时间事实 |
