## 1. 要解决的问题

本轮目标是恢复文档对真实工作的帮助：用户能得到准确的产品说明，贡献者能按说明完成操作，维护者能找到唯一的现行契约，代理能按任务读取并完成已授权工作。成功不能用删了多少行、保持多少文件或新增多少检查代替。

前序审查确认了三种不同问题：过去整理遗漏的事实错误与重复来源、后续变更没有同步读者入口、局部正确的新增逐渐混合长期原则和实现细节。必须分别处理，不能把所有问题解释成近期文档膨胀，也不能默认全库重写。

本方案编制时只获编写授权。2026-10-02 用户随后明确要求执行至完成、勾选归档并开展对抗式审查；本轮按该授权实施本地修复与验证，不包含 commit、push 或远端修改。

## 2. 从第一性原理推导目标

### 2.1 文档服务什么

文档的价值是帮助读者在缺少原会话的情况下做出正确行动。它需要同时满足：答案正确、容易找到、必要条件完整，以及修改后其他入口不提供相反答案。

| 必要条件 | 推导出的处理方式 | 可以观察的结果 |
| --- | --- | --- |
| 同一问题应得到一致答案 | 一个事实有唯一详细 owner，其他入口保留必要摘要和链接 | 从 README、贡献指南或根指令进入，最后回到同一契约 |
| 读者只掌握当前任务上下文 | 按用户任务组织入口，术语与前提在需要处说明 | 小型文案修复无需先读发布、协议与全部架构文档 |
| 软件变化快于手工副本 | 配置、schema、脚本和源码拥有机器事实 | 文档解释用途、边界和调用方式，不复制全量执行图 |
| 正确行动需要知道失败与例外 | 精简前列出受保护命题 | 删除重复后仍知道谁在何时做什么、失败怎样恢复 |
| 实现修复不一定改变承诺 | 先判断契约是否变化，再决定是否写文档 | 满足已有规则的修复可以只改实现和测试 |
| 局部正确不保证整体合理 | 修改后读完整章节及关联入口 | 新段落不会把产品原则变成具体功能操作手册 |
| 检查器只能检测有限事实 | 机械检查与语义、读者路径验收分开 | 检查通过不被表述为整个文档体系完全正确 |
| 后续维护才决定治理是否有效 | 通过真实任务观察修订决策 | 能同时展示一次正确的不更新和一次必要的 owner 更新 |

## 3. 范围、授权与受保护边界

### 3.1 预期实施范围

- 根入口：`AGENTS.md`、中英文 README、`CONTRIBUTING.md`、PR 模板。
- 十份顶层长期文档：逐份审查，只有发现事实、职责或表达缺陷时修改。
- 两份远程推送示例文档，以及其引用的源码和配置核对。
- `scripts/check-doc-governance.ts` 的有证据覆盖缺口、自测和必要的命令接入；PR intake 仅作真实验收入口，除非另有独立证明的实现缺陷。
- 归档链接专项：修复搬迁造成的断链，给历史源码引用保留历史含义。
- 当前本地文档工作方法的有界核对；只有发现直接导致本轮失败模式的指导缺陷才提出对应修订，具体本地清单和评估原始材料不进入长期文档。

### 3.2 不由本方案改变的事实

产品功能、追踪与匿名语义、数据写入、升级、备份恢复、协议兼容、权限和发布不可变性保持原有契约。不得为了让说明更容易成立而修改 Worker 存储、改成私有 `/state`、改变应用行为或降低验证门槛。

Git 提交、push、tag、Release、Issue、Project、外部发布与部署分别遵守既有授权。文档里的示例命令不是执行这些动作的授权。若需要联网核对，先检查工具、环境与 Windows 系统代理，沿用适用配置，不输出凭据、不修改永久代理、不把 PAC URL 当作代理地址。

未识别出对应现有 Project item 时不读取或推测私有队列。后续请求若明确映射某个 item，按 [Project 维护指南](../github-project-maintenance.md) 核对 live state；仓库不保存其当前内容。

### 3.3 何时需要重新决定

常规措辞、链接、错误事实和唯一归属修复可在实施授权内继续。下列情况只暂停依赖该决定的动作，其他工作继续：

- 修订将改变用户已经依赖的产品承诺、外部贡献义务或实际验证门槛，而不只是澄清适用范围。
- 唯一合理落点需要新的长期文档或修改十份上限，现有任务授权不足以决定。
- 事实只能通过生产凭据、远程写入、破坏性恢复或不可用环境证明。
- 工作树中其他任务的修改与本轮目标重叠且无法安全区分。

每次说明具体争议、证据、推荐方案与受阻动作，不笼统询问是否可以继续整个任务。

## 7. 阶段 C：恢复长期文档的职责和细节层级

### 7.1 按读者问题逐份判断

| 文档 | 应回答的问题 | 本轮重点检查 |
| --- | --- | --- |
| AGENTS | 当前任务读什么、可以做什么、完成到什么程度 | 常驻底线与路由是否足够；有无领域完整流程副本 |
| 产品原则 | 服务谁、解决什么、哪些能力不进入主线 | 网页删除、关联等细节中哪些是产品承诺，哪些是实现验收 |
| 路线图 | 多个合格事项如何排序 | 与产品、Project、贡献指南的优先级说明是否竞争 |
| 架构 | 谁拥有事实、生命周期、数据与调用边界 | 路径示例是否帮助定位，还是在复制模块清单和功能过程 |
| 工程质量 | 需要什么风险证据、何时验证、证据何时失效 | 与贡献和模板一致；不复制 package 命令图 |
| 修复边界 | 怎样选择局部修复、边界判断或执行单 | 重新判断不自动要求批准，不重复架构完整规则 |
| Quiet Pro | 跨页面视觉与交互必须保持什么 | 通用文字角色与具体控件映射分层，失败与无障碍契约保留 |
| 本地化 | 怎样安全修改消息、生成并验收语言 | 操作入口真实；不与发布正文或 schema 竞争 |
| 发布规范 | 什么构成发布、升级与资产承诺 | 保留权限和不可变性；当前版本和进度回到机器事实 |
| Web Activity | 客户端与接收端如何兼容 | 不丢字段、停止通知、匿名、有效期与失败语义 |
| Project 方法 | 如何维护私有事项和状态 | 方法留在文档，实时队列留在 Project，排序依据回到路线图 |

本表仅用于本轮审查，不复制到长期文档形成新路由来源。
