## 1. 从第一性原理定义目标

输入是会话事实、查询范围和展示规则，输出是概览及应用趋势。优化应减少得到同一结果所需的计算和分配，不能通过少算数据、改变时间边界或跳过分类规则换取速度。

必要工作是检查有效会话、裁剪范围、确定统计归属、将时长分配到相交的桶，再派生图表数据。调查应区分这些必要成本与重复解析、重复遍历、排序及临时对象成本。以 N 条会话、B 个时间桶、A 个应用分别改变规模，判断成本随哪个变量增长，而不是仅凭函数调用次数猜测瓶颈。

验收要求同时满足：完整业务结果不变，目标正式基准满足原预算，完整稳定性能套件通过。一次较快运行或一个阶段变快都不能代替完整验收。

### 已核实的实现事实

- [x] 年度组合基准先构建一个 `buildDataTrendAggregateContext`，再从同一上下文派生概览和应用趋势。当前已经共享聚合，不能预设“合并两次聚合”就是解法。
- [x] 输入为 365 天 × 120 条会话，共 43,800 条、8 个可执行程序；nowMs 使用本地时区的 2026-06-30 12:00。前后必须保持时区一致。
- [x] 正式年度组合采样 10 次，预算为 average ≤ 420ms、P95 ≤ 150ms、max ≤ 1,680ms。
- [x] 百分位取排序后 `ceil(n × p) - 1`，因此 10 个样本的 P95 等于这一轮最大样本。偶发停顿会触发此门槛，但不能据此删除慢样本。
- [x] 测量函数本身不额外预热，同脚本此前却已运行类似路径；正式复测要保持顺序，不能称为纯冷启动。
- [x] `perf:stable` 为每个基准启动独立进程、运行五轮，失败立即退出。后续未执行项不能记为通过。

依据：[正式基准](../../scripts/perf/data-read-model-benchmark.ts)、[测量工具](../../scripts/perf/benchmarkUtils.ts)、[稳定套件](../../scripts/perf/stable-benchmark-suite.ts)。本项测 Node 读模型计算，不包含数据库、IPC、React 或图表绘制耗时。
