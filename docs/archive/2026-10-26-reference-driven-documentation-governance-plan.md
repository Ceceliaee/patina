## 1. 从第一性原理确定治理目标

文档的价值在于帮助读者作出正确判断、完成具体任务，并让后续维护者能以合理成本保持这些信息可信。文件整齐、篇幅缩短、链接有效都是手段，不能单独证明治理完成。

本方案从五个必要条件推导治理动作：

| 必要条件 | 为什么需要 | 对文档治理的要求 | 可观察结果 |
| --- | --- | --- | --- |
| 找得到 | 读者不知道答案藏在哪个文件，也不应先读完整仓库 | 每个入口说明面向谁、解决什么问题，按任务连接到直接 owner | 从真实入口能找到目标说明，不依赖全文搜索碰运气 |
| 看得懂 | 新读者没有作者的背景知识 | 先交代用途和前提，再给操作或规则，最后展开实现细节 | 不熟悉仓库的开发者能解释下一步及其理由 |
| 用得对 | 正确命令也可能因缺少前提、例外或失败说明而被误用 | 保留触发、义务、失败、恢复、兼容和权限条件 | 成功路径可执行，危险或不适用路径可识别 |
| 信得过 | 文字会随代码、配置和决策变化而过期 | 每项事实有明确来源，区分现行规则、计划、历史和未验证结论 | 文档不以旧记录或另一份 prose 替代事实来源 |
| 维护得动 | 同一规则多处维护会产生矛盾，过度流程会拖慢开发 | 在唯一 owner 修改，入口用必要摘要和链接；按任务读取和验证 | 一项事实变化只需维护其 owner 及必要引用，无需全库联动 |

由此确定本轮交付：覆盖所有现行文档，完成参考方法到 Patina 的适配；按读者任务重组内容；收敛重复规则与不当层级；验证真实阅读路径。错字、死链和过时名词作为其中一部分处理。

### 2.1 采用、适配与不采用

| 参考做法 | Patina 的处理 | 原因与落点 |
| --- | --- | --- |
| 先确定读者、任务、主题和可容纳的细节 | 采用；作为本轮每份现行文档的审查顺序 | 先解决结构与职责，随后修改句子；结果落实到文档开头、标题和链接 |
| 每条事实有一个权威 owner | 采用；入口保留必要操作摘要，不复制完整政策 | 结合现有 AGENTS、长期文档、源码与配置归属落实 |
| 由浅入深，教程与参考有明确边界 | 适配为入门路径、任务指南、查询参考和原理说明；同文件可有清楚分区 | Patina 有混合贡献指南和协议资料，不强制每份文件二选一或新增目录 |
| 细节放到最近 owner，上层只解释关系 | 采用；跨领域保证仍由现有长期 owner 持有 | 代码可查的清单链接源码；必须面向使用者说明的行为不能仅用代码链接代替 |
| 现行说明与过程记录分离 | 采用现行 prose；继续使用 working/archive 管理执行与历史 | 现有数据兼容、迁移和恢复规则仍是有效契约，不能按“历史词”批量删除 |
| 固定 YAML、Summary、目录、折叠段和 Dev Note 模板 | 按真实检索需要适配；不统一强制套壳 | 长文可加任务导航；短文件保持直接；活动上下文留 working，避免长期正文积累草稿 |
| 双语物理行数、sidecar 与生成目录规范 | 保留 Patina 当前双语义务和语义一致性，不移植 DSH 的工具链 | README 配对和 CONTRIBUTING 中英文都需核对；无必要不扩大翻译范围 |

| 所有操作描述均重新执行 | 按变更与风险适配 | 新增或改变的操作应验证真实入口；未变输入的有效证据可沿用。发布、生产凭据和破坏性操作不能为证明 prose 而执行 |
| 每次非平凡变更新增 Agent Note、冻结所有归档 | 不照搬；遵循 Patina 的必要文档更新与归档规则 | 本轮不新增日常强制报告；历史错误和失效引用可修正，但保留原始证据状态 |
| 减少无关指令、重复阅读和无谓验证 | 用于检查入口触发与责任表达 | 不能因此取消必要验收、改变推送授权或降低数据和权限保护 |

### 3.3 受保护内容与条件工作

- 本轮默认保持现有产品、数据、协议、UI、发布和授权语义；改变其承诺需要相应决策，不能夹在文档简化里。
- 具体命令组成、字段清单、版本和配置默认值仍由机器 owner 持有；必要的使用说明、失败保证和稳定协议字段不能因“源码已有”而消失。
- 不修改业务实现，不重做测试整改，不引入自动选测或自动证据复用工具，不恢复已取消的 Mini 长静置测试。
- 检查器只在结构治理产生可复现且实际需要覆盖的检查缺口时调整；提出最小规则及正反例，不为方案建立通用审计平台。
- 可选本地指引只在与最终仓库规则冲突且实际使用时同步；缺失或无写权限不阻塞仓库交付，不能成为 CI 前提。
- 新增长期文档或拆分章节是可用手段，但须说明独立读者任务、owner 和链接维护方式；不能仅为降低字数把同一义务拆散。

## 4. 目标组织方式与事实归属

先建立内容职责，再决定是否移动文件。初始方案保留当前顶层十份长期 owner；需要更深操作说明时，优先整理由现有文件承载的独立章节或已有 examples。确有独立任务再按 G1 的处置记录新增下层文档，不能绕过现行顶层文档限制。

| 内容 | 权威位置 | 其他文件的处理 |
| --- | --- | --- |
| 跨任务授权、按任务读取、文档准入与生命周期 | 根 AGENTS | 专题入口链接适用规则，不重复完整常驻指令 |
| 产品方向、排序、工作项维护 | 分别为产品范围、路线优先级、Project 维护 | 互相链接各自问题，不复制私人队列 |
| 系统结构、跨层职责、数据与运行时保证 | 架构；细节由实际源码/配置 owner 支撑 | 贡献入口给导航，feature 细节不扩成全仓规则 |
| 质量、prose、验证路由 | 工程质量；命令图归 package scripts | CONTRIBUTING 和 PR 模板只保留所需摘要及信息采集 |
| 外部贡献准入、提交准备和审查流程 | CONTRIBUTING | AGENTS 给执行入口，PR 模板与 parser 保持一致 |
| 共享视觉与交互、消息、发布、协议 | 各自已有长期 owner | 跨主题只说本地需要的关系，不复制整套要求 |
| 某项操作的前提、步骤、成功和恢复 | 最近的任务指南或明确分区 | 原理和字段参考通过链接展开 |
| 计划、取舍过程、测量与事故时间线 | working / archive | 长期正文只吸收已确认且仍适用的结论 |

文档开头应让读者判断是否读对地方；长文提供按任务的导航或目录，短文无需统一加模板。可执行操作按前提到结果排列；查询参考采用稳定主题和术语；原理说明保留足够因果，不夹进每一步操作。

  - 区分必要摘要、同一规则重复、不同规则使用相近词汇；确认后者不会被误合并。
  - 完成条件：每项重复或冲突有真实 owner、保留位置和引用方式；不凭文本相似度自动删句。
- [x] **G1-03：确定逐文件处置和目标目录。**
  - 在本文执行记录中列出保留、重排、改写、合并、分拆或迁移的决定，以及对应读者收益。

- [x] **G1-04：记录阅读路径基线。**
  - 按第 6 节场景，从真实入口记录需要打开的文件、跳转次数、无关章节及找不到的答案。
  - 记录篇幅和最大混合章节辅助定位，不预设统一字数或缩短比例。
  - 完成条件：治理后可以用相同问题比较可发现性与完整性，不能只比较总行数。

### G2：治理根入口、用户入口与贡献流程

- [x] **G2-01：整理根 AGENTS。**

### G3：治理全部长期 owner

每项都按“读者问题 → 章节职责 → 内容迁移/重写 → 事实与保留义务 → 阅读验证”执行。以下是具体治理方向，不能只运行链接检查后勾选。

- [x] **G3-01：产品原则与范围。**
  - 整理用户价值、长期原则、当前支持范围、非目标和新功能准入，检查重复解释是否可以合并到一个明确判断。
  - 把排序细节指向路线优先级；保留个人、本地优先、Windows、记录可信、数据控制及 Tools 边界。
  - 验收：一个符合范围和一个越界需求都能找到明确判断依据，不能以短文案掩盖产品范围变化。
- [x] **G3-02：路线与优先级。**
  - 将排序原则、风险高低、插队条件和具体评估方法组织为可执行判断；合并重复的价值陈述。
  - 具体任务与私有排序继续留在执行记录和 Project；结构、兼容、风险定义链接其 owner。
  - 验收：数据安全修复、高频体验优化、扩展功能三个候选能按现行原则排序，文档不复制实时队列。
- [x] **G3-03：架构。**
  - 先说明系统组成、写入与读取的数据流和跨进程关系，再展开前端/Rust owner、关键安全及恢复保证和实现落点。
  - 检查入口说明、禁止事项、重点防守区和 owner 列表的重叠；字段/API 枚举链接源码，必要跨层保证保留可读说明。
  - 验收：读者能定位一项前端改动、一项 SQLite/恢复改动和一项窗口/IPC 改动；不丢失迁移、备份、并发、权限或失败保证。
- [x] **G3-04：工程质量。**
  - 按质量目标、改动风险、编辑反馈、模块验证、稳定候选验收、专项与发布组织验证内容，检查长段落是否混入多个独立判断。
  - 现有测试运行器的内部细节和命令组合回到机器 owner；保留每类验证保护什么、何时需要、什么结果不能替代它。
  - 验收：普通文档、前端展示、共享组件、Rust/SQLite、权限/runtime、发布均能找到路由；不减少完整验收，不恢复逐次全测。
- [x] **G3-05：Quiet Pro。**
  - 分开视觉原则、token 与样式 owner、组件契约、交互/可访问性和审查责任，消除重复的同义约束。
  - feature 局部布局与具体用例链接最近实现；共享状态、键盘、焦点、危险操作和截图/测试职责仍明确。
  - 验收：普通按钮、复合弹层、feature 私有表面各能找到所需规则；不能因精简弱化既有交互状态。
- [x] **G3-06：本地化。**
  - 为修改已有文案、新增语言、交接翻译包三类任务建立可直接进入的操作路径，再连接消息模型和 runtime 参考。
  - 将源资源、生成物、复核记录和消费代码分工写清，保留参数/复数、不可信 XLSX、失败回退和激活一致性。
  - 验收：读者不会直接修改 generated 文件，也不会把工具通过当作语义审核；例子和命令继续受当前实现支持。
- [x] **G3-07：版本与发布。**
  - 将版本/兼容政策、格式与资产参考、发布准备/执行步骤、失败和签收责任分区；消除重复的相同前置条件。
  - 保留已发布资产不可变、签名、校验、双架构、updater、旧数据支持和跨仓协议责任；详细机器字段指向真实 owner。
  - 验收：普通 changelog 修改与正式发布能走不同路径；本轮只核对文档，不为验证示例创建 tag、上传资产或发布。
- [x] **G3-08：问题修复边界。**
  - 按问题定位、选择模式、升级条件和完成判断整理；检查“重新判断”和“需要新授权”是否被混写。
  - 保留真实不确定性、不可逆动作和权限的停止条件；已授权且独立的工作应可继续。
  - 验收：简单文案、小范围实现修复、跨 owner 数据迁移能够选择合适模式，不为每次小改创建完整执行单。
- [x] **G3-09：Project 维护。**
  - 以一次读取、准入、排序、状态维护和完成清理为操作路径，将字段语义放入可查参考区。
  - 现行规则不依赖具体插件，不保存 live state，不将代码任务完成等同于 Project/Issue 状态变化。
  - 验收：没有实时访问时能识别证据限制；仅治理静态指南不读取或改写私有队列，有真实维护请求时再按权限执行。
- [x] **G3-10：Web Activity 协议。**
  - 按连接/请求、活动资格、时间边界、隐私控制、停止通知、拒绝和响应组织查询顺序，统一字段术语和交叉引用。
  - 外部消费者必需的字段、单位、允许值和失败语义完整保留；不把完整协议全部退回源码让接入者自行推导。
  - 验收：正常活动、过期输入、匿名/标题禁用、停止通知和不合法请求均有明确说明；若发现真实语义差异，作为协议问题单独决策，不顺手改变两仓契约。

## 6. 读者场景与验收问题

这些场景同时用于治理前基线与治理后比较。每行需记录实际路径、答案所在 owner、是否存在无关阅读及遗漏；路径长短只是诊断信息，不设统一跳转上限。

| 场景 | 起点与必须找到的答案 | 反向检查 |
| --- | --- | --- |
| U1：首次了解和获取应用 | README → 产品用途、适用平台、下载与支持入口 | 不先要求读贡献规范或架构；隐私/支持限制未丢失 |
| U2：首次本地开发 | README/CONTRIBUTING → 环境来源、启动步骤、成功信号、下一步 | 不能用发布/生产配置作为开发前置，也不能省略必要工具链 |
| U3：普通文案修正 | AGENTS/CONTRIBUTING → 文档 owner 与适用检查 | 不触发全库阅读、应用构建或原生长测 |
| U4：新增普通前端功能 | CONTRIBUTING → 产品准入、实现 owner、UI/消息、分阶段验证 | 定向反馈不冒充稳定候选完整验收 |
| U5：SQLite 恢复或权限改动 | 架构/工程质量 → 受保护保证、失败路径、适用完整与 runtime 证据 | 不能因是“小 diff”跳过数据/权限风险 |
| U6：设计复合弹层 | Quiet Pro → 状态、焦点、键盘、关闭和测试责任 | 不能只找到视觉 token，找不到交互契约 |
| U7：修改文案或增加语言 | 本地化 → 源文件、生成、审核、失败与验证 | 不手改生成物，不把自动检查当母语审核 |
| U8：准备正式发布 | 发布规范 → 版本一致、资产、签名、双架构、授权和签收 | 文档整理不能实际创建 tag 或假定未运行发布检查通过 |
| U9：实现或排障协议接入 | Web Activity/远程状态桥 → 前提、字段、单位、鉴权、时序、拒绝和恢复 | 示例成功不覆盖全部协议，匿名/停止/失败路径仍明确 |
| U10：维护私有队列 | Project 指南 → 实时读取、字段、排序与状态授权 | 本地计划或任务完成不能替代实时状态或授权 |
| U11：引用历史调查 | 当前 owner → 必要的历史证据入口 | 已取消、未验证、已接受风险与测试通过不混同 |
| U12：将来变更一条共同规则 | owning 文档 → 摘要与实际消费者 | 不出现两份完整政策需同时人工维护；也不删除必要用户说明 |

验收说明读者能否完成任务，不使用未经测量的“上下文减少百分比”或“开发提速比例”。复杂安全/发布任务需要更多阅读时保留这些内容，并说明其与决策的关系。

## 7. 验证与证据边界

| 本轮实际改动 | 适用验证 | 不应由此声称 |
| --- | --- | --- |

| 新增或改变操作示例 | 真实本地入口及相应失败/限制检查；不可执行部分具名记录 | 只读源码等同于执行通过，或本地成功等同于远端部署 |
| PR 模板或解析规则 | 真实 parser/CLI 的合法与拒绝案例，保持现有 intake 必需字段 | 文档扩展名可以豁免机器语义变化 |
| 文档 checker 实现 | 精确正反例、真实 CLI、类型/lint，并按工程质量选实际代码门槛 | 自测通过就可取消原有默认门槛 |

验证选择由[工程质量第 5 节](../engineering-quality.md#5-默认验证门槛)持有，实际命令定义由 [package.json](../../package.json)持有。本方案不把 DSH 的 `test:docs`、`doc-sync`、双语 sidecar 或覆盖率要求直接当作 Patina 命令。

操作事实核验遵循已授权范围。只影响文档的重排不触发产品完整构建、browser、Rust 或原生长测；有实际 checker/模板/命令行为变化时，按新增风险升级，不以“文档治理”为理由规避必要验证。无需为核验远端操作而索取或写入生产凭据。
