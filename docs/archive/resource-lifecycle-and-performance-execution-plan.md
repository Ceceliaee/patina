## 1. 目标与第一性原理

Patina 的价值是准确、低打扰地记录活动，并在用户需要时立即提供可操作的内容。当前切页、筛选、日期切换和详情操作基本没有可感知的卡顿或加载等待。优化必须保留这一体验，同时减少无用工作和没有释放责任的资源。

### 1.1 资源为什么存在

CPU 用于完成工作；内存用于保存正在使用或值得复用的数据；线程用于执行或等待任务；句柄用于持有操作系统对象。资源数量低并不自动代表实现更好。必要缓存能避免重复查询和重建，适量后台任务能保证追踪与提醒正确。

对每项资源，依次回答：

1. 它为哪个用户行为或必要后台能力服务？
2. 谁创建它，谁持有它，谁负责结束其生命周期？
3. 什么事件使它失去用途？结束、取消、失败、销毁路径是否都处理这个事件？
4. 为保留它付出的成本，是否换来了可验证的响应速度或可靠性？
5. 如果持续创建，是否有数量、字节、并发或时间边界？边界之外如何处理？

只有回答完这些问题，才能决定保留、复用、减少创建或释放。不得单凭任务管理器数字删除缓存或压缩工作集。

### 1.2 从原理推导实施顺序

| 原理 | 推导出的行动 | 验收事实 |
| --- | --- | --- |
| 不再服务任何用途的资源不应继续持有 | 先排查泄漏和失去消费者的任务 | 重复操作后资源收敛，失败和取消路径也释放 |
| 相同工作没有必要重复执行 | 再检查重复查询、订阅和计算 | 请求或计算次数下降，结果新鲜度不退化 |
| 缓存的价值是用空间换取响应速度 | 保留现有有效缓存、预热和页面复用 | 暖切页与常用操作继续无感 |
| 销毁窗口意味着其专属消费者消失 | 核查窗口与本体之间的生命周期边界 | 窗口专属资源释放，后台追踪继续正确 |
| 操作成本会在不同阶段转移 | 同时测前台、后台和重建 | 后台下降不以切页或重新打开变慢为代价 |
| 短期稳定不能证明长期无泄漏 | 做重复循环与长时间观察 | 区分初始化增长、缓存平台期和持续增长 |

## 3. 范围、授权与非目标

### 3.1 纳入范围

- 前台 Rust 本体和能够确认归属的 WebView2 进程。
- 后台本体、主窗口隐藏阶段、WebView 销毁后阶段。
- 主窗口与挂件各自的资源，以及仍在使用 WebView 时的共享进程归属。
- 缓存、事件订阅、定时器、异步任务、线程、数据库连接、文件、socket、Win32/GDI/USER 对象。
- 资源测量、根因定位、局部修复、回归验证与回退。

### 3.2 默认排除

- 用缩小有效缓存、取消预加载、每次切页卸载重建来降低内存。
- 改变后台优化默认值、销毁等待策略或增加更激进的 WebView 回收。
- 强制工作集修剪、按资源数字强杀 WebView2、终止其他应用进程。
- 新建通用缓存框架、第二套资源管理层或为本专项做全仓库重构。
- 无具体证据的数据库迁移、协议变化、计时策略调整和新 UI。
- 预先承诺 CPU、内存、线程或句柄降低比例。

| 场景 | 操作步骤 | 初始规模 | 重点证据 |

| 详情 | 反复打开关闭应用及网页详情，固定展开内容 | 每类 20 轮 | 订阅、图片、DOM、缓存与请求释放 |
| 后台隐藏 | 隐藏主窗口，保持原有设置，覆盖销毁前阶段 | 完整覆盖实际等待窗口 | 隐藏页面是否继续做无用工作 |
| 后台销毁 | 等待可信生命周期事实确认销毁，再继续观察 | 销毁后 10 分钟 | 残留进程、本体引用、内存与句柄平台 |

### 12.7 新发现：WeType 相关目录句柄残留

第二组每轮自然销毁后，主进程句柄最低值依次为 617、625、635、641、651、657、667、673、683、689。同期 GDI 均为 25，线程最低值主要为 33，私有提交有涨有跌，不能用内存回落掩盖句柄趋势。

- File 与 Event 类型随循环增长，数据库文件句柄保持 1 个。
- 脱敏后的重复目录指向 `%USERPROFILE%\AppData\LocalLow\Tencent\WeType` 及其 `crash` 子目录；第二组第 9 轮销毁后分别保留 20 与 19 个目录句柄。
