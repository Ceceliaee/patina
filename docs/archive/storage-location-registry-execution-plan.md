## 1. 目标与范围

将 Patina 的本机存储位置配置迁入当前 Windows 用户的注册表。已有用户升级时，自动转存旧定位文件中的设置，成功后清理旧定位文件。用户的数据库和缓存不因配置转存而搬动，以后仍可反复更改目录或恢复默认位置。

两个自定义根都已离开默认位置、迁移完成且没有操作进行时，删除原 `%APPDATA%\Patina` 和 `%LOCALAPPDATA%\Patina` 目录，不应使路径回退。这个承诺不适用于删除仍在使用的默认数据、缓存或安装目录；也不表示所有 Patina 临时文件永远不会再次出现在 AppData。

本方案来自已确认的产品目标与代码调查，不保存 Project 的实时内容、字段或排序。后续执行前按[Project 维护规范](../github-project-maintenance.md)读取实时队列；文档进度不代表远端状态。

### 受保护边界

- 数据库内容、计时语义、备份格式及已有恢复流程保持原契约。
- 本机路径不随跨电脑备份恢复而覆盖目标电脑的路径配置。
- 保留现有目录预览、安全写探针、数据库 checkpoint、staging、重启、路径身份比较与清理保护。
- 设置页面继续使用现有目录操作入口；失败提示遵循[Quiet Pro](../quiet-pro-component-guidelines.md)和[本地化契约](../localization.md)。
- 不增加便携版、全盘找库、通用配置框架或永久双写。缓存清理范围不在本项修改范围内。
- 本文件不授权代码实施、提交、推送、Issue/Project 写入或发布；这些动作遵循[仓库授权规则](../../AGENTS.md)。

## 2. 第一性原理与设计约束

### 2.1 启动定位必须先于数据读取

程序需要先知道数据库位置，才能打开数据库。因此，数据库不能成为自身位置的唯一记录处。路径配置必须有一个与自定义目录无关、启动时可确定的入口。

采用当前用户注册表作为入口。只存储启动和存储维护所需的少量控制状态；活动记录和普通业务设置仍由现有 SQLite owner 持有。微软将当前用户注册表列为适合少量用户配置的常规位置，见[Registry Functions](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-functions)。

### 2.2 配置转存与数据搬迁是两种操作

| 操作 | 实际改变 | 成功证据 |
| --- | --- | --- |
| 首次升级配置转存 | JSON 中的路径转为注册表状态 | 转存前后解析到同一数据库和 WebView 根 |
| 用户更改数据目录 | 数据搬到目标位置并提交新路径 | 新数据校验成功、配置提交成功、重启读取新库 |
| 用户更改缓存目录 | 按现有规则迁移必要 WebView 状态并切换根 | 页面状态保留、两个窗口使用同一目标根 |
| 恢复默认目录 | 执行现有搬迁流程后将对应位置设为默认 | 数据仍在、默认位置生效、另一位置不改变 |

“一次性”仅指每个用户/profile 的旧配置转换成功一次，不限制以后更改目录的次数。进程中断后重试同一次转换必须安全。

### 2.3 路径必须有唯一权威来源

新状态有效时，只用新状态。旧文件存在也不能参与优先级竞争。新状态损坏、权限拒绝或目标不可用，均不能解释成“没有设置”，更不能悄悄启用默认空库。

新状态与旧文件都不存在时，系统无法区分“首次安装”和“用户手动抹掉了全部定位信息”。不得声称能自动找回未知路径。此时只能采用首次安装规则，并在恢复指导中说明如何保全已有数据。

### 2.4 删除只能发生在新的可恢复状态成立之后

新配置提交、校验和所需持久化边界完成前，不删除唯一有效旧配置。数据库搬迁中，目标未验证或配置未提交前，不清理源数据。注册表提交和文件系统搬迁不是一个天然事务，必须用现有操作记录及明确提交点跨越二者。

### 2.5 多用户、profile 与升级必须稳定

注册表路径不包含应用版本或安装路径，普通更新不能改变入口。production、local、dev 和测试分别隔离。不同 Windows 用户使用各自的 HKCU，遵循[用户数据隔离建议](https://learn.microsoft.com/en-us/windows/win32/termserv/storing-user-specific-information)。

## 4. 拟采用的状态契约

### 4.1 注册表位置与记录

实现使用 `HKCU\Software\Patina\Storage\<profile>`，以单个 `State` 值保存有界的序列化记录。实现使用 `REG_BINARY`、64 位注册表视图及 64 KiB 上限；候选安装/updater 的实际验收仍待完成。

记录至少表达：格式版本、profile、数据位置、缓存位置、旧配置导入是否完成、旧文件清理是否待重试；按需要承载现有 pending 操作及维护结果。数据和缓存各自明确表示 `default` 或 `custom`，自定义值为绝对路径。

- 默认模式也保留已初始化记录，不能用删除整个记录表示“恢复默认”，否则旧文件可能被重新导入。
- 两个路径必须作为一个逻辑快照提交，避免先写数据路径、再写缓存路径留下混合状态。
- 不把序列化格式版本放进源码模块名，也不把普通设置迁入该记录。
- 采用现有 Windows 依赖的最小访问权限；读取不创建键，写入只操作 Patina 专属键。
- 单值写入不等于已证明跨文件事务或断电耐久性。阶段 B 必须核实 API 保证、刷新策略和失败读回行为后，才能依赖其提交语义。

### 4.2 启动决策

| 观测状态 | 行为 |
| --- | --- |
| 新记录有效 | 使用新记录；仅重试已登记的旧文件清理，不重新导入路径 |
| 新记录存在但格式未知、损坏或不可读 | 阻止依赖路径的启动，保留原状态并提示；不回读旧路径 |
| 新记录不存在，旧配置有效 | 组装完整候选、校验、提交并读回；成功后转入新记录 |
| 新记录不存在，旧配置损坏或权限拒绝 | 阻止转换，保留旧文件；明确报告原因 |
| 新记录和旧配置均不存在 | 初始化默认模式，使用现有首次安装行为 |
| 自定义数据库缺失、磁盘离线或无权限 | 保留所选路径，阻止正常追踪启动；不创建替代数据库 |
| 自定义缓存根不可访问 | 保留设置并报告；不静默改用默认根。可重建缓存与磁盘不可访问要分开处理 |

基线中的 `resolve_storage_paths` 会在部分配置错误时使用默认根，自定义库缺失时也可能采用已有默认库。本项需要消除这些与唯一来源原则冲突的路径，并验证默认位置存在另一份真实数据库时仍不会串库。

### 4.3 启动顺序

建议顺序：确认 profile 和实例互斥 → 读取或导入控制状态 → 处理未完成存储操作 → 验证最终有效根 → 初始化 SQLite → 创建主窗口/挂件并启动追踪。

配置导入不能机械要求源库一直存在：如果旧 pending 表明数据已进入 staging 或目标，必须先识别现有迁移阶段，再由迁移 owner 恢复。没有 pending 证据时，不能把“源不存在、目标存在”直接判为成功。

## 9. 实施与审查记录（2026-10-02）

### 已落地结果

- 注册表 `State` 是两个位置、pending 阶段和维护结果的唯一运行时来源；显式默认状态保留，不删除初始化记录。旧 writer 和原 `storage_anchor.rs` 已删除。
- 首次导入保存、刷新并读回快照后，仅清理四类旧控制文件及其 `.previous`/`.tmp`；清理中断后继续使用新快照，受占用旧文件保留诊断并可重试。
- pending 使用 `preparing-target` 和 `locations-committed` 区分提交前后。提交前保留源，提交后重启不再次搬迁或删除；无法判定的旧中断现场停止启动并保留证据。
- 自定义库缺失时，即使默认位置存在另一份库也返回错误。启动原生提示通过消息 schema 和四个生产语言资源生成。
- 对历史本地 tag 的源码核对覆盖 v1.8.0～v1.9.9。v1.8.0～v1.8.2 的 pending v1 和独立缓存清理标记由窄导入器转换；v1.8.3～v1.9.9 使用 pending v2。此处是源码格式证据，不是这些版本的逐一安装验收。
