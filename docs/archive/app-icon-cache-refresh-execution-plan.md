# 应用图标缓存低频按需刷新执行方案

> 状态：实施完成，74 项执行步骤已勾选，验收记录已归档。
> 创建日期：2026-09-16
> 执行 owner：本次任务实现者；涉及范围变化时由维护者决定。

## 1. 目标与第一性原理

图标是可重新获取的展示数据，追踪会话才是必须及时、可靠保存的事实。图标新鲜度不能以阻塞计时、频繁访问 Windows 图标接口或启动时扫描全部应用为代价。

判断图标是否真的变化，最终仍需读取图标。应用版本、exe 修改时间都只是间接信号，不能证明图标内容变化。因此采用有界的新鲜度取舍：成功获取或核验后复用 30 天；到期后遇到该应用的新会话，再后台核验一次。没有使用的应用不产生刷新工作。

“30 天”指连续的 `30 × 24` 小时，不是自然月，也不是每天执行一次检查。是否到期由既有图标缓存查询顺带判断。自动刷新允许延迟：到期后长期未使用的应用仍显示旧图标；连续运行而没有新会话的应用也可能等待下一次会话建立。本文不承诺图标变化后严格在 30 天内更新。

成本分为四类，分别约束：

| 成本 | 触发条件 | 目标 |
| --- | --- | --- |
| 缓存元数据读取 | 既有会话建立后的图标任务 | 用原查询带出时间，不新增每日任务或逐采样查询 |
| Windows 图标提取 | 缓存缺失，或到期且退避已结束 | 后台执行，沿用并发上限和按应用去重 |
| SQLite 写入 | 成功核验 | 相同图标只更新时间；不同图标替换内容与时间 |
| 界面更新与取色 | 图标内容确实变化 | 定向失效并重新读取，保留用户自定义颜色 |

### 受保护边界

- 不改变应用归属、会话切分、计时、分类映射、历史记录或用户自定义颜色。
- 不按应用升级次数刷新，不加入版本检测、文件监控、网络下载、每日调度或启动全库重建。
- 不新增手动刷新界面，不改网页 favicon 刷新策略，不重做取色算法。
- 不将图标缓存从 exe 身份改成包或路径身份；同名 exe 的应用区分是另一项身份问题，不能靠刷新周期解决。
- 实现、验证与归档已由维护者授权；本任务不包含提交、推送、发布或外部事项状态修改。

长期约束以 [架构规范](../architecture.md)、[稳定期修复边界](../issue-fix-boundary-guardrails.md)、[工程质量](../engineering-quality.md) 和 [版本与发布政策](../versioning-and-release-policy.md) 为准。本文不保存外部开发队列的正文、字段或顺序。

## 2. 已核对的代码链路

以下为方案编写时的源码事实，执行前需要确认没有变化。

| 环节 | 当前 owner | 与本项有关的事实 |
| --- | --- | --- |
| 触发 | `src-tauri/src/engine/tracking/active_session.rs` | 会话写入成功后启动异步图标任务；不是每次采样都提取 |
| 调度策略 | `src-tauri/src/engine/tracking/metadata.rs` | 已有按 exe 的 in-flight guard、并发限制及失败负缓存；缓存存在就返回 |
| 数据端口 | `src-tauri/src/engine/tracking/ports.rs` | `is_icon_cached` 只返回存在性，不能判断到期 |
| 数据实现 | `src-tauri/src/data/tracking_runtime.rs` | 每次操作取得当前 pool，避免长期持有已被恢复流程关闭的 pool |
| 缓存读写 | `src-tauri/src/data/repositories/icon_cache.rs` | 已保存 `exe_name`、`icon_base64` 和 `last_updated`；查询使用大小写不敏感匹配 |
| schema | `src-tauri/src/data/schema.rs` | `last_updated` 允许 NULL，不能假设所有已安装数据都有合法时间 |
| 平台提取 | `src-tauri/src/platform/windows/app_metadata.rs`、`icon.rs` | 负责 Windows 图标来源选择与资源释放 |
| 主窗口图标缓存 | `src/platform/persistence/appIconRuntimeCache.ts` | 已有图标不会重新读取；只改数据库不能保证可见内容更新 |
| 页面状态 | `src/shared/hooks/useRequestedAppIcons.ts` | 合并页面基础图标和已加载图标；旧快照可能覆盖更新的基础值 |
| 自动配色 | `src/shared/hooks/useIconThemeColors.ts`、`src/platform/persistence/iconThemeColorStore.ts` | 按图标内容来源缓存颜色；必须让新图标进入这条链路 |
| Widget | `src/app/widget/widgetIconService.ts` | 独立缓存图标与 pending promise，不能假定主窗口缓存失效会自动影响它 |

实现模式采用跨 owner 执行单：策略仍归 tracking metadata，读写归 repository，平台提取归 Windows 模块，界面缓存失效归前端现有缓存 owner。不要在各个页面分别实现 30 天策略。

## 3. 状态契约与推荐决策

### 3.1 核验时间与兼容

推荐先复用 `last_updated` 表达“最近一次成功取得或确认当前缓存图标的时间”。已有时间是此前成功写入图标的时间，可自然作为周期起点。实施前必须审查所有读取方，确认没有调用方将其解释为“内容最后变化时间”并依赖这一更窄语义。

如果发现冲突，再在 schema owner 增加独立核验字段，并补迁移及恢复测试；不要为了方便同时保留两套未经说明的时间策略。默认方案不新增列、不改变备份格式、不扩展旧备份 writer。

时间异常按以下目标收口：NULL、零或负值按待核验处理；未来时间先保留旧图标，通过一次按需成功核验归一化，避免永久不刷新。所有时间差计算使用安全算术。失败不能把成功核验时间推进 30 天。

### 3.2 状态转移

| 输入状态 | 本次动作 | 成功后的持久化结果 | 通知界面 |
| --- | --- | --- | --- |
| 无缓存 | 沿用首次提取 | 写入图标与核验时间 | 让已有缺失图标消费者获取结果 |
| 缓存未满 30 天 | 返回 | 不写入 | 否 |
| 到期但任务已在执行 | 返回 | 由正在执行的任务负责 | 不重复 |
| 到期但仍在失败退避 | 返回 | 不写入 | 否 |
| 到期但没有并发额度 | 放弃本次，等待后续会话机会 | 不伪造成功或失败时间 | 否 |
| 到期，提取成功且内容相同 | 确认当前图标 | 只更新核验时间 | 否 |
| 到期，提取成功且内容不同 | 替换图标 | 原子更新内容与核验时间 | 提交成功后定向通知 |
| 提取失败、无有效图标或数据库写入失败 | 保留旧结果并退避 | 不覆盖旧图标、不推进成功时间 | 否 |
| 提取期间发生恢复、清理或缓存内容被替换 | 丢弃失效结果 | 不向新数据状态回写旧任务结果 | 否 |

推荐旧图标刷新失败使用至少一小时的内存退避，和首次缺失图标的短重试需求分开判断；保留已有有界负缓存机制，不另建无限增长的任务队列。进程重启可以重新尝试一次失败核验，成功核验周期必须跨重启保留。

“内容相同”首先比较标准化后的图标载荷，不比较生成时间或包版本。如果现有编码过程对相同像素不能稳定产生相同载荷，在到期路径比较解码后的尺寸与 RGBA 像素；不因 PNG 编码元数据差异触发界面更新，也不在未到期路径解码图片。

### 最终实现决策

- 生产修改落在 tracking metadata/port、data adapter/repository、恢复与清理入口、前端缓存及既有图标 hooks；Windows 图标选择优先级不变。新增生命周期 helper 只管理当前 pool 的刷新快照与维护互斥，没有常驻任务。
- 未到期查询继续使用原有覆盖索引进行大小写不敏感的名称匹配，再按主键取一条时间字段。没有新增读取图标载荷的全表扫描，也没有增加索引；不能将原有的名称索引扫描描述为完全不存在扫描。
- 图标生成仍由 Windows owner 将位图统一编码为 PNG。比较时归一化 data URI 前缀；本次不增加逐像素解码层。无图、资源提取失败沿用 `None`，不写入空图标。窗口消息超时、Shell 工作线程和资源释放沿用现有平台实现。
- 真实 SQLite 集成测试由 `data/tracking_runtime/icon_refresh_tests.rs` 注册，调用生产策略的可注入接缝；纯时间边界仍在 metadata 单元测试内。测试代码不通过 engine 路径引入 data 依赖。
- 失败退避保留 512 项上限；同 exe 去重和提取并发上限 2 沿用已有约束。旧图刷新失败至少退避一小时；新缺失 packaged 图标继续使用原有短重试。
- 自定义颜色仍由现有展示模型优先决定；只更新时间不发事件，新图内容才进入现有按内容缓存的取色链路。

| --- | ---: | ---: | ---: | ---: | ---: |

### 验收范围与处置

- 本次采用同机、同数据集、交替 SQL/生产策略微测量作为前后基线，并以既有页面与启动性能矩阵保护整体回归；不执行整机旧版本/新版本 GUI A/B，避免把环境和 UI 测量差异当作查询成本。该额外整机实验不列为本次实现的待办。
