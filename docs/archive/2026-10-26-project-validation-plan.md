owner 指事实或行为的权威归属；消费者指依赖它的模块、页面或进程；fixture 是测试准备的隔离数据与环境；candidate 是准备交付的确定候选；prepared 是已构建并经过输入/产物校验的可复用测试产物。

## 1. 目标与完成边界

首轮覆盖前端、Rust、数据库、权限、原生窗口以及静态、性能和交付相关路径。每类常见改动都能找到编辑反馈、模块验证、候选完整验收及风险升级条件。后续新增功能沿用所属层的入口、fixture 和阶段规则，只补独有失败模式和特殊前提。

日常修改不因每次保存、代码行数或文件数单独进入完整回归。开发时先检查当前行为，行为单元完成后覆盖模块及实际消费者，稳定候选集中完成适用完整门槛；高风险或组合影响按实际需要提前验证。失败修复后重验受影响范围，涉及共享状态、顺序或聚合编排时重跑对应组合。

首轮成功须同时具备全项目可用路径、明确升级边界及完整保护；Mini 只可作为原生领域的一个代表。全项目覆盖不等于重写全部测试：已有入口满足要求就复用，缺少有效短反馈的层补最小能力。必须真实等待的风险仍按原条件验收，并与能尽早发现问题的低层/短功能反馈分别报告。

维护者与 Agent 根据改动选择现有命令，继续使用 prepared 校验并人工核实已有检查结果是否有效。首轮交付是各层可用的验证路径和清楚的执行分工，新增功能沿用这些能力。

## 3. 首轮范围与受保护约束

2026-10-26 维护者授权执行本测试方案至完成、勾选归档，随后开展对抗式审查。独立文档治理方案不在本次实施范围；提交、推送、远端 dispatch、Issue/Project 与发布仍需各自授权。

实施中维护者明确取消 Mini 的 10 分钟静置测试及其代码，理由是固定等待成本过高；该项从本轮验收和后续运行中移除。保留普通路径已有的 1 秒停止轮询检查；短观察不再承担长期静置结论。下文的保护要求以最新决定为准，历史运行记录保持原样。

随后维护者要求将讨论中的循环次数减半：完整 Mini 展开 100→50 次、重开 20→10 次，主窗口每种 GC 模式 30→15 轮，采样点相应为第 3/8/15 轮。分位数按实际样本长度计算；已有短反馈 3/2 次、真实时间边界、主窗口 60 秒静置和各项资源/延迟阈值不在此次次数调整范围。新版有界工作负载不宣称与原样本数具有相同统计精度。

获批后的首轮包含 T0～T9：先明确本地、CI 与发布职责及规则切换条件，再逐层核实实际入口、测试/coverage 范围、隐式构建与成本，补齐必要独立运行、严格过滤、故障 fixture 或短原生反馈，落实新增功能继承规则，核对完整验收并比较效果。通用验证规则归工程质量；命令组合归 package；具体场景与执行能力归测试 owner；发布专属义务仍归发布政策。只修实际缺口，不把第 4 节整段迁入长期规范。

文档治理方案处理 AGENTS 生命周期及活动计划状态；本文处理工程质量第 5 节的验证规则与对应 CONTRIBUTING 摘要。相关 owner 清楚后即可推进各层工作；实际冲突只阻塞对应段落，不等待另一份方案整体收口。

必须保留：

- [个人、本地优先 Windows 范围](../product-principles-and-scope.md)、tracking 正确性、原数据保护与失败恢复。已发布数据库、备份、协议和升级边界继续受支持，UI 退役不取消迁移保护。
- main/Mini caller guard、ACL/plugin 拒绝、跨 profile 隔离、敏感凭据边界和真实落盘证据；mock 成功不能冒充真实边界通过。
- 候选 `check` / `check:full`、适用完整 runtime、风险追加、CI 与发布的现有保护集合。双架构、版本、签名、摘要与独立资产校验不削弱；x64、消息注入或开发 profile 各有证明边界。
- 未被维护者明确取消或调整的断言、样本数、观察时长和阈值。不得擅自删断言、skip、无理由 ignore、放宽预算或自动重试到绿制造提速；保留原始失败、取消与未执行项。
- 独立 fixture、受控环境、取消和安全清理；不停止用户应用。资源/基准串行、桌面输入互斥，避免同机构建污染测量。
- 可选本地指引不成为仓库/CI 依赖，不写入长期技能清单、不修改记忆；公共信息按第 4.6 节继承。

CI 首轮核对执行职责、同候选证据、新增入口可达性和完整集合；确有缺口时只补必要接线，不做 job 重组、跨 job 缓存或按路径跳过等优化。减少本地与 CI 的重复执行须满足第 4.2.1 节，不删除完整保护或扩大首轮基础设施范围。

未来实施授权不自动授予 push、Issue/Project、tag、Release、正式安装、新长测或扩大数据操作。缺少条件只暂停对应动作，继续独立已授权工作；共享工作树回退只撤本任务增量。常规入口/fixture 组织和已授权规则修补无需逐项请示。

## 4. 分阶段验证设计

### 4.1 全项目分阶段验证矩阵

下表定义首轮要贯通的路径，不是新的测试文件清单。实际入口、参数与执行图仍由 package、测试/场景和 Cargo module tree 持有。各层先核实已有命令；不足处按 T3～T5 补最小能力。早期反馈只证明其命中的行为，右列的候选保护保持有效；本地与 CI 的执行职责及生效条件见第 4.2.1 节。

| 层级/领域 | 编辑时的最小有效反馈 | 行为单元完成后的模块验证 | 候选与专项保护 |
| --- | --- | --- | --- |
| TS model/unit/contract | 命中 owner 的状态、不变量、乱序及时间边界测试，配合适用类型/静态检查 | 实际消费者及跨模块契约；共享模型扩大组合 | 候选保留默认快速测试、coverage/mutation 与构建等现行集合 |
| 静态/结构、文档与 i18n | 命中的真实 checker；文档按内容风险核对，消息资源按既有生成/审阅流程 | 检查器/allowlist 正反例；消息 key/参数与命中界面消费者 | 默认静态门槛不删项；纯文档及翻译例外沿用现行 owner |
| SSR 与 browser | 相关渲染、DOM、键盘焦点和异步交互场景；过滤须非空且可解释 | 共享 primitive/theme 的消费者组合，失败恢复与交互状态 | 保留默认 SSR/browser 并集；stub IPC 不证明原生行为 |
| Rust 领域及集成 | 独立质量 target 下的真实模块/测试过滤、边界反例及适用 fmt/check | 公共类型、tracking、并发、helper 与直接/间接消费者 | 候选保留 `check:full` 的保护集合，包括 fmt/check/test/clippy、依赖及适用原生证据 |
| SQLite、迁移、备份恢复 | 隔离 fixture 中的事务、损坏输入、回滚、幂等、ID 重映射与旧格式反例 | 相关真实 data-recovery/storage-restart、池重开及新旧世代；跨落盘边界时提前验证 | 完整门槛、适用完整 runtime 与已发布数据兼容保护；成功恢复不替代失败保护 |
| 权限与 IPC | 注册/permission/capability 检查及 caller guard 的允许/拒绝反例 | 命中的真实 main/Mini denial、跨 profile 与敏感凭据边界 | 适用完整门槛与真实 runtime；一行权限改动也不能仅靠静态通过 |
| 原生生命周期 | 模型/故障端口，加必要真实短功能检查：创建、状态切换、焦点、输入、退出等 | 命中的窗口/WebView/进程/持久化组合；保留隔离与取消清理 | 适用完整 runtime；资源变化追加循环/静置，真实电源与设备条件另验 |
| 性能、资源、耐久 | 用功能断言、固定小负载或查询正确性先排除明显错误，不宣称性能通过 | 按具体瓶颈运行定向 benchmark 或生命周期检查；保留测量前提 | 固定负载、样本、统计阈值、完整进程树及观察区间；24 小时只用于明确可靠性调查 |
| coverage 与 mutation | 先证明行为断言能检出错误；需要覆盖率时分别选择测试与受影响源码 | 保留所选源码的既有阈值和全部消费者；变异保护按实际风险核对 | 默认风险域 gate 保留；局部覆盖率不冒充全仓结果，全仓 coverage、native/runtime mutation 仍按专项用途运行 |
| CI 与发布 | workflow/版本/changelog 改动先用现有静态契约、自测和相关叶子反馈 | 核对可信 candidate、入口并集、工具链/架构与资产契约 | CI 完整集合、双架构、签名、独立资产校验及适用安装/updater 证据不变 |

新增功能按其实际涉及的行组合路径；跨层功能同时保留各层独有风险。功能名字、文件后缀或代码行数不能决定是否需要升级，也不要求每个功能重新执行无关层的专项。

### 4.2 五个时点

| 时点 | 何时开始 | 必须证明 | 不应误解成 |
| --- | --- | --- | --- |
| 编辑快反馈 | 完成一个可观察行为修改后，需要判断方向时 | 当前 owner 的最小有效行为/类型/静态反例；新增风险先证明测试能检出 | 每次保存都自动运行测试；局部绿灯等于可交付 |
| 模块验证 | 一个行为单元完成、准备继续相邻工作时 | owner、实际消费者及跨层接口组合；必要 browser/原生分组 | 只按被修改文件名选择测试 |
| 候选完整验收 | 候选稳定、准备交付或审查时 | `check` / `check:full` 及适用风险追加的完整证据，按第 4.2.1 节区分本地与 CI；未齐时说明待验 | 每一轮按钮调整后都重复全套；本地完成就等于 CI 和完整验收通过 |
| 专项耐久/测量 | 资源/性能 owner 改变、有新的泄漏/卡死线索、相关候选需资源签收时 | 固定负载、样本、环境、阈值及适用观察区间 | 所有小改强制长时静置、全仓 coverage 或连续 24 小时 |
| 发布 | 实际准备正式发行时 | 发布契约要求的源码、资产、架构与升级证据 | 修改普通 changelog 即可/必须生成安装包，或 CI 构建成功等于安装验收 |

开发中不以每次保存、一个小改或新增一份文件为完整回归触发条件。若修改了权限、数据安全、跨层契约、共享状态或组合顺序，按实际风险提前追加相关真实验证；局部无法证明时扩大范围并解释原因。普通编辑反馈、模块完成和稳定候选各自保留明确的结束条件，不能把每轮修改都视作交付候选。

完整候选验证按稳定输入集中安排。失败后先定位产品、fixture、环境或编排原因，修复后重验受影响部分；跨组顺序、共享状态或聚合编排失效时重跑对应组合。阶段切换只重新评估证据，不因“现在提交”重复未失效检查。完整门槛的叶子全集仍可达；受控分段必须满足第 4.5 节并说明“聚合直接通过”或“有效叶子证据齐备”，不能改写原失败。

#### 4.2.1 本地、CI 与发布的职责

以下为本方案拟落地的分工。工程质量第 5 节和贡献指南目前仍要求适用的本地 `check` / `check:full`；实施前及切换条件未满足的范围继续执行原规则，不能凭本方案直接省略。

| 执行场所 | 拟承担的责任 | 完成边界 |
| --- | --- | --- |
| 本地开发与交接 | 最小有效行为验证、命中消费者、必要类型/静态检查；构建、真实原生与资源证据按实际边界追加。影响无法可靠缩小、CI 问题确需全套复现或用户明确要求时完整演练 | 针对当前改动的必需本地证据齐备；已知失败先处理，不能推给 CI 碰运气 |
| CI 候选验收 | 保持 `check:full` 全集合及适用 runtime、双架构和依赖新鲜度；核实真实聚合与消费者，保留失败、取消和未执行结果 | 必需 job 对同一可信候选全部成功；旧提交绿灯、跳过或仅启动 workflow 均不成立 |
| 发布与设备专项 | 按发布政策验证 tag、正式资产、签名、升级及适用设备/电源条件 | 开发构建和普通 CI 不替代正式产物；无法在 CI 证明的真实条件保留本地或人工验收责任 |

T1 先逐项确定哪些证据必须本地取得、哪些完整检查可由现有 CI 承担；T8 核实接线与结果后才切换对应规则。切换必须同时满足：完整保护不减少，CI 的参数、环境、覆盖与失败传播可核实，证据绑定当前候选与适用 base，工程质量及 CONTRIBUTING 中英说明同步。可在更早阶段完成的独立范围不必等无关层；未验证的范围保持原要求。这是实施期对职责调整的验证；生效后新增功能直接使用本地定向路径，CI 结果决定完整候选是否通过，无需先等 CI 才继续开发。

没有授权的远端运行、CI 不可用或本地有未提交输入时，不能预支远端结果。需要本地完整验收时执行所需完整本地检查；必需远端或设备证据仍缺失则完整验收保持未完成。仅开发交接可以明确“本地验证完成、完整验收待 CI”，不得等同于全部通过。必需 CI 失败、取消或漏组时，相关验收同样未完成。

职责明确后，同一候选、同一场景且仍有效的检查结果不因提交、推送或交接再重复执行；CI 的独立可信环境和发布新鲜度义务仍保留。现有聚合入口继续可用，供本地兜底、排障及必要完整演练使用。

### 4.3 暂定预算与测量方法

以下为获批后验证可行性的目标，非现有保证、CI timeout 或产品阈值。T2 在调整各层入口前，用已有日志和有代表性的自然开发迭代建立基线；T7 在路径落地后使用相同口径比较。逐层区分选测判断、无效重复全测、过大的 coverage 范围、隐式准备/编译、测试执行及桌面占用；不等所有领域都凑齐样本才修已证实缺口，也不为统计本身循环跑所有重型检查。

| 对象 | 暂定观察目标 | 测量与超预算处置 |
| --- | --- | --- |
| 普通文档/文案/低层 TS 编辑 | 首个有用反馈 30 秒内，所选小集合 60 秒内 | 分开类型全项目启动成本与 owner 测试；超出先消除不相关准备 |
| 单模块 TS/browser | 已安装依赖、暖缓存通常 3 分钟内 | 报告浏览器启动、fixture 与执行各段；共享消费者多时允许解释性超预算 |
| Rust 模块 | 暖构建下首个测试反馈 2 分钟内、所选模块 3 分钟内 | 编译与执行分列；冷编译不假装暖结果，不跳 fmt/check/clippy 的候选职责 |
| 短原生功能 | 复用合法 prepared 产物后，单组争取 3 分钟内；主动输入区争取 90 秒内 | 保留真实时间边界；超过目标需说明必要等待和实际输入占用，不能删断言 |
| 需要完整演练时 | 暖本地环境 `check` 争取 5 分钟内、`check:full` 10 分钟内；桌面普通完整并集另计，争取 10 分钟内 | 按第 4.2.1 节触发，不要求每次修改都测此目标；429.55 秒只作旧观察，CI 排队、冷构建和专项分列且不隐去总墙钟 |
| 资源与专项 | 保留未被明确取消的样本与观察窗口，暂不承诺统一上限 | Mini 10 分钟项按维护者决定删除；其他采样记录用途和触发，不扩大短观察的证明范围 |
| 发布/长测 | 不设通用“几分钟完成”目标 | 记录完整流程预算与阻塞；连续 24 小时是具体调查要求，不外溢为通用义务 |

首轮覆盖全项目路径，前后比较选各层有代表性的真实改动，不限于 TS 或 Mini。只改执行时点的领域比较避免了哪些无关完整运行；改变入口的领域比较相同风险的反馈成本。性能/资源、coverage/mutation、CI/发布的完整用途继续保留，短反馈目标不要求把它们缩成几秒完成。

运行级公共记录包含命令、选择范围、候选/输入摘要、结果、适用工具链、缓存状态和总墙钟；由现有运行器或日志提供，缺失时补最少记录，不为记录另建通用包装器。非 runtime 入口先用命令级起止及可观察的首次有用结果；选测判断耗时单列人工观察，不混入测试耗时。仅对已定位瓶颈补准备/编译、执行、等待或清理分段，无法分开的部分注明未知。用单调时钟计耗时，UTC 记录事件时间。

OS、架构、WebView2、数据规模、供电/负载、显示与输入条件按对应原生或性能结论记录；桌面组另记主动输入及可能显示窗口的区间。普通纯函数测试继承运行器信息，无需逐项填写 WebView2、供电或桌面字段。公共信息的归属与覆盖规则见第 4.6 节。

成功、失败、取消分别统计；失败到完成的总等待包含排障和补验，不能作为单次执行时长。至少 3 次同类自然迭代才作初步趋势比较，并报告每次值和中位数/范围；样本不足时只报告观察，不作为每个入口都必须重复三次的验收要求，也不声称稳定 p95。冷/暖缓存、不同架构、带 coverage 与无 instrumentation 分开。达到目标的前提是保护集合不减少；同机并行构建污染性能样本时记录污染并结束该次测量。

### 4.4 按改动选择测试、覆盖范围与准备步骤

维护者与 Agent 根据实际 diff、行为变化、owner 和消费者选择现有入口。每次只需说明当前阶段、所选命令为何覆盖当前风险、候选前还需哪些证据；不要求另建全库选择台账或为每个功能写长报告。阶段通用规则归工程质量，具体运行方式跟随实际入口。

输入评估覆盖相关已提交、暂存、未暂存、未跟踪、删除与重命名内容，混合改动合并其风险。共享 API、schema、窗口/权限、动态调用、生成源、依赖以及只改测试/fixture 的情况，都要检查实际消费者。影响不明时先查明；仍无法判断则扩大到能覆盖风险的模块/上层入口，并说明原因。反复出现的无从定向验证应作为入口缺口处理，不能永久用每轮全测替代。

首轮可以补齐已有 browser/Cargo/runtime 入口所需的严格过滤或短功能选项。未知参数、冲突参数、零匹配、缺组和与预期集合不符必须失败；只看退出码 0 不能证明执行了测试。调用保留固定 argv、工作目录、相关环境、coverage/mutation 包装、准备条件与顺序依赖；不能因为覆盖同一测试文件就删除不同语义的验证。完整聚合入口继续拥有其执行图。

测试过滤和 coverage 源码范围分别核实：执行少量测试不保证采集范围也已缩小。局部覆盖率必须覆盖全部受影响源码，保持所选文件的原阈值；不足时补相关测试，不能缩小 include 隐藏缺口。报告选中的测试数量和源码范围，局部结果不能冒充原完整 gate。各入口按真实参数转发方式验证，不能直接照搬 DSH 的 Vitest 参数。

现有依赖图或测试图仅辅助定位。配置装配、动态加载、生成输入、worker、子进程、IPC 和发布产物须显式核对真实消费者，图上无边不能作为免验依据。

将源码反馈、产物准备、类型/构建检查和产物测试分别核实。源码测试只准备确实依赖的组件；真实应用或发布路径使用匹配的构建产物。需要产物时优先复用合法 prepared，输入失配则重新准备；首次缺失依赖必须清楚失败或按原入口准备，不能使用陈旧产物，也不能为提速漏掉测试/脚本类型检查。

### 4.5 证据复用与失败处置

复用分为两件事：prepared 产物是否可运行；某次测试结论是否仍适用于当前候选。前者有效不意味着后者有效。继续使用现有 prepared 校验，由执行者结合现有日志人工判断检查结果；不要求普通测试增加结果登记流程。

可复用必须同时满足输入与环境匹配、结论覆盖当前所需范围、原检查有效期未过、外部数据新鲜度满足原 owner 要求，以及执行场景允许复用。没有文件变化也可能失效。JS 离线审计仍须通过现有入口校验最近 24 小时的成功联网报告与锁文件摘要；过期、缺失或损坏均不能复用。发布 CI 的联网新鲜度义务不能被本地离线成功代替，期限仍由原检查 owner 持有。

| 变化 | 最少重新评估范围 |
| --- | --- |
| 生产源码、配置、schema、生成输入/输出、产物变化 | 所有覆盖该行为及消费者的测试；影响构建输入则 prepared 失效；共享输入无法细分时保守扩大 |
| 测试、断言、fixture、时钟/种子或 harness 变化 | 受影响组的结论失效；共享 fixture 影响全部消费者。纯测试变化是否需要重新编译由真实构建依赖决定 |
| 锁文件、依赖、编译器、运行器、构建参数变化 | 类型/构建、相关运行证据、依赖审计；不能只比较产品源码哈希 |
| Windows、WebView2、架构、权限、显示器/DPI、供电、输入设备、数据规模变化 | 对应原生/性能/环境结论重新验证；纯模型证据可在前提不变时保留 |
| base、候选或选择政策变化 | 重算 diff/风险/必需集合；重新绑定仍有效的叶子，不能仅凭同 HEAD 复用脏工作树结果 |
| 时间到期、外部安全数据更新或执行场景要求变化 | 按原检查 owner 重验期限、新鲜度及场景；同输入摘要不延长有效期，不能将本地证据自动升级为发布证据 |
| 只补执行记录或提交元数据 | 若不改变覆盖输入/风险，保留原有效证据；文档本身仍做适用检查 |

每份拟复用结论能追溯 run ID、候选/输入摘要、命令和选择范围、适用的测试/fixture/依赖/工具链/环境身份、结果/退出码、计时和原始日志位置；有时效限制时还需采集时刻、外部数据身份及有效性规则来源。公共信息由运行记录继承，单个测试不重复填报。运行前后核对输入，期间漂移则相应结果无效；不能核实期限、新鲜度或场景时重新验证对应范围。

失败先保留原记录，再分流：产品失败回到真实 owner；fixture 失败修复前提并重验该 fixture 的消费者；环境失败补齐缺失条件；基础设施失败修复选择、启动、报告或清理。未知归因保持未知，不把重跑通过当成已确认环境问题。清理失败与原失败同时保存。

仅补失效范围。分段补验可以形成完整证据包，但必须说明哪些通过复用、哪些重新运行、仍缺什么；不得将原失败的 `check:full` 日志改成成功。若失败涉及跨组顺序、共享状态、生命周期或聚合编排，则完整组合本身已成为风险，必须重跑对应组合。

### 4.6 公共信息继承与最小登记

运行器拥有公共环境、命令、计时、退出、取消和清理规则；测试组拥有共同层级、触发、预算及 fixture 前提；单个测试只说明独有风险、真实 owner 和不同于组默认的特殊前提。已有名称、位置、断言和命令能表达的信息无需另写字段表。普通纯函数测试可直接继承所属组，不新增供电、WebView2、桌面或专用清理声明。

继承关系须能从实际入口查到，特殊覆盖只记录差异和理由，不能削弱候选保护或时效要求。新增进程、数据库、端口或原生资源的测试必须声明其特殊资源归属与清理；不创建这些资源的测试沿用运行器契约。预算先在命令/组层观察，只有定位到单测瓶颈才追加明细。首轮核实各层公共契约，单测只处理新增和本次改变项，不要求全库补元数据。

以后新增功能先按实际 owner 复用第 4.1 节的开发、模块和候选路径，再为独有失败模式补测试。新增顶层测试仍登记唯一叶子并进入原有聚合图；新增特殊环境或长期采样只增加相应专项，不把成本默认推入每次编辑。能复用入口就不再造框架，确需新入口时同时说明快速反馈、完整验收及清理职责。

### 4.7 真实结果、隔离与确定性等待

低层反馈优先使用真实 owner，只在昂贵、不可控或不确定的边界使用替身。涉及 IPC、权限、持久化、窗口和发布产物时，按风险追加真实入口；通过独立读取文件/数据库、观测状态与事件或确认进程正常退出证明结果，不只检查被测组件的“成功”消息。新守卫要有会被拒绝的反例，竞争缺陷用明确闸门证明操作重叠，重复压力运行只作补充。

只对本次新增或改变的资源型、异步测试核对以下事项，已有可靠 fixture 直接复用：

- 端口通过实际绑定分配，临时根和数据库命名空间独立；避免先探测空闲再占用的竞争。需要桌面输入或性能独占时保留明确互斥范围，不能因一个 fixture 缺陷把全部无关测试串行化。
- 等待就绪事件、握手、状态或受控 promise，超时只限定等待上界；仅时间本身是被测对象时使用受控时钟或必要真实等待。真实 Windows 时间边界及资源采样仍按第 4.1 节保留。
- 获取资源后立即登记清理；退出必须等待进程、端口、worker、文件句柄和回调停止，调用 abort/close/kill 不等于清理完成。环境变量、工作目录、时钟和全局拦截精确恢复，Windows 大小写、句柄和信号差异按真实语义处理。
- 测试、setup 与 teardown 共同使用适用运行阶段的超时预算。调整预算须说明等待对象和观察依据，不用盲目延时、吞错或重试到绿隐藏问题。

验证随风险追加：改全局状态就证明恢复；改生命周期就证明清理后没有晚到写入；修跨进程资源冲突才补独立进程并发；新增守卫才补负对照。无需让普通纯函数测试承担这些条件。

## 5. 执行步骤

T0 → T1/T2 → 按实际缺口推进 T3～T6 → T7/T8 → T9。T1 先定执行分工，T2 在改入口前记录成本；T8 可随各层成果提前核实职责切换，不等无关测量。各层只读取相关 owner，已证实缺口可先修；按稳定输入集中安排必要完整验收，不把每步都当独立交付再跑全套。

- [x] **T0：固定本任务范围与可辨认基线。**
  - 前置：获得本方案实施授权；不依赖文档治理方案完成。
  - 动作：读取实际 Git 状态、diff、相关未跟踪文件、现行验证 owner 及已有日志，辨认其他任务成果、重叠段落和环境条件。
  - 完成与验证：记录相关输入、已有能力和本任务增量；只读核对，不以全量测试固定基线。
  - 风险与回退：旧 HEAD 不代表脏工作树；无法辨认的重叠只暂停该处，不覆盖或回退他人工作。

- [x] **T1：确定本地、CI、发布分工与升级规则。**
  - 前置：T0；相关工程质量、贡献入口与实际 package graph 可核实。
  - 动作：对照现行 owner 与 DSH 参考，按第 4.2.1 节列明本地必须、CI 完整验收、发布/设备专项和无 CI 时的处置；明确各阶段触发、补验及证据时效。需要改变现行本地默认义务时写明对应检查和切换条件，经 T8 核实后再使该部分规则生效。
  - 完成与验证：第 6 节场景能说明现在测什么、在哪里完整验收、何时扩大范围；CI 缺失/旧候选/失败和仅本地交接有明确状态。高风险不因 diff 小而免验，发布本地义务继续有效。文档 gate、自测及规则正反场景通过，CONTRIBUTING 中英只摘要并链接。
  - 风险与回退：不改变默认保护集合，不把定向验证说成新增原则；有歧义时撤回表述，保留原有效契约。

- [x] **T2：逐层核实入口与改动前成本。**
  - 前置：T0/T1 的相关规则明确。
  - 动作：按第 4.1 节逐行确认编辑入口、模块消费者、完整检查的执行场所与环境前提；分别核对测试过滤、coverage 源码范围、默认隐式构建和准备复用。入口调整前用已有日志与自然迭代记录各段成本，识别仅选少量测试却仍采全仓 coverage 或反复构建的情况。临时结果留本文，实际命令留机器 owner。
  - 完成与验证：所有层均有“已有可用”或具体缺口、owner 与修补位置；不只选 TS/Mini。每个代表入口能区分测试集合、采集范围、准备条件和输出数量；代表样本可比，未知成本注明未知，没有短入口的层不能只登记“回退全量”结项。
  - 风险与回退：必要长等待保留真实验收，同时明确可提前获得的反馈。样本不足只限制收益结论，不反复重跑凑数，也不阻塞已证实缺口的修补。

- [x] **T3：补齐前端、静态与浏览器的快速反馈路径。**
  - 前置：T2 命中该层的真实缺口；已有可靠能力直接复用。
  - 动作：核对 package 叶子、TS 测试、checker/self-test、SSR 与 browser 场景。必要时补独立调用、严格过滤及局部 coverage 范围，拆开无关准备；保留测试/脚本类型检查及真正需要的构建。共享 primitive/theme/i18n 覆盖实际消费者，纯文档与本地化沿用各自风险规则。资源型 fixture 按第 4.7 节修实际缺口。
  - 完成与验证：实际 CLI 的过滤确实生效，坏参数/缺组/零匹配失败；局部 coverage 覆盖全部命中源码且不降低阈值。快速分区互斥并集完整，无孤儿或普通顶层重复；缺失/陈旧构建不冒充有效输入。新增或改变入口运行命中行为、类型/lint、治理自测及适用反例。
  - 风险与回退：保留 coverage/mutation 包装、参数、环境与依赖语义；不能按相同测试文件去重。无法可靠独立时暂保留原组合并明确剩余缺口，不能称本层已完成。

- [x] **T4：补齐 Rust、数据和权限的定向验证路径。**
  - 前置：T2 命中该层的真实缺口；读取真实 domain/data/command owner。
  - 动作：在独立质量 target 下使用实际 Cargo module tree 与可核对非零结果的过滤，必要时在现有入口补严格适配。数据用隔离故障 fixture 覆盖拒绝、损坏、回滚、幂等、ID 重映射、旧库/备份及世代隔离；跨落盘/重启或权限风险追加真实 runtime，独立读取实际数据与拒绝结果。并发、全局状态和恢复等待按第 4.7 节核对。
  - 完成与验证：Rust 局部行为、SQLite 风险和 IPC/caller guard 各有早反馈与模块升级路径，公共类型、并发及 helper 消费者不遗漏。新增过滤/fixture 的正反例、真实 main/Mini denial 与命中恢复组有效；保留候选完整 Rust 和 runtime 责任。
  - 风险与回退：低层测试不替代真实落盘、权限或兼容保护；不把所有 Rust 测试改成 mock。独立性不足时恢复组合并修实际缺口，不跳过失败组。

- [x] **T5：补齐原生短功能反馈，分开必要长采样。**
  - 前置：T2 指出原生/资源路径的具体缺口；先核对现有七组与 prepared 能力。
  - 动作：按真实行为区分模型不变量、原生功能、统计分布和资源/耐久断言，复用 fixture 与函数补必要短路径；不再拆一次已有分组。覆盖窗口/WebView/输入/进程等实际 owner，Mini 是其中一个案例，不作为唯一交付对象。
  - 完成与验证：开发时可获得创建、状态转换、焦点/命中、拖动、持久化、退出等命中行为的短反馈；模块阶段覆盖相应组合。按第 3 节最新决定，完整入口使用 50 次展开、10 次重开及主窗 forced/natural GC 各 15 轮；Mini 10 分钟静置删除。短路径不声称性能或完整 runtime 通过。
  - 最小验证：新路径独立运行、非零结果、真实就绪、取消及清理后无晚到操作；拆前/拆后逐条保护映射。运行器等待进程与资源确实退出，相关窗口/落盘结果从外部观察。改变的长采样路径完成必要同候选对照；真实 29/31 秒等边界保留，不为本方案新增 24 小时长测。
  - 风险与回退：运行前确认合法 prepared、profile/DB/端口隔离、显示/输入与日志条件；性能证据要求正确架构、无 instrumentation、完整进程树且无竞争负载。缺前提立即停止；等价性未证实时保留原完整路径和时长，短路径只作补充。

- [x] **T6：让新增功能继承路径，核实补验与清理边界。**
  - 前置：T1/T2 的公共契约明确，使用 T3～T5 已核实入口。
  - 动作：按第 4.6 节由运行器提供公共环境/结果/取消清理，组提供触发/预算/fixture；单测只补独有风险和特殊前提。新增测试登记唯一叶子及聚合归属，复用现有报告，只有实际瓶颈才加明细计时。
  - 完成与验证：普通纯函数测试无需填 WebView2/供电/桌面字段；自建进程、端口、数据库有可追溯资源归属。用场景走读新增 TS、Rust、browser、数据与原生功能怎样进入开发/模块/候选路径，普通新增功能无需新建流程。
  - 补验规则：人工按第 4.5 节核实输入、期限、新鲜度和执行场景，沿用 prepared 校验；过期审计、旧产物、同 HEAD 脏内容变化不复用。原失败与补验分别保留，未知归因不被重跑成功抹去。
  - 最小验证与回退：只对改变的 runner/report/fixture 按第 4.7 节补适用的输入漂移、取消、恢复、报告写失败及清理失败反例；失败保留诊断并非零退出。清理仅针对本轮创建身份、Job 与已验证临时根，归属不明时停止清理；成功要求正常退出与数据断言。

- [x] **T7：比较各层反馈效果与必要总成本。**
  - 前置：T2 基线及 T3～T6 相关路径已有可核实成果。
  - 动作：按相同场景、风险集合和环境比较首次反馈、测试/coverage 范围、准备/执行、桌面占用与必要总耗时。分别报告减少重复全测、缩小无关采集和避免重复构建的收益；转到 CI 的等待单列，不把成本转移冒充消失。复用自然迭代和有效记录，样本不足只报告观察。
  - 完成与验证：逐层区分路径可用、保护完整、收益可证及预算达成；不因一项功能变快就宣称全项目完成。某层仍无有效早反馈则保留缺口；必要真实等待或预算未达成须说明原因，不削弱断言。
  - 风险与回退：排除冷暖缓存、负载和 instrumentation 差异；无可比证据不虚构百分比。超出预算先定位实际瓶颈，不扩大首轮范围或削弱验收。

- [x] **T8：对齐候选、CI 与发布的完整保护。**
  - 前置：T1 拟定的分工与相应入口可核实；本步可随各层提前完成，不等待无关测量。
  - 动作：核对 package graph、Verify/准入/发布 workflow 及实际候选结果；逐项确认由 CI 承担的完整检查有等价参数、环境、覆盖与失败传播。新入口只补必要接线，不重组 job 或新增缓存。满足第 4.2.1 节的范围再同步工程质量、CONTRIBUTING 中英及适用本地指引，切换对应本地重复义务。
  - 完成与验证：新旧完整保护并集、实际聚合可达性与相关自测有效；同候选 CI 必需 job 已成功的范围才可确认切换。旧候选绿灯、跳过/取消/漏组不能接管本地义务；发布联网新鲜度、本地 release:check、双架构和正式资产责任继续有效。
  - 风险与回退：正式资产签名、摘要、attestation、独立校验、安装/updater/恢复与设备限制保持原契约。远端执行需相应 push/dispatch 授权；未跑记“CI 实机未验”，对应职责暂不切换，继续原门槛。缺证据只阻断相关结论，不将本地通过扩大为全链通过。

- [x] **T9：贯通验收、交接与独立归档。**
  - 前置：T0～T8 适用工作与第 6 节验收成立；文档治理方案的状态整理不作为前置。
  - 动作：核对全部层的早反馈、模块与候选关系、实际 diff、新增功能接入、时效和失败处置；集中完成最终输入要求的完整候选及命中专项。改变编排时至少验证一次真实聚合路径，有效证据不为写总结重复运行。
  - 完成与验证：全项目路径均可用，必要完整保护与原失败可追溯；说明本地/CI 职责切换状态、收益、预算和环境限制。关键层缺口仍未解决时本方案保持未完成，不以“回退全量”掩盖缺少反馈路径；已证实的独立成果可分别交付。
  - 交接与回退：长期契约留原 owner，本文只留执行证据。实际剩余事项写承接人、入口及触发。本文不再活动且适用项已完成/拒绝/转交时独立归档并修链接，无需等待配套方案；有关键漏测则恢复原可靠入口并继续处理，不能通过归档隐藏未完成目标。

## 6. 首轮贯通验收

以下场景从实际改动出发，由维护者或 Agent 找到 owner、入口、执行场所、阶段与升级理由；不需要真的新增七个产品功能。已有可靠入口可使用仍有效的证据，新建/改变的入口必须验证真实调用及失败路径。

| 场景 | 编辑与模块阶段应能做到 | 完整验收与反例 |
| --- | --- | --- |
| 普通文案或消息资源 | 文档用文档检查；消息按既有 i18n/类型及命中界面路径；改变政策/命令说明追加相应自测和真实路径 | 不因文字含 tracking 自动升级 Rust；也不能因扩展名是 Markdown 免除操作契约风险 |
| 一个局部交互 | owner 行为、类型/适用静态、相关 browser 或原生短功能能及时反馈 | 前端候选保留 `check` 的完整集合，按第 4.2.1 节分工；数据/IPC/native 按风险升级，样式调整不自动触发长采样 |
| 共享组件 | 找到跨页面真实消费者，覆盖 SSR/键盘/焦点与组合 | 不能只测当前页面；保留候选全集，命中订阅或资源生命周期追加相应证据 |
| Rust 逻辑 | 实际模块过滤非零，覆盖边界、并发/helper 与公共消费者 | 候选保留 `check:full` 集合，按第 4.2.1 节分工；零匹配不能成功，纯函数不自动触发多日长测 |
| SQLite 恢复 | 隔离 fixture 的拒绝/中断/回滚/幂等/旧库先反馈，再按边界补真实恢复/重启组 | 成功路径不替代数据安全；候选保留完整门槛、适用 runtime 与已发布升级保护，不用生产 DB 作 fixture |
| 原生生命周期 | 模型、故障端口及命中短功能独立可用；输入、取消、落盘及恢复组合有升级路径 | 保留完整 acceptance、适用资源样本及真实设备/电源限制；只验 Mini 不算全项目原生路径齐备 |
| 发布相关改动 | 版本/changelog、workflow/资产契约先给定向反馈，明确实际准备发布的阶段 | 正式发布保留完整源码、双架构、资产及安装/updater 责任；本地、离线或开发 profile 不扩大为发布证据 |

另核对静态检查器、i18n、权限的一行改动、性能/资源、coverage/mutation 与 CI 的行级覆盖，确保第 4.1 节每一行都有路径。反例包含：只改 fixture、共享消费者遗漏、参数转发失效、零匹配或缺组、测试已过滤但仍无意采集全仓、缩小 coverage 隐藏受影响源码、同测试不同包装/环境被错误合并、旧 prepared、审计过期、同 HEAD 脏内容变化，以及取消时报告或清理失败。

职责走读还应覆盖：规则切换前仍需原门槛；切换后同候选 CI 完整成功无需本地重复；旧候选成功不覆盖新输入；CI 不可用/失败/取消时只能报告实际完成状态；真实设备和发布证据仍有独立责任。资源型测试按改动验证端口/临时根隔离、全局状态恢复、确定性竞争及清理后无晚到写入，不要求无此风险的测试运行这些场景。

新增功能走读至少覆盖 TS、Rust、数据/权限与原生边界：公共信息可继承，独有风险有断言，开发入口与完整归属可查。规则推演、CLI 执行、真实原生和远端/设备证据分别报告；缺少环境时明确待验 owner，不声称通过。
