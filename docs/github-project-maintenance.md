# GitHub Project 维护指南

## 1. 文档定位

本文说明维护者怎样把 [`roadmap-and-prioritization.md`](./roadmap-and-prioritization.md) 的排序原则落实到私有 GitHub Project。

它回答字段、状态、权限、核对与清理流程，不回答产品为什么优先，也不保存 Project 的当前条目、顺序、字段值、截图或其他私有 live state。当前队列只能在已登录且有权限的 GitHub Project 中读取。

## 2. 当前事实来源与不可用处理

- 每次读取、核对或维护前，必须从有权限的登录会话读取 live Project。
- 聊天记录、本地计划、commit、Issue、Pull Request、截图、缓存和上次读取结果都不能代替 live Project。
- 运行环境可以选择任何能可靠读取当前登录态与页面结果的能力；仓库规则不绑定具体插件、连接器或客户端。
- 无法访问、未登录、权限不足或结果无法验证时，明确报告缺少的条件，不猜测当前状态，也不写入。
- 本文只拥有维护方法；Project 自身拥有当前队列事实。

## 3. 内容边界

Project 是维护者筛选后的开发队列，不是公开反馈收集箱：

- 只收录维护者已经确认想做的工作。
- 不自动收集公开反馈，不记录评论者身份、点赞数、反馈次数或来源渠道。
- 维护者未选中的想法不进入 Project，也不用 `Parked` 等状态保存未决定事项。
- 每项工作使用独立 draft item；直接对应仓库 Issue 时，可保留精简的 `Related: Ceceliaee/patina#N`。
- Project 状态与 Issue、Pull Request 状态相互独立；维护 Project 不自动修改它们。
- 原始截图和外部材料只用于理解，不进入最终工作项；仓库和本文也不保存 Project 截图。

## 4. 字段、状态与工作项结构

长期字段只有：

- `Status`
- `Area`
- 可选的 `Target release`

不维护 `Source`、`Feedback count` 或数字 `Priority / Order`。Project 的手动顺序就是实际开发顺序。

`Status` 语义：

- `Queued`：已确认，但尚未进入近期窗口。
- `Next`：当前工作结束后优先处理；默认最多三个可执行事项。
- `In progress`：正在实施；默认最多一个主要事项。
- `Blocked`：已确认，但存在未满足的依赖、必要输入或外部等待。
- `Done`：实现和相应验证已完成，等待发布或清理。

每个工作项至少包含：

- `Problem`
- 可选的 `Related`
- `Expected outcome`
- `Scope`
- `Non-goals`
- `Acceptance criteria`

依赖和风险只记录影响排序所需的信息。具体实施仍按 [`issue-fix-boundary-guardrails.md`](./issue-fix-boundary-guardrails.md) 选择小修、边界判断或执行单，不把 Project item 写成完整实施计划。

## 5. 新事项准入与授权

维护者可以用自然语言、链接或临时材料提供已决定想做的事项。协作者先：

1. 读取 live Project，排除重复或高度重叠事项。
2. 合并重复反馈，拆分可独立交付的目标，把过大范围拆成可验收阶段。
3. 按产品范围、架构 owner、前置依赖、风险、验证与成本核对。
4. 整理标题、问题、结果、范围、非目标和验收条件。
5. 给出初始状态、领域、可选目标版本、推荐位置和排序理由的完整预览。

展示预览不等于获得写权限。新增、删除、合并、拆分、扩大范围或修改正文与字段，必须获得维护者针对该结构变更的明确确认。

新增确认后：

1. 在 Project 默认底部创建 draft item。
2. 写入完整正文并设置已确认的初始 `Status`、`Area` 和可选 `Target release`。
3. 重新读取 live Project，验证创建与字段结果。
4. 报告实际字段、推荐位置和维持 `Next` 窗口所需的成组状态建议。
5. 不移动或重排新旧事项；维护者在 Project 页面手动调整顺序。

首次创建所需的初始字段属于本次确认范围。后续状态变化由第 6 节处理。

## 6. 执行期间的状态协作

请求明确对应现有 Project item 时：

1. 实施前读取 live Project，确认事项、当前状态、现有 `In progress` 和 `Next` 窗口。
2. 获得实施授权后，建议维护者将事项拖到 `In progress`，并同时报告必要的 `Next` 补位。
3. 状态拖动是非阻塞协作；已授权的本地实施可以继续。
4. 出现未满足依赖、缺少必要输入或外部等待时，建议改为 `Blocked` 并说明原因。
5. 条件解除时，根据真实位置与近期窗口建议回到 `In progress`、`Next` 或 `Queued`。
6. 实现和风险匹配验证完成后，建议改为 `Done`；仍等待外部审核时保持 `Blocked`。
7. 下一检查点重新读取 live Project；实际状态不一致时明确报告，不能用本地完成记录代替。

协作者判断并报告状态建议，维护者在 `Board` 视图实际拖动。若已有另一个 `In progress`，开始新事项前必须先说明切换影响并取得确认。

## 7. `Next` 窗口与排序

每次开始、完成、阻塞、解除阻塞、新增事项或手动顺序变化后，重新计算：

1. 排除 `In progress`、`Blocked` 和 `Done`。
2. 按 Project 手动顺序扫描剩余事项。
3. 建议最靠前的三个可执行事项进入 `Next`。
4. 建议其余未开始事项进入 `Queued`。

如果较高位置事项解除阻塞，较低位置的 `Next` 可能需要回到 `Queued`；所有相关拖动建议应一次报告。状态补位不能绕过手动顺序，也不能把未获维护者选择的反馈加入队列。

排序服从路线图，不按反馈时间、热度或实现趣味：

1. 数据丢失、错误清理、错误恢复和不可逆风险。
2. 错误记录、错误统计、升级回归和明显信任损害。
3. 阻塞正常使用的核心问题。
4. 后续工作的必要前置依赖。
5. 高频核心页面和主路径改进。
6. 普通体验改进。
7. 低频功能和新产品表面。

工作量只微调同一风险层级。`In progress` 默认锁定；只有可信度、数据安全或严重主路径回归可以建议中断。`Target release` 只有在范围、依赖、风险和验证成本基本明确后填写。

## 8. 完成、发布与清理

- `Done` 只表示实现和相应验证完成，不自动关闭 Issue，也不代表已经发布。
- 完成事项先保留在 `Recently Done`，供维护者查看尚未发布的近期进展。
- 正式发布且相应变化已写入 [`CHANGELOG.md`](../CHANGELOG.md) 后，经本次发布流程授权删除对应 draft item。
- 不需要 changelog 的内部工作，可在验证完成且确认不再需要跟踪后删除。
- Git 提交和 changelog 承担长期历史；Project 不承担历史档案职责。

## 9. 隐私与长期维护

- 不把私有 Project 的当前内容复制进本文、路线图、执行计划、测试 fixture 或仓库媒体。
- 本文只在字段语义、状态流、权限或协作流程变化时更新。
- 排序依据变化更新路线图；产品范围变化更新产品原则；当前队列变化只更新 Project。
