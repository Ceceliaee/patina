# Windows ARM64 双架构发行执行方案

> 状态：In progress（本地实现与验证已完成，准备云端双架构验证）
> 创建日期：2026-09-05  
> 最后更新：2026-09-05  
> 执行 owner：Patina 维护者与获授权的实现者  
> 生命周期：临时执行依据；完成后移入 `docs/archive/`  
> 关联公开需求：[Windows ARM64 支持](https://github.com/Ceceliaee/patina/issues/74)

## 1. 目标与第一性原理

用户下载的安装包必须在其设备上安装正确架构的 Patina；后续自动更新必须取得与当前应用架构匹配、能够保留数据与设置完成升级的安装包；每个公开安装包必须能够对应到确定的版本、源码和文件摘要。这三个结果决定构建、发布和验证的组织方式。

### 1.1 从用户结果推导工程约束

| 基本事实 | 必须成立的结果 | 实施含义 |
| --- | --- | --- |
| x64 与 ARM64 是不同的机器码目标 | 安装后的主程序架构正确 | 分别构建并检查主程序，不能只检查文件名 |
| 安装包是用户下载和更新的实际字节 | 签名、摘要、证明绑定同一个最终文件 | 重命名后重新读取摘要，签名与对应包配对 |
| 一个版本同时服务两种架构 | 两个资产对应同一 tag、版本和源码 | 两路构建汇总后进行完整性 gate，再统一发布 |
| 更新器需要按应用架构选包 | x64 应用只取 x64，ARM64 应用只取 ARM64 | 一份清单包含两个明确的平台键，不自动切换架构 |
| 镜像只是备用下载来源 | 来源切换不改变安装包和签名 | R2 复制同一批最终文件，仅替换清单中的下载 URL |
| 构建通过不能证明全部桌面行为 | 发布说明准确表达验证范围 | 保留自动化 gate，明确实体设备人工验证未执行 |

### 1.2 已确定的任务边界

本次采用自动化验收后正式发布的方式。维护者没有 ARM 实体设备；不等待实体设备人工验收，不将该项保留为待完成或完成阻塞。真实设备的电源、托盘、追踪和长期使用差异作为已接受的剩余风险，发布后通过正常用户反馈处理。

这项决定不免除 ARM 原生构建、可执行的自动化测试、发布资产验证和 x64 回归检查。自动化失败必须定位并处理，不能用“发布后反馈”代替失败 gate。

本文记录本次实施步骤与验证结果。本次执行已获授权在云端跑通验证；不发布新版本，不创建发布 tag，不执行 R2 同步。后续远程操作以当前任务的明确授权及[仓库协作规则](../../AGENTS.md)为准；本方案本身不是授权凭证。

## 3. 范围与 owner

### 3.1 实施范围

双架构构建、原生自动化验证、架构明确的资产准备与校验、统一 updater 清单、两个安装包的构建证明、R2 同步、下载说明和相关回归测试。

### 3.2 非目标

不新增 32 位 Windows、Linux 或 macOS 支持；不制作跨架构单一程序；不迁移 npm；不重写 tracking、数据库或前端；不引入通用发布框架；不增加新的应用分层、兼容壳或架构选择设置；不自动把已安装的 x64 应用迁移成 ARM64；不更换签名密钥或把构建证明描述成 Windows Authenticode。

## 4. 目标资产契约

下表是拟实现的固定映射；`<版本>` 为最终选定版本，并非已决定的新版本号。

| 发行架构 | Rust target | updater 平台键 | 最终公开安装包 |
| --- | --- | --- | --- |
| x64 | `x86_64-pc-windows-msvc` | `windows-x86_64` | `Patina_<版本>_x64-setup.exe` |
| ARM64 | `aarch64-pc-windows-msvc` | `windows-aarch64` | `Patina_<版本>_arm64-setup.exe` |

每次 Release 具有两个安装包、一份根级 `SHA256SUMS.txt` 和一份根级 `latest.json`。签名内容写入对应平台清单；是否另外公开 `.sig` 文件沿用已确认的发布契约，不顺带扩大附件范围。GitHub 自动提供的源码归档不计入必备应用资产集合。

- [ ] 在发布脚本建立仅含两个受支持目标的规范映射，未知 target 明确报错。
- [ ] 以架构隔离原始 bundle 输入目录；每个目录中保持唯一 `.exe/.exe.sig` 配对。
- [ ] 确保输入文件、输出文件名、updater 平台、下载 URL 和实际主程序架构一致。
- [ ] `SHA256SUMS.txt` 恰好记录两个最终安装包，顺序固定为 x64、ARM64，保持小写摘要、两个空格、无路径文件名及 LF 格式。
- [ ] `latest.json` 恰好包含两个平台；版本、更新说明和发布时间共享，URL 与签名分别绑定各自安装包。
- [ ] 为每个最终公开安装包生成 attestation，subject 使用明确路径，不将原始 bundle 或目录 glob 作为替代。
- [ ] 任一架构缺失、校验失败或证明生成失败，阻断该版本公开发布。

## 5. 执行阶段

### 阶段 A：固定工作基线

- [ ] 阅读当前长期规范及相关目录的适用说明，确认没有新增约束。
- [ ] 实施前再次读取已登录 live Project；按维护规则报告状态建议，实际拖动由维护者操作，不把 live 内容写入仓库。
- [ ] 检查 `git status --short` 和当前 diff，识别已有本地修改；不覆盖、不暂存、不提交其他任务文件。
- [ ] 记录当前源码 revision、锁文件和工具链版本，后续 CI 证据必须能对应到执行 revision。
- [ ] 检查相关测试当前基线；区分已有失败与本次引入失败，不在失败未归因时宣称通过。
- [ ] 核对 ARM runner 镜像及 action 兼容性，使用仓库现有 action 固定版本方式。

阶段出口：工作范围、机器 owner、已存在修改和验证入口均明确。

### 阶段 B：先建立发布契约测试

- [x] 为两种目标分别增加名称、URL 和平台映射测试，保留现有 x64 文件名兼容断言。
- [x] 建立两组内容不同的安装包 fixture 和签名 fixture，避免相同字节掩盖串用问题。
- [x] 增加双记录校验和读写测试：重复文件、缺行、额外文件、路径穿越、非法摘要、BOM 和 CRLF 应失败。
- [x] 增加 bundle 配对测试：缺安装包、缺签名、空签名、多组候选、错误目录应失败。
- [x] 增加合并清单测试：缺平台、未知平台、重复平台、版本不符和 URL 串用应失败。
- [x] 增加重新读取磁盘的验证测试：生成后篡改一个安装包、清单或校验和，独立 verifier 必须拒绝。
- [x] 区分签名字符串配对测试与真实密码学验签；fixture 的假签名不能证明签名真实性。
- [x] 运行聚焦测试，确认新测试能够暴露当前单架构限制，再进行实现。

阶段出口：双架构成功和主要失败路径都有可执行判定。

### 阶段 C：收口发布脚本

- [x] 修改 `buildReleaseInstallerName` 及 URL 生成入口，使用同一架构映射。
- [x] 改造 `renderSha256Sums` 和 `parseSha256SumsText`，支持固定资产集合并拒绝重复、额外或缺失记录。
- [x] 保留每架构目录的严格配对，再在上层遍历两个目录；不把两组包混在一起后按第一个结果选择。
- [x] 调整 `prepareReleaseAssets`：先验证完整输入，分别复制命名，比较输入与最终文件摘要，再一次生成完整校验和与清单。
- [x] 调整 `writeLatestJson`：一次消费全部平台记录，避免多次运行覆盖同一文件。
- [x] 调整 `verifyReleaseAssets`：从磁盘独立读取两组输入、最终包、校验和与清单，不信任 prepare 的内存结果。
- [x] 验证器检查完整集合与每项关联，不只检查调用者指定的一个平台是否存在。
- [x] 定义新 CLI 参数和 help，迁移所有 workflow、npm、测试及文档调用者；参数形态在实现后固定，不保留无真实外部调用者的兼容分支。
- [x] 为 R2 清单生成提供同一脚本入口：从已验证的 GitHub 清单派生，只改 URL 基址和相应对象路径。
- [x] 聚焦测试通过后检查 diff，确认没有顺带重写版本同步、changelog 解析或无关发布逻辑。

阶段出口：两组 fixture 可完整生成并独立校验，破坏任何一组都会失败。

### 阶段 D：ARM 编译与日常验证

- [ ] 保留 x64 runner，增加 `windows-11-arm` 原生 runner；在日志输出 OS、Node 架构和 Rust host，确认 ARM 任务没有实际使用 x64 Rust host。
- [ ] 使用仓库固定 Node 与 Rust 版本；检查 ARM64 MSVC、SDK 和 NSIS 所需工具，缺失时仅补充必要组件。
- [ ] 在两个原生 runner 上执行 Rust check、test 和 clippy；格式与纯前端检查可复用公共 gate。
- [ ] 将依赖审计的不可达性检查扩展为两个 Rust target，每个例外必须在两者均不可达。
- [ ] 检查新增原生依赖可达性；存在安全问题时在真实依赖 owner 处理，不扩大豁免来使 gate 变绿。
- [ ] 执行现有 `test:tauri-runtime-smoke`；ARM 环境失败时区分工具环境、测试假设和产品缺陷，逐项修复。
- [ ] 检查 smoke 的隔离身份和临时数据路径，禁止污染用户正式数据。
- [ ] 如果出现 ARM 编译错误，记录首个有效错误和依赖路径；只在对应依赖、构建设置或 Windows 平台模块修复。
- [ ] 如果修复需要新增共享抽象、跨层搬迁或兼容壳，按边界守则重新判断范围，不自动扩大计划。

阶段出口：两种原生目标均有对应 revision 的通过记录。依赖树成功不能替代此出口。

### 阶段 E：双架构正式构建与汇总

- [ ] 发布构建明确传入两个 Rust target，沿用 NSIS 和当前生产身份配置。
- [ ] 核对显式 target 后的实际输出目录；路径包含 target 时同步修改上传、下载和 verifier 输入，不沿用默认 host 路径。
- [ ] 使用不同 artifact 名称，例如 `tauri-bundle-x64`、`tauri-bundle-arm64`，防止矩阵任务互相覆盖。
- [ ] 检查构建得到的主程序 PE Machine，x64 与 ARM64 分别匹配期望；必要时增加发布专用二进制检查及畸形文件测试。
- [ ] 不以 NSIS 安装器外壳的 PE 架构替代主程序检查；NSIS 外壳可能仍为 x86，而内部应用为 ARM64。
- [ ] 同一 tag 的两路构建通过后，在单一汇总任务中下载两个 artifact，再调用 prepare 和独立 verify。
- [ ] 对两个最终安装包分别执行 updater 签名验证或通过实际 updater 消费验证；使用生产公钥，私钥只存在于获授权的签名 job。
- [ ] 独立验证后分别生成两个 attestation，然后才允许公开 Release。
- [ ] 保留版本 gate、changelog gate、已有 Release 拒绝、同版本并发保护及禁止覆盖资产的规则。
- [ ] 检查 job 权限和密钥范围，普通 PR 验证不得获得正式签名或发布权限。
- [ ] 更新工作流保护测试，验证双构建依赖、完整资产集合以及“准备 → 验证 → 证明 → 发布”顺序。

阶段出口：工作流能够从同一 tag 生成完整双架构发行集合；任一路失败不会进入公开发布。

### 阶段 F：安装与更新的自动化验收

- [ ] 在一次性 Windows runner 中为每种架构安装对应包，核对安装后的主程序版本和架构。
- [ ] 自动化启动与退出，检查 WebView2 初始化、基础数据读写及实际 smoke 覆盖的窗口和 IPC 行为。
- [ ] 使用合成数据建立升级 fixture，验证安装升级后数据与设置保留；不得读取维护者真实数据库。
- [ ] 用可控测试端点和独立测试签名密钥验证 updater 选择：x64 只接受 x64 记录，ARM64 只接受 ARM64 记录。
- [ ] 验证签名错误、文件损坏、平台缺失和下载失败时停止安装并给出可观察的失败结果。
- [ ] 验证已有 x64 应用在 ARM Windows 上仍选择 x64 更新；不启用按物理设备自动换架构。
- [ ] 核对手动 x64 → ARM64 安装的安装目录、已有进程、卸载记录和数据路径；未建立覆盖安装证据时，不在下载说明承诺无缝切换。
- [x] 按维护者确认的范围取消自定义安装器架构拦截及其验收；保留产物架构验证、明确的文件名称和更新器架构匹配。
- [ ] 验证卸载移除程序文件和快捷方式，并符合已有用户数据保留规则。
- [ ] 记录每项自动化的环境、revision、结果及日志；无法自动化的真实硬件交互写入剩余风险，不伪装成通过结果。

实体设备人工验收在本任务中明确不适用，不增加该项待办。自动化基础设施缺陷或产品失败仍需修复；若某个新测试在托管环境中无法实现，应明确缩窄证据声明并说明替代验证，不静默跳过。

### 阶段 G：R2 备用镜像

- [ ] 在 GitHub Release 成立后，从已验证最终资产同步两个安装包，保持字节不变。
- [ ] 每次 AWS CLI 调用后检查退出码；任何包上传失败时，不发布新的根级 `latest.json`。
- [ ] 两包上传成功并验证后，最后上传双平台镜像清单，避免清单先指向不存在的对象。
- [ ] 回读镜像安装包并核对摘要，验证清单两个 URL 均可下载对应文件。
- [ ] 清理逻辑保留当前版本目录内两个包；仅在新镜像完整成立后清理历史目录。
- [ ] 验证 R2 未配置或同步失败时不撤销 GitHub Release，应用继续优先使用 GitHub endpoint。
- [ ] 覆盖 R2 清单派生测试，确保两个 signature、version 和 notes 不因来源切换改变。

阶段出口：镜像具备与主源相同的双架构资产，镜像失败不损坏主发布事实。

### 阶段 H：用户下载说明与长期规范

## 6. 验证矩阵与运行入口

| 风险 | 聚焦验证 | 通过证据 |
| --- | --- | --- |
| 名称正确但实际主程序架构错误 | 构建与安装后检查主程序 PE Machine | 两种架构匹配，负例被拒绝 |
| ARM 包混入 x64 URL 或签名 | 两组不同字节 fixture、实际 updater 选择 | 对应包通过，错配失败 |
| 第二次生成覆盖第一平台 | 聚合生成 + 磁盘回读 | 清单同时且仅包含两个平台 |
| 某架构缺包仍发布 | 缺失 artifact 与 workflow 依赖检查 | 不进入 publish |
| 复制或上传改变字节 | 输入、最终包及远端回读 SHA-256 | 同一资产摘要一致 |
| 校验和、签名或证明绑定错误 | 独立 verifier、密码学验签和 attestation 验证 | 每个最终包均可独立验证 |
| ARM 上新增可达漏洞 | 两目标依赖审计 | 所有豁免在两目标均不可达 |
| 运行时或数据回归 | 两架构原生 Rust 测试、隔离 smoke、安装升级 fixture | 对应 revision 日志通过 |
| R2 清单引用未上传文件 | 模拟任一包上传失败 | 新清单不发布，旧镜像保留 |
| 下载说明误导用户 | 生成说明测试与人工预览 | 双架构直链和真实文件名匹配 |

下列命令来自当前仓库入口。本地 `check:full`、发布聚焦测试与 changelog 检查已通过；原生 ARM 验证由云端执行。执行者必须根据修改后的 `package.json` 和脚本 help 核对最终形态。正式资产构建与签名默认在 Actions 执行。

```powershell
# 文档验证
npm run check:docs

# 发布脚本聚焦测试；与当前 Node 原生 TypeScript 运行方式一致
node --experimental-strip-types tests/releasePolicy.test.ts

# 最终实现状态的前端、Rust、结构和依赖综合验证
npm run check:full

# 在两种原生 Windows runner 分别执行
npm run check:rust
npm run test:tauri-runtime-smoke
```

发布阶段使用现有 `release:validate-version-files`、`release:validate-changelog` 和 `release:check` 入口；prepare/verify 的双架构 CLI 将在阶段 C 定义后同步进工作流。本文不将尚未实现的参数接口写成当前可运行命令。

- [ ] 在最后一次相关代码修改后运行聚焦测试及综合 gate，记录退出结果。

## 7. 失败处理与发布顺序

| 失败时点 | 处理方式 |
| --- | --- |
| ARM 编译或测试失败 | 保留错误日志，在依赖或平台 owner 修复；不改成只发 x64 来完成双架构任务 |
| 任一资产缺失、摘要或签名不符 | 停止发布，检查输入关联和生成逻辑，重跑完整校验 |
| attestation 失败 | 停止公开 Release，不用校验和替代来源证明 |
| tag 存在、Release 不存在 | 按现有发布规范处理失败补跑，不新增另一套恢复流程 |
| Release 已经存在或出现部分公开状态 | 先检查远端实际状态，遵守不可变规则，不覆盖资产；必要时准备新版本 |
| GitHub 已发布、R2 失败 | 保留 GitHub 主源，修复镜像；不撤回或重建同 tag 主资产 |
| 发布后 ARM 用户报告问题 | 定位可复现问题，按正常修复版本处理，不原地替换已发布安装包 |

- [ ] 发布前检查完整发布范围，选择 SemVer 并同步现有版本文件和 changelog。
- [ ] 核对当前任务的提交、远程推送、tag 和 Release 授权范围；遵循根 AGENTS 的分组与 staged diff 检查规则。
- [ ] 获得相应授权后，使用现有 tag 发布流程；本方案不要求创建新分支或 PR。
- [ ] 两种架构的质量 gate、资产 verifier 和 attestation 全部成功后发布完整 Release。
- [ ] 发布后回读两个公开安装包、校验和与清单，验证下载、摘要和来源证明，并检查下载说明中的链接。
- [ ] 检查镜像结果并如实报告，区分主发布成功与备用镜像失败。
