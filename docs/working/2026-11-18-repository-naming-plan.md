# Patina 全仓库命名优化执行方案

状态为待执行。目标是让读者能从产品里的一个概念找到实现和测试，也能从一个文件名、函数调用或字段名判断它负责什么。适用于 Patina 自己维护的所有子系统，包含内部实现和对外接口。选择目标名称时不计迁移成本，安排实施时按真实消费者验证数据和行为。

## 1. 从名字要解决的问题出发

名字出现在读者作决定的地方。浏览目录时，人要判断打开哪个文件。读调用点时，人要判断这一步会读取、修改或通知什么。处理数据时，人要知道一个数表示时刻还是时长、单位是什么、属于谁。一个名字是否够好，取决于读者在那个位置能否答对这些问题。

| 判断 | 怎么选 | 在 Patina 中怎么检验 |
| --- | --- | --- |
| 对象和职责准确 | 先用一句话说明对象是谁、动作作用于谁。选能覆盖实际职责的名词或动词。 | 看到包含安装、删除操作的类型名时，读者能否判断调用可能修改状态？ |
| 同义归一，异义可辨 | 同一领域概念沿调用链使用一致词根。相邻概念用判别它们所需的词。 | 产品里的工具、可安装的插件、加载插件的宿主，能否各自从界面追到实现？ |
| 上下文决定长度 | 在真实路径、接收者和参数类型旁边读一次，再从公开导入或日志里单独读一次。选两处都够用的最短表达。 | `windows/mini` 已说明是什么窗口。模块里的 `load` 导出到 crate 根时，调用者还需要知道加载什么。 |
| 行为和数据可以预测 | 读取、写入、删除、尝试操作和已发生的事件分别表意。对裸数值标清影响解释的单位，对布尔值写清真假所代表的状态。 | `duration_ms` 表示时长，`now_ms()` 返回时刻。`MainClosed` 表示窗口已经关闭。 |
| 名字有读者，也可能有消费者 | 源码读者、序列化对端、旧数据库、已安装插件和 Windows 各自读取不同表面。逐一确认可观察到的名称。 | Rust 字段名、JSON 键、SQLite 列名即使拼写相同，也分别检查其读写方和升级路径。 |

## 2. 建立全仓范围与术语

- [ ] 从当前工作树列出项目维护的文件。用 `git ls-files --cached --others --exclude-standard` 起步，核对实际存在的路径和在途改动。按本文第 5 节的子系统登记，每个项目维护的路径都有归属。根 Cargo workspace 之外的插件和示例单独计入。[工作区清单](../../Cargo.toml)
- [ ] 清点人工源码、测试与样例、脚本和 Cargo 配置、工作流、打包资源、翻译源、根目录说明及当前文档。第三方上游名称按上游契约核对，Patina 在 `vendor/` 中自己的适配代码纳入审查。生成文件沿生成源修改并重新生成，本机缓存、私有配置和构建产物不作为命名对象。
- [ ] 用“记录一段应用活动”“修改分类规则”“安装并打开提醒工具”三条路径建立第一版术语。从界面、协议一路找到业务、存储、测试。其他子系统补上自己的概念，尤其区分活动、采样、会话、记录和历史，以及工具、插件、安装实例和宿主。
- [ ] 给有歧义的词写一个定义、一个真实用例和一个容易混淆的邻近概念。例如确认 `session` 指活动会话、桌面登录会话还是测试会话。相同英文词在不同领域含义不同时，只在容易误读的作用域加限定词。
- [ ] 给每个候选记下所在位置、旧名、建议名、读者会误解什么、涉及的消费者和验收办法。结果可为“改名”或“保留并说明语义”。仍有疑问时记下缺少的调用点、样本或契约证据。对已经清楚的一组私有局部名，可按模块记录审查结果。

## 3. 首批候选与判断依据

下列条目来自方案编写时的工作树。建议名用于开始审查，执行时按调用点和测试定案。

| 对象 | 观察到的问题 | 优先检验的处理 |
| --- | --- | --- |
| 目录 `crates/activity`、包 `patina-recorder`、类型 `Recorder` | 目录和包名各用一个词。同一个 crate 还导出历史、日汇总和趋势。 | 优先验证包名 `patina-activity`，保留 `Recorder` 表示录制对象。一起核对依赖、Rust 导入、Cargo 过滤器和 xtask 的依赖检查。[包清单](../../crates/activity/Cargo.toml) · [公开接口](../../crates/activity/src/lib.rs) |
| 文件 `recording/manage.rs` 与子目录 `manage/` | 单看路径只能知道“管理”，读代码才发现有分类规则、应用关联和网站规则。 | 盘点整个模块的读写操作，验证 `classification` 或 `classification_rules` 能否涵盖其职责。模块声明、子模块路径和调用方一起检查。[模块实现](../../crates/activity/src/recording/manage.rs) |
| 函数 `today::load` 与公开名 `day_summary_at` | 同一函数有两个入口语境。前者只能在模块中读懂，后者说明了结果和时间，但隐去了读库动作。 | 分别阅读模块内和公开调用，检验 `load_day_summary` 等候选是否既表达读库又能看懂指定时刻的含义。[函数定义](../../crates/activity/src/recording/today.rs) · [导出位置](../../crates/activity/src/lib.rs) |
| 协议枚举 `Query` | 同时承载 `Preferences`、`SaveRules` 和 `InstallUpdate`，按“查询”理解会低估副作用。 | 比较 `Request` 与 `WindowRequest` 在协议内外的可读性。分别核对 Rust 类型名和实际传输的枚举标签，逐项判断是否需要改动线上格式。[协议定义](../../crates/desktop-protocol/src/lib.rs) |
| `SaveRules(r, w, l, c)` | 与窗口侧相同的四组输入在宿主侧丢失含义，阅读时需反查位置。 | 复用调用方已经表达的应用规则、网站草稿、关联和分类含义，在匹配与调用两端读一遍。检查位置与类型仍逐一对应。[窗口调用](../../apps/patina-ui/src/client/requests.rs) · [宿主分派](../../apps/patina/src/window_process.rs) |
| `tool-host`、`plugin-sdk`、界面“工具” | 三者分别面向宿主开发者、插件作者和用户。将所有出现的 `tool` 替换成 `plugin` 会抹去产品含义。 | 检验 `plugin-host` 是否准确描述运行和安装职责，单独核对面板、协议、清单 ID 和签名绑定。以能从工具页追到插件实现作为验收。[宿主](../../crates/tool-host/src/lib.rs) · [工具协议](../../crates/desktop-protocol/src/tools.rs) |

## 4. 每个子系统都要审到哪一层

| 命名表面 | 逐项审查 |
| --- | --- |
| 路径和构建目标 | 目录、文件及配套资源、Cargo 包名、crate 导入名、bin、feature、模块路径和重导出。检查只改大小写的路径在 Windows 工作树和 Git 索引中能否正确表示。 |
| Rust 行为 | 函数、方法、回调和宏。检查接收者和宾语是否清楚，是否隐含持久化、调度、异步通知或失败。调用方需要区分事务内外时保留这种信息。 |
| Rust 数据 | struct、enum、variant、trait、类型别名、常量、静态项、泛型、字段、参数和局部变量。核对单复数、布尔极性、ID 所属对象、单位、时区、索引和计数。遵循该语言惯例，熟悉且局部明确的 `id`、`tx` 等可以保留。 |
| 系统和外部接口 | 检查 IPC 请求、回复、事件及标签，启动命令、环境变量、进程与窗口角色，以及插件 API、清单、能力名与安装身份。核对 HTTP 路径、JSON 键和协议版本，区分身份、显示名和动作。 |
| 数据、界面和运维 | 数据库和查询、设置键、备份与导出格式、翻译键与插值参数、无障碍名称、资源文件、诊断事件、工作流和发布资产。面向用户的词按语言和任务自然表达。 |
| 验证与说明 | 测试模块和函数、fixture 和快照、示例、文档标题和操作命令。测试名应说明场景与可观察结果，阅读时能推断哪项行为退化会让它失败。 |

## 5. 按子系统执行和勾选

每个勾选代表完成本行范围的审查、采纳的改名、消费者更新和对应验证。按一条完整调用链落地，跨目录的引用和测试随所属批次一起改。可独立验证的子系统可分别推进。[目录职责表](../architecture.md#7-新增代码-owner-与落点)

- [ ] **活动、分类与存储。** 审查 `crates/activity-model`、`activity`、`storage` 及所属测试。追踪从活动事实到日汇总、从分类规则到持久化两条链。核对时间单位、会话与记录身份、事务边界、数据库列和设置键。运行 Recorder 契约，改到持久化格式时验证旧库升级、再次打开和备份恢复。
- [ ] **桌面宿主、协议和系统探测。** 审查 `apps/patina`、`crates/desktop-protocol`、`windows-integration`。沿启动、窗口握手、探测超时和退出查命令、事件、进程参数、诊断名。同步宿主、窗口与子进程两端，验证握手、故障回收和关窗续录。已约定的英文进程与窗口角色分别按实际读者核对。
- [ ] **GPUI 界面和 QuietPro。** 审查 `apps/patina-ui`、`crates/quietpro` 的窗口、页面、实体、控件、状态、主题资源及无障碍标签。从页面动作找到处理函数和状态所有者。改动控件身份或标签时核对键盘、无障碍和受影响窗口的具名用例。
- [ ] **工具和插件。** 审查 `crates/tool-host`、`plugin-sdk`、`plugins/official`、`plugins/counter`，连同宿主工具服务和工具页。用官方插件与独立样例验证构建、安装、调用和状态读取，变动安装身份或能力名时再核对旧包、拒绝路径和升级后的授权。
- [ ] **更新、安装和发布资产。** 审查 `crates/updater`、`packaging/windows` 与 `xtask/src/release` 的文件名、资源、清单、签名输入及安装交接参数。改到外部名称时用同一候选验证真实安装、旧版升级与失败回滚。[版本与发布规范](../versioning-and-release-policy.md)
- [ ] **本地化和用户术语。** 审查 `locales`、`crates/i18n` 与 `xtask/src/i18n`。同步消息契约、各语言资源、参数和调用点，从人工源生成 Rust 文件，核对消息检查及对应界面的实际措辞。[本地化契约](../localization.md)
- [ ] **浏览器与对接示例。** 审查 Patina 的 Web Activity 接收端、远程状态桥及 `examples/remote-status-bridge-worker`。区分两种协议各自的字段、调用方和错误。Web Activity 线上契约有变化时，按两仓协议核对现有扩展与新服务端的兼容组合。独立构建示例并验证实际请求。[Web Activity 协议](../web-activity-protocol.md)
- [ ] **仓库工具、测试支持和文档。** 审查 `xtask` 其余命令、`crates/test-support`、`.cargo`、`.github`、根清单、Patina 维护的 vendor 适配、文档及示例命令。CI 工作流改名时追到按名字订阅它的工作流和必需检查。当前文档和链接跟随新名。已发布记录、历史协议样本和归档保留其当时指向的事实。
- [ ] **补齐盘点差额。** 把执行期间新增、移动和最初未归类的项目文件重新对照第 2 节的清单。为每个剩余目录指定审查批次，记录已审查且沿用原名的子系统。根目录和各独立 Cargo 工程均可从记录中找到。

## 6. 每批怎样改、怎样证明

1. 在定义、导入、实际调用、日志或序列化样本中核实语义。把旧名和目标名放到同一行调用或同一条路径中比较，也搜索目标名，避免重名、遮蔽或引入第二个领域词。
2. 按引用关系修改代码。再查编译器看不到的引用，包括 SQL 字符串、Serde 标签、Cargo 元数据、资源嵌入路径、探测启动参数、CI 过滤器、测试选择器及文档链接。按大小写、连字符、下划线和驼峰分别回搜。处理 Cargo 清单时更新相应锁文件，用 `--locked` 验证可重现。
3. 对持久化和外部名称先取得旧输入或已发布样本，再运行变更后的真实读取端。内部命名能与外部已有契约独立时分别命名。若目标包含外部改名，为相应格式实现迁移或版本协商，验证旧数据的含义、失败恢复和新写入结果。已有签名包和历史数据库样本保留原始字节。
4. 按下表记录实际运行的检查、验证了什么、结果和环境。改名命中动态分派、界面定位或历史数据时，至少观察一条实际消费路径。只修改拼写的局部变量，所属代码编译和已有行为测试即可覆盖。
5. 回搜旧名，给剩余命中归因到历史事实、仍在使用的外部契约或语义不同的合法用法。发现歧义则回到定义处修正。将改名结论和验证证据填入本计划，完成一批勾选一批。

| 改动触及 | 验证入口与通过条件 |
| --- | --- |
| 局部 Rust 模块或包 | 对最终包名运行 `cargo test --locked -p <包名>` 和相关格式、Clippy 检查。改测试名或 Cargo target 时，对比变更前后的测试枚举和筛选结果，原断言仍有入口。 |
| 公共类型、依赖或多个模块 | 运行 `cargo test-headless --locked` 及相应静态检查。工作区汇总入口是 `cargo xtask check native`。进程、原生交互和安装行为另运行受影响的 Windows 具名用例。[工程质量](../engineering-quality.md#5-默认验证门槛) |
| xtask、CI、Cargo 路径、示例或插件构建 | `cargo xtask check tools` 覆盖依赖边界、仓库工具、独立示例及插件构建。额外核实按字符串匹配的任务名和产物名能被实际下游找到。[工具检查入口](../../xtask/src/check.rs) |
| 文档、翻译或使用示例 | 运行 `cargo xtask docs check`。翻译源变化运行 `cargo xtask i18n generate` 和 `cargo xtask i18n check`。核对改过的命令能选中目标，链接能到达新位置。 |

每个批次可在此追加一行。只填写实际发生的结果。

## 7. 最终验收与归档

- [ ] 第 5 节覆盖清单与当前项目文件一致。每个候选都有最终名称或有依据的保留决定。确需转交的项写明问题、责任模块和关闭条件。
- [ ] 重走活动记录、编辑分类、安装工具三条路径。能从用户术语找到页面、请求、执行、存储和测试，并能从关键函数或字段名解释上游意图。为另外实际修改的子系统各重走一条受影响路径。
- [ ] 对涉及旧数据或外部接口的批次，保留旧输入和新结果的对照证据。对内部旧名的剩余命中逐一解释，同义实现和过渡别名都有明确去向。
- [ ] 汇总相关测试、原生验证、文档链接和 UTF-8 检查。记录环境缺口与受影响结论。需要额外环境的结果在取得证据后勾选。
- [ ] 将长期有效的术语定义落实到对应代码、协议或所属文档。工作项均已验收、有理由关闭或明确转交后，将本方案移入 `docs/archive/`，修复引用并核对归档记录。
