# Quiet Pro 组件规范

## 1. 文档定位

本文定义本项目长期使用的 `Quiet Pro` UI 规范。

它不是某一轮美化任务的执行单，也不是某个页面的局部设计说明，而是以后新增组件、扩展页面和修复界面时都应默认遵循的长期母规则。

---

## 2. 与其他长期文档的关系

- [`architecture.md`](./architecture.md) 约束代码结构与 owner；本文约束视觉与组件体系应该怎样长。
- [`product-principles-and-scope.md`](./product-principles-and-scope.md) 定义产品边界；本文定义这些产品能力应该以什么气质呈现。
- [`issue-fix-boundary-guardrails.md`](./issue-fix-boundary-guardrails.md) 约束 UI 问题怎样修才不越界；本文约束允许形成什么样的长期视觉规则。

如果某个局部方案与本文冲突，默认先确认是否真的需要新的长期设计方向，而不是让单页方案覆盖母规则。

---

## 3. Quiet Pro 一句话定义

`Quiet Pro = 安静、专业、克制、可长时间使用的桌面效率工具界面。`

它不追求“第一眼惊艳”，而追求：

- 信息清晰
- 层级稳定
- 长时间使用不累
- 不像模板化 AI 设计
- 后续容易继续扩展

---

## 4. 当前产品语境

本项目是一个：

- `Tauri` 桌面应用
- 时间追踪与工作陪伴型工具
- 以 `Dashboard / History / Data / App Mapping / Tools / Settings / About` 为核心工作面的产品
- 以更新状态、备份恢复、桌面挂件等能力作为低噪音支持面的产品

因此 UI 默认应更接近：

- 桌面工具
- 工作台
- 稳定系统
- 长时间持续使用的软件

而不是：

- 营销页
- 创意展示页
- 娱乐型效率产品
- 视觉实验场

---

## 5. 核心设计原则

### 5.1 信息优先于装饰

视觉的第一职责是帮助用户理解信息和完成操作，而不是制造“设计感”。

优先使用这些手段建立质量感：

- 字重
- 间距
- 对齐
- 留白
- 信息分组
- 语义清晰的状态层级

### 5.2 中性系统优先于单页特效

界面整体应保持中性、专业、耐用。

即使页面有重点区域，也应通过系统化样式表达，而不是靠单页独有的强效果抢眼。

### 5.3 产品气质重于内容皮肤

本项目更像桌面效率工具，不是品牌展示页。

因此组件应优先体现：

- 可靠
- 清晰
- 稳定
- 易扫读

### 5.4 主题变化必须建立在稳定骨架之上

允许继续演进主题，但主题变化应建立在稳定骨架之上：

- token
- 语义颜色
- 圆角尺度
- 边框/阴影尺度
- 密度规则

不应通过页面内部大量硬编码样式来“换皮”。

### 5.5 好看必须可复用

Quiet Pro 不反对设计感，但要求这种设计感能被系统化复用。

如果某个效果：

- 只能在一个页面成立
- 依赖页面独有背景
- 依赖大量硬编码值
- 复制到其他页面就违和

那它通常不属于 Quiet Pro 认可的长期做法。

---

## 6. 明确允许与明确禁止

## 6.1 允许的整体气质

- 冷静
- 克制
- 专业
- 中性
- 有桌面工具感

## 6.2 明确禁止

- 玻璃拟态
- 重模糊
- 霓虹发光
- 大面积炫目渐变背景
- 过度圆角
- 为了“高级感”堆大阴影
- 单页面专属花哨特效
- 明显的 AI 模板感

## 6.3 对“高级感”的正确理解

Quiet Pro 的高级感来自：

- 排版干净
- 层级明确
- 控件一致
- 颜色克制
- 节奏稳定
- 比例准确

而不是来自：

- 大面积装饰
- 发光
- 强品牌色占满页面
- 到处悬浮与漂浮
- 为显得贵而故意复杂

## 7. Token 与样式规则

### 7.1 一切优先走语义 token

新增视觉角色时，优先：

1. 复用现有 token
2. 如果现有 token 语义不够，再新增语义 token

不要直接在组件里硬编码：

- 新颜色
- 新圆角
- 新阴影
- 新边框风格
- 新动效尺度

### 7.2 Token 必须描述语义，不描述一次性外观

优先形成的是下面这类语义角色：

- `panel`
- `control`
- `chip`
- `status`
- `track`
- `muted text`
- `danger`

而不是“这个页面看起来大概需要一个什么值”。

### 7.3 分类色可以丰富，但外围 chrome 必须克制

分类色、图表色、状态点颜色允许相对丰富，但只服务业务识别。

周围界面 chrome 仍应保持 Quiet Pro 的中性骨架，不要让彩色元素反过来主导整页。

外部品牌色属于例外，只能在确实表达外部品牌、平台或第三方入口时使用，并且应收敛到最小元素，例如图标、品牌词或一小段文本。不要为了品牌色把整枚按钮、整张卡片或整块页面 chrome 改成强色。

### 7.4 尺度应可预测

长期上，控件应尽量收敛在有限的档位内：

- 圆角档位
- padding 档位
- 字级层级
- 边框与阴影强度

Quiet Pro 不鼓励“这个页面再发明一个更顺眼的新档位”。

### 7.5 样式事实要有清楚 owner

`src/App.css` 长期只作为样式入口，汇总导入 `src/styles/` 下的 CSS-only 文件。当前样式 owner 口径为：

- `src/styles/tokens.css`：Quiet Pro token、主题 scheme 与语义变量
- `src/styles/quiet-pro.css`：可复用组件原型
- `src/styles/app-shell.css`：应用壳层、通用页面与响应式规则
- `src/styles/features/*`：对应 feature 的局部样式

主题 swatch 与可选主题列表这类结构化主题数据不应留在页面组件内部，优先放在稳定的 shared settings/theme owner 中，再由页面组件消费。

## 8. 页面骨架与原型

## 8.1 壳层

应用壳层应保持：

- 稳定导航
- 清晰页头
- 主内容区边界明确
- 页面切换不过分戏剧化

壳层服务的是长期使用秩序，不承担视觉表演。

## 8.2 面板

面板是本项目最常见的容器原型。

它应体现：

- 清晰分组
- 克制边界
- 足够留白
- 不依赖重阴影建立层次

## 8.3 页头

页头应承担：

- 页面身份识别
- 简短上下文提示
- 必要的 controls、status 与 actions

页头不应承担：

- 大片品牌展示
- hero 式舞台
- 页面私有的强视觉实验

## 8.4 列表与工作台

列表、映射表单、设置区块应更像“工作台”，而不是“卡片墙”。

优先保证：

- 行级可扫读
- 信息密度平衡
- 操作入口稳定
- 状态对比明确

## 9. 组件规则

### 9.1 组件原型优先复用

新组件优先归入已有原型之一：

- `panel`
- `control`
- `chip`
- `status`

如果无法归类，再考虑新增原型，而且必须非常谨慎。

### 9.2 状态必须完整

新组件至少应定义：

- `default`
- `hover`
- `active`
- `focus`
- `disabled`

需要时再补：

- `loading`
- `empty`
- `selected`
- `error`

不能只做静态样子，不定义交互状态。

### 9.3 图标只做辅助识别

图标的职责是辅助识别，而不是成为视觉主角。

因此：

- 图标尺寸要克制
- 图标颜色不抢主信息
- 图标背景只服务识别，不应变成装饰噪音
- 同一组同层级 action 里的图标默认保持同一视觉强度；只有明确语义需要时，才允许某个图标单独使用 `danger / warning / success` 等语义色

### 9.4 按钮与输入控件应利落、清晰、可预期

默认不要引入：

- 过分圆润
- 拟物感
- 强阴影营造的“高级感”

同一组 action 按钮默认应使用统一的按钮原型、边框、背景、尺寸和 hover 反馈。不要因为某个按钮是支持、反馈、外链或品牌入口，就默认给它单独的边框、背景、阴影或更强 hover；如果需要强调，只优先在图标或小段文本上表达。

### 9.5 状态类组件必须有语义

`badge`、`chip`、`status` 之类组件只应用于：

- 当前状态
- 风险提示
- 筛选条件
- 轻量标签

不应用于：

- 大块装饰
- 替代标题
- 没有语义必要的“彩色点缀”

### 9.6 共享组件准入与 owner

组件是否进入 `shared/*`，先看长期语义和 owner，不看 JSX 是否相似。

共享组件默认应满足：

- 已经存在两个独立 feature 的真实消费者，或本身属于稳定的全局 UI 原型；
- props 使用产品或交互语言，不暴露单个页面的内部状态名；
- 不直接依赖 feature service、Tauri、SQLite、runtime gateway 或平台环境；
- 多数消费者预期在未来一起改变；
- 能明确写出状态、键盘、焦点和测试责任。

只服务一个 feature 的业务组合默认留在该 feature。标题栏、侧栏和 widget 控件留在 `app/*`。两个组件只是外观相近，但操作目标、状态机或未来变化方向不同，不构成共享理由。

原生 `button / input / select / textarea` 不是视觉债务。语义正确、行为专用且没有重复状态机时，可以继续使用原生元素；不要建立“原生标签清零”目标。

### 9.7 普通按钮契约

跨 feature 的普通文本 action 优先使用共享按钮原型，并只使用稳定语义：

- `primary`：当前表面最主要的确认或推进动作；
- `secondary`：取消、稍后、辅助或并列动作；
- `danger`：会造成删除、清理或其他高风险结果的确认动作。

尺寸、排列和局部密度可以由消费者布局决定，但 tone、disabled、busy、focus 与 hover 行为应由共享原型负责。

以下情况不应强行改成普通按钮：

- 语义上应是链接的外部导航；
- 时间线、日期格、格式选项等复合控件内部元素；
- 标题栏、侧栏或 widget 的专用按钮；
- 尺寸和交互契约明确不同的 feature-owned 图标操作。

不要为按钮增加没有真实消费者的多态渲染、`asChild` 或大量布尔变体。

### 9.8 Dialog、Popover 与复合输入契约

Dialog 至少应保证：

- 打开后有明确可访问名称和初始焦点；
- 初始焦点由任务语义决定，不得由 DOM 中第一个可聚焦元素偶然决定；
- 说明、帮助、长内容或复杂配置默认聚焦可见标题；标题可用 `tabIndex={-1}` 接收程序化焦点，但不进入正常 Tab 顺序；
- 输入任务聚焦第一个必要输入，选项任务聚焦当前选项，危险确认聚焦取消或最安全动作；
- 禁用、隐藏、加载中的控件和 Tooltip 辅助图标不得成为初始焦点；目标不可用时稳定回退到标题；
- Tab 与 Shift+Tab 不泄漏到背景；
- Escape 只由最上层 Dialog 响应；
- 关闭后焦点返回真实触发元素；
- 嵌套 Dialog 关闭后返回父 Dialog 内的打开者；内容刷新不得再次抢焦点；
- backdrop 是否可关闭由显式契约决定；
- loading 或 disabled action 不重复提交。

Select、Tooltip、日期、时间、颜色等复合控件至少应保证：

- 触发器具有正确的 expanded、controls、popup 或描述关系；
- 键盘可以完成核心选择路径；
- 选项数量较多且支持方向键时，优先使用单一或分组的 roving tab stop，避免几十个选项全部进入 Tab 顺序；如因包体、兼容性或原生交互保留 Tab 顺序，必须保证核心路径可完成并记录边界理由；
- Escape 关闭并按契约恢复焦点；
- 声明 `role="dialog"` 的弹层必须在打开后把焦点移入内部；若焦点按设计留在触发器，则应改用匹配的 disclosure、listbox 或其他非 Dialog 语义；
- portal 在滚动、缩放、关闭和卸载后正确清理；
- 弹层在窗口边缘不产生新的横向溢出；
- Tooltip 不能作为图标操作唯一的可访问名称。
- Tooltip 应继续响应用户主动的键盘焦点；弹窗打开时意外出现 Tooltip，应修正弹窗初始焦点，不得全局禁用 focus Tooltip 或使用延迟隐藏掩盖焦点错误。
- 不把 HTML `title` 属性当作默认提示方案。它的样式、延迟、定位和可访问行为不受 Quiet Pro 控制；需要提示时使用现有 Quiet Pro Tooltip，并保留独立的 `aria-label` 或可见名称。
- 自解释内容不重复提供 Tooltip。名称、日期、时长、已有文字标签，以及已经可通过 disclosure 查看完整信息的字段，默认不在 hover 时再次弹出内容；只有图标含义不明确、文本确实被截断且没有其他完整读取路径，或时间线色块需要补充精确数据时才保留提示。

### 9.9 组件验证责任

纯展示组件可以由结构测试和页面 smoke 保护。涉及下列任一行为的组件必须有真实浏览器证据：

- portal；
- 全局 listener；
- 键盘导航；
- 焦点陷阱或焦点恢复；
- 日期、时间、范围或复合输入；
- 危险操作、loading 或重复提交防护。

测试应保护独有失败模式，不要为同一事实增加多层重复断言。组件测试必须进入现有测试执行图；不得通过引入独立、不可达的测试入口制造“已经覆盖”的假象。

### 9.10 先复用、再探索、确认后固化

Quiet Pro 组件工作的默认顺序是：

1. **先查现有规范和组件。** 开始 UI 实现前，先检查本文、`src/shared/components/*`、现有真实消费者与相关浏览器测试。不能把“没有查到”误当成“没有规范”。
2. **已有规范就复用真实 owner。** 当现有组件已经覆盖相同的视觉骨架、交互目标或状态机时，应直接组合或扩展该组件。不得只复制 class、尺寸或截图外观，另写一套近似实现。
3. **只有确实没有规范时才进入探索。** 新方案先留在真实 feature owner 内，复用现有 token 和基础原型，完整定义 `default / hover / active / focus / disabled` 等状态。探索阶段可以形成新方案，但不得提前宣称它是 Quiet Pro 通用规范。
4. **确认是固化门槛。** 用户或维护者确认方案后，判断它是一次性业务组合、既有组件的新变体，还是新的稳定共享能力。确认前不为假想复用制造抽象；确认后也不能继续保留重复的页面私有实现。
5. **固化后更新规范与保护证据。** 稳定方案应进入正确 owner，补充本文中的适用场景与边界，并用结构测试或真实浏览器测试保护尺寸、状态、键盘、焦点和弹层行为。

这里的核心区分是：

- **有规范但未查找**：属于实现错误，应改为复用。
- **有相同外壳但内容或业务状态不同**：复用外壳 owner，内容和状态留在各自 owner，不复制外壳。
- **确实没有规范**：允许设计探索，确认后再决定是否进入共享层。
- **只在一个 feature 成立的组合**：即使确认，也可以保留在 feature 内；“成为规范”不等于必须进入 `shared/*`。

### 9.11 日期与范围控件索引

日期与范围控件必须按交互目标选择，不按页面位置或截图相似度选择：

| 组件 | 稳定职责 | 应使用的场景 | 不应采用的做法 |
|---|---|---|---|
| `QuietRangeControl` | 左箭头—中心标签—右箭头的紧凑导航外壳；统一尺寸、边框、状态和可访问关系 | 周、月、年、近几天、单日等前后导航；中心标签可为静态状态，也可打开选择弹层 | 在页面内手工拼三个按钮，或复制 class 模拟外观 |
| `QuietCalendar` | 单月日历内容、月份导航、日期格语义与日期边界 | History 日历、单日选择器及其他需要相同月份内容的界面 | 为新页面复制一份日期网格或单独维护星期顺序 |
| `QuietDatePicker` | 单日选择的触发器、popover 生命周期、outside click、Escape、焦点和 `QuietCalendar` 组合 | 普通日期输入；需要“范围控件外壳 + 历史日历内容”时，通过明确变体组合 `QuietRangeControl` 与 `QuietCalendar` | 把输入型日期按钮硬塞进范围导航，再用页面 CSS 覆盖冲突状态 |
| `QuietDateRangePicker` | 开始和结束日期的范围选择状态机 | 自定义时间范围 | 用两个互不协调的单日选择器重新实现范围规则 |
| `HistoryCalendarPopover` | History feature 的日期导航包装与业务状态 | History 页面自身 | 将它整体搬进其他 feature；其他消费者应复用其下层 `QuietCalendar` 内容契约 |

对象详情弹窗的日期控件采用以下组合：

- 外壳：`QuietRangeControl`
- 单日选择与弹层生命周期：`QuietDatePicker`
- 日历内容：与 History 相同的 `QuietCalendar`
- 日期数据和前后日导航：`destination` feature 自己的状态 owner

这个组合是“共享视觉与交互原型、保留 feature 业务 owner”的标准示例。以后遇到类似场景，应先检查能否按层组合现有组件，不应从页面截图重新实现。

### 9.12 锚点信息弹层

需要在不改变列表行高的前提下补充标题、网址、时间等次级信息时，使用 `QuietAnchoredPopover` 作为稳定弹层外壳：

- `QuietAnchoredPopover` 只负责 portal、锚点定位、窗口边缘收敛、outside click、Escape、滚动关闭和共享 Quiet Pro chrome；
- feature 继续拥有触发条件、标题、列表内容、字段顺序与业务状态，不把业务数据结构放进共享组件；
- 触发器使用 `aria-expanded` 与 `aria-controls`；焦点按设计保留在触发器，因此弹层使用 disclosure 对应的非 Dialog 语义；
- 弹层打开不得撑高列表行、改变滚动容器尺寸，或把内容以内联抽屉插入原列表；
- 标题与网址同时存在时，标题在上、网址在下；时长与时间范围置于独立的右侧信息列，长文本允许在弹层内部换行；
- 不用 `QuietTooltip` 承载需要点击、阅读或包含多条记录的内容，也不复制 History 的 feature 私有定位状态机。

对象详情中的“标题详情”是当前标准消费者。History 页面级时间线仍由 History owner 维护；对象详情弹窗内的记录弹层统一复用共享外壳并由 `destination` 拥有数据与触发状态。

### 9.13 工作台列表卡片与紧凑 disclosure

History 时间线列表与对象详情这类高密度、可扫读的工作台列表，共用以下稳定外壳：

- `qp-workbench-list-card` 负责中性背景、边框、控制级圆角与克制的 hover 反馈；feature 只负责行内数据排列，不再各自复制卡片 chrome；
- `qp-compact-disclosure` 用于紧邻计数徽标的 18px 圆形详情入口，只打开锚点信息弹层，不把整张卡片变成展开触发器；
- 卡片可因业务不同省略图标、色条或第二行时间，但边框、圆角、背景和 disclosure 反馈必须一致；
- 高密度列表应明确可视行数并只让列表本身滚动，不能依赖露出半张卡片暗示仍有内容。

### 9.14 对象详情弹窗与图标入口

Dashboard、History 与 Data 的应用/网页对象详情统一使用 `destination` feature 提供的同一弹窗、读模型、时间轴、列表、偏好与文案契约：

- 入口只绑定对象图标，不把整行或整张卡片变成详情触发器；鼠标双击图标打开，键盘聚焦图标后按 Enter 打开；
- 图标入口使用 `button` 或等价可访问控件，必须有独立 `aria-label`、`focus-visible` 状态与 `cursor: pointer`；图标外的时间轴色块仍使用普通箭头，除非它自身支持拖动；
- 来源页面只提供稳定对象标识、显示名称、图标、颜色、初始日期和运行时版本；详情内容与导航状态由 `destination` owner 读取和维护；
- 弹窗顶栏与时间轴固定，只有下方详情列表滚动；切换日期、来源页面或对象时保持弹窗外框尺寸稳定，不清空为白屏或整块 loading；
- 双击时使用 pointer-down 预备的对象快照，避免第二次 click 先改变单选状态再打开错误对象；关闭后恢复来源选择、滚动位置与触发器焦点；
- 应用与网页使用同一结构。网页可补充标题和网址，应用可补充活动与标题计数，但卡片 chrome、行高、disclosure 和日期控件不得分叉；
- Web Sync 关闭时不出现网页入口；不可用状态必须由来源页诚实隐藏或由弹窗明确表达，不能伪装成零活动。

### 9.15 分段控件与单选列表的选择边界

控件原型由选择集合的性质决定，不能靠压缩字号、间距或文案来延长错误原型的寿命：

- 固定、少量、短小且需要同时比较的闭合集合使用 segmented control，例如主题模式；
- 会继续扩展、原生名称长度不可控，或用户只需确认当前值并偶尔更换的单选集合使用 select/listbox，例如界面语言；
- 同一项设置不能根据当前选项数量在 segmented 与 select 之间动态切换，避免版本升级后交互形态漂移；
- listbox 必须完整支持打开、方向键、Home/End、typeahead、Enter 选择、Escape 关闭、选中语义和焦点恢复；
- 语言选项使用注册表中的原生名称，不用国旗，也不为单一地区变体显示技术 locale tag；将来同一语言出现多个地区变体时，先使用各自语言中的完整地区名称；
- 选项首次需要异步准备时，保留最后一个可用值；目标内容就绪后再更新可见内容、locale、`document.lang` 与 `document.dir`，加载失败不得静默保存未实际展示的值。

### 9.16 Select / Listbox 密度规范

`QuietSelect` 使用两档稳定密度。密度由所在任务决定，不按选项数量或当前语言动态变化：

- `regular` 用于分类映射、对话框表单和其他需要明确输入面的场景；沿用 34px 触发器、32px 选项和现有表单排版；
- `compact` 用于 Settings 这类低频、行内、只需确认当前值的偏好控件；其视觉密度继承原有紧凑 segmented control，不得把普通表单下拉直接撑满设置控制列。

`compact` 的固定视觉契约如下：

| 角色 | 尺寸与排版 | 颜色与状态 |
|---|---|---|
| 触发器 | 高度 28px；水平内边距 8px；内容间距 6px；字号 11px；字重 650；行高 1 | 当前值使用 `--qp-text-secondary`；背景、边框与圆角继续使用 `control` token |
| 展开箭头 | 12px，不参与主信息竞争 | 使用 `--qp-text-tertiary`；展开时只做短旋转反馈 |
| 菜单 | 与触发器间距 4px；内边距 4px；宽度不小于触发器 | 使用 `--qp-bg-panel`、`--qp-border-subtle`、`--qp-radius-control` 与 `--qp-shadow-overlay` |
| 选项 | 最小高度 28px；水平内边距 8px；字号 11px；字重 650；单行显示 | 默认 `--qp-text-tertiary`；hover / 键盘高亮使用 `--qp-text-primary` 与 `--qp-bg-elevated` |
| 已选项 | 与普通选项同尺寸 | 使用 `--qp-text-secondary` 与中性 `--qp-bg-elevated`；不使用强调色描边制造第二层卡片 |
| 禁用状态 | 尺寸不变 | 使用 `--qp-text-disabled`，并保留不可操作光标和语义 |

宽度和响应式规则如下：

- `compact` 触发器的内在宽度由全部选项中实际渲染最宽的一项决定，不由当前值决定，也不允许默认 `width: 100%` 填满空白控制列；切换选项时宽度必须保持稳定；
- 触发器宽度等于最宽选项文字宽度，加左右各 8px 内边距、6px 内容间距、12px 箭头和边框；消费者只能提供可用空间上限与对齐，不能为视觉整齐预留固定空白宽度；
- Settings 的语言选择器桌面双列布局右对齐，堆叠布局回到说明文字下方左对齐；宽度随生产 locale 注册表中的原生名称自动更新；
- 菜单至少与触发器等宽；原生名称需要更多空间时可按内容扩展，但触发器和菜单均最多 220px，并始终受消费者可用宽度与视口安全边距约束；
- 触发器和选项文字保持单行；达到菜单宽度上限后使用省略，不通过增加行高或撑宽整页容纳长名称；完整名称仍必须通过可访问名称和选项文本读取；
- `compact` 必须由共享 `QuietSelect` 的正式 density 契约提供；feature 只能决定布局宽度和对齐，不得用页面私有后代选择器覆盖触发器、菜单或选项内部样式。

## 10. 排版、密度与数据展示

### 10.1 排版质量优先

Quiet Pro 的质量感很大程度来自排版。

优先保证：

- 标题层级清楚
- 副文案简短
- 数字与时间信息易扫读
- 长段说明尽量少

### 10.2 密度要服务效率，不服务压迫感

本项目是效率工具，不是海报。

默认应保持：

- 比营销页更高的信息密度
- 比传统后台更克制的噪音
- 在紧凑和可读之间偏专业的平衡

### 10.3 图表与分类色只服务信息理解

图表可以丰富，但图表周围的 UI 不应跟着一起变花。

如果分类色较多，应主动压低：

- 轨道色
- 面板边框
- 背景层次

---

## 11. 动效规则

Quiet Pro 的动效应当：

- 短
- 轻
- 有反馈意义
- 不打断使用节奏

可以有：

- 页面切换的轻过渡
- 悬停反馈
- `toast / modal` 的短入场

不应有：

- 大幅位移动画
- 浮夸弹跳
- 为了显得灵动而增加的表演性动效

去掉动效后，组件和页面仍应成立。

---

## 12. 实现偏好

- 先扩展设计系统，再做页面局部 workaround
- 能复用现有模式，就不要为单个场景发明新视觉语言
- 没有明确需求时，不改变现有功能语义和操作路径
- 新视觉角色优先进入共享 token 或共享组件，而不是页面私有实现
- 局部例外必须显式、可解释，而且尽量变薄
