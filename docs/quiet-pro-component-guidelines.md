# Quiet Pro 组件规范

## 1. 文档定位

本文定义本项目长期使用的 `Quiet Pro` UI 规范。

它不是某一轮美化任务的执行单，也不是某个页面的局部设计说明，而是以后新增组件、扩展页面和修复界面时都应默认遵循的长期母规则。

---

## 2. 与其他长期文档的关系

- [`architecture.md`](./architecture.md) 约束代码结构与 owner；本文约束视觉与组件体系应该怎样长。
- [`product-principles-and-scope.md`](./product-principles-and-scope.md) 定义产品边界；本文定义这些产品能力应该以什么气质呈现。
- [`issue-fix-boundary-guardrails.md`](./issue-fix-boundary-guardrails.md) 约束 UI 问题怎样修才不越界；本文约束允许形成什么样的长期视觉规则。

如果某个局部方案与本文冲突，默认先确认是否真的需要新的长期设计方向，而不是让单页方案覆盖母规则。

---

## 3. Quiet Pro 一句话定义

`Quiet Pro = 安静、专业、克制、可长时间使用的桌面效率工具界面。`

它不追求“第一眼惊艳”，而追求：

- 信息清晰
- 层级稳定
- 长时间使用不累
- 不像模板化 AI 设计
- 后续容易继续扩展

---

## 4. 当前产品语境

本项目是一个：

- `Tauri` 桌面应用
- 时间追踪与工作陪伴型工具
- 以 `Dashboard / History / Data / Classification / Tools / Settings / About` 为核心工作面的产品
- 以更新状态、备份恢复、桌面挂件等能力作为低噪音支持面的产品

因此 UI 默认应更接近：

- 桌面工具
- 工作台
- 稳定系统
- 长时间持续使用的软件

而不是：

- 营销页
- 创意展示页
- 娱乐型效率产品
- 视觉实验场

---

## 5. 核心设计原则

### 5.1 信息优先于装饰

视觉的第一职责是帮助用户理解信息和完成操作，而不是制造“设计感”。

优先使用这些手段建立质量感：

- 字重
- 间距
- 对齐
- 留白
- 信息分组
- 语义清晰的状态层级

### 5.2 中性系统优先于单页特效

界面整体应保持中性、专业、耐用。

即使页面有重点区域，也应通过系统化样式表达，而不是靠单页独有的强效果抢眼。

### 5.3 产品气质重于内容皮肤

本项目更像桌面效率工具，不是品牌展示页。

因此组件应优先体现：

- 可靠
- 清晰
- 稳定
- 易扫读

### 5.4 主题变化必须建立在稳定骨架之上

允许继续演进主题，但主题变化应建立在稳定骨架之上：

- token
- 语义颜色
- 圆角尺度
- 边框/阴影尺度
- 密度规则

不应通过页面内部大量硬编码样式来“换皮”。

### 5.5 好看必须可复用

Quiet Pro 不反对设计感，但要求这种设计感能被系统化复用。

如果某个效果：

- 只能在一个页面成立
- 依赖页面独有背景
- 依赖大量硬编码值
- 复制到其他页面就违和

那它通常不属于 Quiet Pro 认可的长期做法。

---

## 6. 明确允许与明确禁止

## 6.1 允许的整体气质

- 冷静
- 克制
- 专业
- 中性
- 有桌面工具感

## 6.2 明确禁止

- 玻璃拟态
- 重模糊
- 霓虹发光
- 大面积炫目渐变背景
- 过度圆角
- 为了“高级感”堆大阴影
- 单页面专属花哨特效
- 明显的 AI 模板感

## 6.3 对“高级感”的正确理解

Quiet Pro 的高级感来自：

- 排版干净
- 层级明确
- 控件一致
- 颜色克制
- 节奏稳定
- 比例准确

而不是来自：

- 大面积装饰
- 发光
- 强品牌色占满页面
- 到处悬浮与漂浮
- 为显得贵而故意复杂

## 7. Token 与样式规则

### 7.1 一切优先走语义 token

新增视觉角色时，优先：

1. 复用现有 token
2. 如果现有 token 语义不够，再新增语义 token

不要直接在组件里硬编码：

- 新颜色
- 新圆角
- 新阴影
- 新边框风格
- 新动效尺度

### 7.2 Token 必须描述语义，不描述一次性外观

优先形成的是下面这类语义角色：

- `panel`
- `control`
- `chip`
- `status`
- `track`
- `muted text`
- `danger`

而不是“这个页面看起来大概需要一个什么值”。

### 7.3 分类色可以丰富，但外围 chrome 必须克制

分类色、图表色、状态点颜色允许相对丰富，但只服务业务识别。

周围界面 chrome 仍应保持 Quiet Pro 的中性骨架，不要让彩色元素反过来主导整页。

外部品牌色属于例外，只能在确实表达外部品牌、平台或第三方入口时使用，并且应收敛到最小元素，例如图标、品牌词或一小段文本。不要为了品牌色把整枚按钮、整张卡片或整块页面 chrome 改成强色。

### 7.4 尺度应可预测

长期上，控件应尽量收敛在有限的档位内：

- 圆角档位
- padding 档位
- 字级层级
- 边框与阴影强度

Quiet Pro 不鼓励“这个页面再发明一个更顺眼的新档位”。

七个主页面按阅读任务选择七个文字角色：页面标题 `page-title`，板块与弹窗标题 `section-title`，容器内部的分组标题 `group-title`，名称、正文与操作 `body`，占比、刻度、文件名和状态标签 `caption`，核心汇总与计时读数 `metric`，数量标记、时间轴图例和紧凑分段导航 `compact`。没有分组的页面不额外增加层级；列表内的时长仍属于内容，不因为是数字就使用核心读数角色。

角色的字号和行高由 [tokens.css](../src/styles/tokens.css) 中配对的 `--qp-font-size-*` 与 `--qp-line-height-*` 持有，使用 `rem` 并保留用户根字号。组件消费角色，不另建逐页字号或响应式字号变体；窄空间先调整布局、换行或刻度密度。字重独立使用 `tokens.css` 的 `--qp-font-weight-regular`、`--qp-font-weight-medium`、`--qp-font-weight-emphasis` 三个角色：正文与说明使用 regular；名称、设置项、输入内容和普通时长使用 medium；时间轴图例、时间轴与小时图刻度、摘要指标标签也使用 medium，保持小字号下的识别度；各级标题、按钮、分段选项、重点数值与 badge 使用 emphasis。控件尺寸不另设字重，hover、focus 和禁用状态不改变字重；选中状态沿用背景与颜色表达，确需字重强调时复用 emphasis。名称可以省略，状态与重要数值不能被挤截。

基础 `h1/h2/h3` 字号放在 CSS 基础层，允许组件明确的视觉角色覆盖；保留语义标题结构，不依赖标签级别强制视觉大小。SVG 图表使用相同字号 token，并按实际容器尺寸建立坐标。紧凑信息统一使用 `compact` 角色，包括数量标记、时间轴图例、紧凑分段切换、工具侧栏标签和热力图日历标签。数据窄列选择器使用 `caption` 名称与时长、`compact` 元信息；输入框（含提示文字、日期、时间和颜色值）、搜索框、紧凑按钮和紧凑下拉使用 `caption`。数据汇总数值与趋势内联数值使用 `section-title` 尺度，区别于 24px 核心读数。相同阅读任务复用角色，不保留逐页局部字号。桌面挂件与窗口壳层保留各自几何约束，由其样式 owner 持有；共享控件改动仍须覆盖这些消费者的回归检查。

### 7.5 样式事实要有清楚 owner

`src/App.css` 长期只作为样式入口，汇总导入 `src/styles/` 下的 CSS-only 文件。当前样式 owner 口径为：

- `src/styles/tokens.css`：Quiet Pro 几何、字体、动效 token 与 Tailwind 颜色别名
- `src/shared/theme/`：主题预设、默认对比度与颜色派生；`useAppThemeMode` 将结果应用到主窗口及 Widget 的 `--qp-*`
- `src/styles/quiet-pro.css`：可复用组件原型
- `src/styles/app-shell.css`：应用壳层、通用页面与响应式规则
- `src/styles/features/*`：对应 feature 的局部样式

主题色样和预设默认对比度由 [themePresets.ts](../src/shared/theme/themePresets.ts) 持有；[colorSchemeOptions.ts](../src/shared/settings/colorSchemeOptions.ts) 保留可选项及显示名称。颜色计算和 Patina 语义映射由 [deriveTheme.ts](../src/shared/theme/deriveTheme.ts) 持有，组件消费 `--qp-*`，不再维护逐主题 CSS 色板。

浅色和深色分别保存主题预设，颜色派生采用各预设默认对比度，不提供用户对比度选项，也不读取或保存自定义覆盖值。普通与强调边框保留 Patina 各主题既有配色，由预设持有；主按钮文字保持白色。

主按钮背景由 `deriveTheme.ts` 派生为 `--qp-button-primary-bg`；仅当强调色与白字的对比度低于 [WCAG 4.5:1 阈值](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)时，以最小必要幅度向黑色混合。主按钮边框和交互态使用该 token，保留既有混色比例；全局强调色和其他控件配色不变。

Codex 参考用于校正命名主题的基础调色板和背景派生，不替换 Patina 的文字、滑条、开关、滚动条和交互状态配色规则。默认主题保留 Patina 原有基础与语义配色。控件继续消费既有语义 token，保持原来的混色比例和明暗层级。

统计进度条的未填充底色使用独立的 `--qp-chart-track`，保持轻淡；设置滑条继续使用 `--qp-track-muted`，两者不互相改变对比度。

内层卡片底色在浅色和深色下均略暗于所在面板，以表达嵌入关系；浅色保留柔和色差，避免与面板同色。具体混色由颜色派生 owner 维护。

预览只影响当前窗口草稿；取消、Escape 或遮罩关闭恢复打开弹窗时的配色。确认保存当前模式的配色，并通过现有设置事件同步 Widget，不提交其他设置草稿。保存期间锁定编辑与关闭；写入失败保留草稿供重试或取消。

## 8. 页面骨架与原型

## 8.1 壳层

应用壳层应保持：

- 稳定导航
- 清晰页头
- 主内容区边界明确
- 页面切换不过分戏剧化

壳层服务的是长期使用秩序，不承担视觉表演。

## 8.2 面板

面板是本项目最常见的容器原型。

它应体现：

- 清晰分组
- 克制边界
- 足够留白
- 不依赖重阴影建立层次

## 8.3 页头

页头应承担：

- 页面身份识别
- 简短上下文提示
- 必要的 controls、status 与 actions

页头不应承担：

- 大片品牌展示
- hero 式舞台
- 页面私有的强视觉实验

## 8.4 列表与工作台

列表、映射表单、设置区块应更像“工作台”，而不是“卡片墙”。

优先保证：

- 行级可扫读
- 信息密度平衡
- 操作入口稳定
- 状态对比明确

## 9. 组件规则

### 9.1 组件原型优先复用

新组件优先归入已有原型之一：

- `panel`
- `control`
- `chip`
- `status`

如果无法归类，再考虑新增原型，而且必须非常谨慎。

### 9.2 状态必须完整

新组件至少应定义：

- `default`
- `hover`
- `active`
- `focus`
- `disabled`

需要时再补：

- `loading`
- `empty`
- `selected`
- `error`

不能只做静态样子，不定义交互状态。

### 9.3 图标只做辅助识别

图标的职责是辅助识别，而不是成为视觉主角。

因此：

- 图标尺寸要克制
- 图标颜色不抢主信息
- 图标背景只服务识别，不应变成装饰噪音
- 同一组同层级 action 里的图标默认保持同一视觉强度；只有明确语义需要时，才允许某个图标单独使用 `danger / warning / success` 等语义色

### 9.4 按钮与输入控件应利落、清晰、可预期

默认不要引入：

- 过分圆润
- 拟物感
- 强阴影营造的“高级感”

同一组 action 按钮默认应使用统一的按钮原型、边框、背景、尺寸和 hover 反馈。不要因为某个按钮是支持、反馈、外链或品牌入口，就默认给它单独的边框、背景、阴影或更强 hover；如果需要强调，只优先在图标或小段文本上表达。

### 9.5 状态类组件必须有语义

紧邻文字的行内 badge 和徽标式辅助操作，字号比其依附文字低一个已有档位，而不是固定为 12px。例如 14px 名称旁用 12px，12px 说明旁用 10px；字重仍复用 emphasis。不新增局部字号，10px 已是最小档。独立状态不按附近无关文字推导大小。

`badge`、`chip`、`status` 之类组件只应用于：

- 当前状态
- 风险提示
- 筛选条件
- 轻量标签

不应用于：

- 大块装饰
- 替代标题
- 没有语义必要的“彩色点缀”

Feature 私有表面也必须使用同一状态语义，但其布局和交互细节由最近的代码与测试 owner 维护。例如桌面挂件由 `src/app/widget/*`、对应样式和 `tests/uiBrowserSmoke/widgetScenarios.ts` 负责，本文不保存第二份行为清单。

### 9.6 共享组件准入与 owner

组件是否进入 `shared/*`，先看长期语义和 owner，不看 JSX 是否相似。

共享组件默认应满足：

- 已经存在两个独立 feature 的真实消费者，或本身属于稳定的全局 UI 原型；
- props 使用产品或交互语言，不暴露单个页面的内部状态名；
- 不直接依赖 feature service、Tauri、SQLite、runtime gateway 或平台环境；
- 多数消费者预期在未来一起改变；
- 能明确写出状态、键盘、焦点和测试责任。

只服务一个 feature 的业务组合默认留在该 feature。标题栏、侧栏和 widget 控件留在 `app/*`。两个组件只是外观相近，但操作目标、状态机或未来变化方向不同，不构成共享理由。

原生 `button / input / select / textarea` 不是视觉债务。语义正确、行为专用且没有重复状态机时，可以继续使用原生元素；不要建立“原生标签清零”目标。

### 9.7 普通按钮契约

跨 feature 的普通文本 action 优先使用共享按钮原型，并只使用稳定语义：

- `primary`：当前表面最主要的确认或推进动作；
- `secondary`：取消、稍后、辅助或并列动作；
- `danger`：会造成删除、清理或其他高风险结果的确认动作。

尺寸、排列和局部密度可以由消费者布局决定，但 tone、disabled、busy、focus 与 hover 行为应由共享原型负责。

以下情况不应强行改成普通按钮：

- 语义上应是链接的外部导航；
- 时间线、日期格、格式选项等复合控件内部元素；
- 标题栏、侧栏或 widget 的专用按钮；
- 尺寸和交互契约明确不同的 feature-owned 图标操作。

不要为按钮增加没有真实消费者的多态渲染、`asChild` 或大量布尔变体。

### 9.8 Dialog、Popover 与复合输入契约

Dialog 至少应保证：

- 打开后有明确可访问名称和初始焦点；
- 初始焦点由任务语义决定，不得由 DOM 中第一个可聚焦元素偶然决定；
- 说明、帮助、长内容或复杂配置默认聚焦可见标题；标题可用 `tabIndex={-1}` 接收程序化焦点，但不进入正常 Tab 顺序；
- 输入任务聚焦第一个必要输入，选项任务聚焦当前选项，危险确认聚焦取消或最安全动作；
- 禁用、隐藏、加载中的控件和 Tooltip 辅助图标不得成为初始焦点；目标不可用时稳定回退到标题；
- Tab 与 Shift+Tab 不泄漏到背景；
- Escape 只由最上层 Dialog 响应；
- 关闭后焦点返回真实触发元素；
- 嵌套 Dialog 关闭后返回父 Dialog 内的打开者；内容刷新不得再次抢焦点；
- backdrop 是否可关闭由显式契约决定；
- loading 或 disabled action 不重复提交。

Select、Tooltip、日期、时间、颜色等复合控件至少应保证：

- 触发器具有正确的 expanded、controls、popup 或描述关系；
- 键盘可以完成核心选择路径；
- 选项数量较多且支持方向键时，优先使用单一或分组的 roving tab stop，避免几十个选项全部进入 Tab 顺序；如因包体、兼容性或原生交互保留 Tab 顺序，必须保证核心路径可完成并记录边界理由；
- Escape 关闭并按契约恢复焦点；
- 声明 `role="dialog"` 的弹层必须在打开后把焦点移入内部；若焦点按设计留在触发器，则应改用匹配的 disclosure、listbox 或其他非 Dialog 语义；
- portal 在滚动、缩放、关闭和卸载后正确清理；
- 弹层在窗口边缘不产生新的横向溢出；
- Tooltip 不能作为图标操作唯一的可访问名称。
- Tooltip 应继续响应用户主动的键盘焦点；弹窗打开时意外出现 Tooltip，应修正弹窗初始焦点，不得全局禁用 focus Tooltip 或使用延迟隐藏掩盖焦点错误。
- 不把 HTML `title` 属性当作默认提示方案。它的样式、延迟、定位和可访问行为不受 Quiet Pro 控制；需要提示时使用现有 Quiet Pro Tooltip，并保留独立的 `aria-label` 或可见名称。
- 自解释内容不重复提供 Tooltip。名称、日期、时长、已有文字标签，以及已经可通过 disclosure 查看完整信息的字段，默认不在 hover 时再次弹出内容；只有图标含义不明确、文本确实被截断且没有其他完整读取路径，或时间线色块需要补充精确数据时才保留提示。

### 9.9 组件验证责任

纯展示组件可以由结构测试和页面 smoke 保护。涉及下列任一行为的组件必须有真实浏览器证据：

- portal；
- 全局 listener；
- 键盘导航；
- 焦点陷阱或焦点恢复；
- 日期、时间、范围或复合输入；
- 危险操作、loading 或重复提交防护。

测试应保护独有失败模式，不要为同一事实增加多层重复断言。组件测试必须进入现有测试执行图；不得通过引入独立、不可达的测试入口制造“已经覆盖”的假象。

### 9.10 先复用、再探索、确认后固化

Quiet Pro 组件工作的默认顺序是：

1. **先查现有规范和组件。** 开始 UI 实现前，先检查本文、`src/shared/components/*`、现有真实消费者与相关浏览器测试。不能把“没有查到”误当成“没有规范”。
2. **已有规范就复用真实 owner。** 当现有组件已经覆盖相同的视觉骨架、交互目标或状态机时，应直接组合或扩展该组件。不得只复制 class、尺寸或截图外观，另写一套近似实现。
3. **只有确实没有规范时才进入探索。** 新方案先留在真实 feature owner 内，复用现有 token 和基础原型，完整定义 `default / hover / active / focus / disabled` 等状态。探索阶段可以形成新方案，但不得提前宣称它是 Quiet Pro 通用规范。
4. **确认是固化门槛。** 用户或维护者确认方案后，判断它是一次性业务组合、既有组件的新变体，还是新的稳定共享能力。确认前不为假想复用制造抽象；确认后也不能继续保留重复的页面私有实现。
5. **固化后更新对应 owner 与保护证据。** 稳定方案进入正确 owner，并用结构测试或真实浏览器测试保护尺寸、状态、键盘、焦点和弹层行为。形成或改变跨页面契约时才补充本文的适用场景与边界；单个 feature 的组合保留在其代码与测试 owner，文档更新遵守根 [`AGENTS.md`](../AGENTS.md#documentation-hygiene)。

这里的核心区分是：

- **有规范但未查找**：属于实现错误，应改为复用。
- **有相同外壳但内容或业务状态不同**：复用外壳 owner，内容和状态留在各自 owner，不复制外壳。
- **确实没有规范**：允许设计探索，确认后再决定是否进入共享层。
- **只在一个 feature 成立的组合**：即使确认，也可以保留在 feature 内；“成为规范”不等于必须进入 `shared/*`。

### 9.11 跨页面交互原型与机器 owner

跨页面复用的 Dialog、Popover、Tooltip、Select、日期与范围控件优先由 `src/shared/components/Quiet*.tsx` 拥有实现契约；feature wrapper 只组合领域数据和文案，不能复制焦点、关闭、定位或键盘状态机。

长期通用契约只有：

- overlay 打开后建立明确焦点，支持 Escape 与外部关闭语义，关闭后把焦点还给触发点；Dialog 需要焦点陷阱，非模态 Popover 不伪装成 Dialog；
- listbox、menu、calendar 和分段选择使用正确 role、单一可操作焦点与键盘移动，视觉选中不能代替语义状态；
- icon-only 入口必须有可访问名称、可见焦点和足够命中区，不能只靠 hover tooltip 解释；
- 日期、范围、时区和 locale 语义由共享组件与领域 resolver 分工，feature 不自行复制日期算法；
- 共享原型的键盘、焦点、关闭、定位、viewport 和消费者场景由 `tests/uiBrowserSmoke/*Scenarios.ts` 保护；新增独有失败模式先补可重复测试。

滚动区域的唯一视觉 owner 是 `src/styles/components/quiet-scroll-region.css` 中的 `.qp-scroll-region`。feature 拥有尺寸、padding、`overflow-*` 和 overscroll，不得复制 scrollbar pseudo、创建 JavaScript 自绘滚动条或使用已退出的 `.custom-scrollbar`。`.qp-scroll-region-stable` 只适用于 overflow 前后宽度变化会破坏真实信息几何且有 browser geometry test 的消费者；forced-colors、原生键盘/指针路径和系统 overlay scrollbar 必须保持可用。

单个 feature 的卡片布局、挂件状态、具体日期入口、详情弹窗内容和消费者选择规则归最近的 feature 源码与测试。只有跨页面契约发生变化时才更新本文。

## 10. 排版、密度与数据展示

### 10.1 排版质量优先

Quiet Pro 的质量感很大程度来自排版。

优先保证：

- 标题层级清楚
- 副文案简短
- 数字与时间信息易扫读
- 长段说明尽量少

### 10.2 密度要服务效率，不服务压迫感

本项目是效率工具，不是海报。

默认应保持：

- 比营销页更高的信息密度
- 比传统后台更克制的噪音
- 在紧凑和可读之间偏专业的平衡

### 10.3 图表与分类色只服务信息理解

匿名活动使用未分类固定色叠加低对比稀疏微点，应用图标位使用中性灰 EyeOff。时间条与图表复用共享纹理，小圆点保持圆形裁切；SVG pattern ID 在实例间唯一。名称与可访问文本仍明确标识“匿名活动”，不依赖颜色或微点作为唯一提示。

图表可以丰富，但图表周围的 UI 不应跟着一起变花。

如果分类色较多，应主动压低：

- 轨道色
- 面板边框
- 背景层次

---

## 11. 动效规则

Quiet Pro 的动效应当：

- 短
- 轻
- 有反馈意义
- 不打断使用节奏

可以有：

- 页面切换的轻过渡
- 悬停反馈
- `toast / modal` 的短入场

不应有：

- 大幅位移动画
- 浮夸弹跳
- 为了显得灵动而增加的表演性动效

去掉动效后，组件和页面仍应成立。

---

## 12. 实现偏好

- 先扩展设计系统，再做页面局部 workaround
- 能复用现有模式，就不要为单个场景发明新视觉语言
- 没有明确需求时，不改变现有功能语义和操作路径
- 新视觉角色优先进入共享 token 或共享组件，而不是页面私有实现
- 局部例外必须显式、可解释，而且尽量变薄

---

## 13. Review 门槛

UI review 同时检查 owner、token、状态、键盘、焦点、可访问性和可重复测试。明显偏离 Quiet Pro 或需要新视觉方向时先确认；可见 UI PR 的截图只通过仓库外附件提供，不能提交审查媒体或用截图替代测试。
