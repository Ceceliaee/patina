# 文档治理

仓库文档供维护者、贡献者与 Agent 共同使用。接手工作的人应能找到当前承诺、负责它的位置和核实结果的方法。文档需要修改的时机包括行为或承诺变化、原说明有误，以及读者无法据此完成任务。

## 知识的归属

| 读者要找什么 | 权威出处 |
| --- | --- |
| 产品定义、隐私与数据控制、提案准入及优先级 | [产品与优先级](product.md) |
| 进程、数据流、依赖、职责与代码落点 | [系统架构](architecture.md) |
| 工程风险、验证证据、评审和工程表述 | [工程质量与修复](quality.md) |
| Quiet Pro 布局、组件、键盘、焦点与交互状态 | [界面设计](ui.md) |
| 文案资源、译者交接、语言回退 | [本地化](localization.md) |
| 版本选择、兼容窗口、签名、发布与恢复 | [版本与发布](release.md) |
| 桌面接收端与扩展共同遵守的本机接口 | [Web Sync 本机协议](web-sync-protocol.md) |
| 贡献、提交与 PR 准入；Agent 的协作和操作授权 | [贡献指南](../CONTRIBUTING.md) · [Agent 指令](../AGENTS.md) |

每条约定在负责它的专题维护一次。入口可以保留简短说明并链接到相应章节。字段、依赖和命令清单由 schema、manifest、源码或工具帮助维护。文档补足读者需要理解的行为、失败结果、兼容条件和必要理由。跨仓独立交付同一协议时同步两份正文和引用，以两端可实现的同一契约验收。

## 内容与结构

按读者要学会的操作、要完成的任务、要查询的事实或要理解的原因组织正文。教程提供可观察的终点；操作指南在需要的步骤前交代前提；参考页用稳定术语描述约定；解释说明取舍的原因。问题能直接说明时直接写，举例以消除会导致不同操作的歧义为限。

能用不同方法达到相同结果时，执行者可自行选择方法。只有产品承诺、技术依赖、权限或验证条件要求特定顺序时，才把它写成强制步骤。保留适用范围、例外和失败结果。编辑技术文字时核对[工程表述](quality.md#工程表述)。

长期文件使用简短的英文主题名。独立读者任务或独立维护责任值得分篇；同一判断的前提与结果尽量放在一起。引用使用相对于当前文档的文件与章节路径。改名或合并时同步检查 Markdown 链接、文字路径、节号、测试、模板、跨仓引用及机器检查中的文件名。

## 工作记录与归档

长期专题描述当前有效的契约。局部实现若满足原有约定，验证改动即可。一次故障的经过、测量和迁移顺序留在工作记录；只有脱离事件背景仍然有效的承诺进入长期正文。

用户要求计划，或阶段交接、恢复和证据留存需要记录时，在 `docs/working/` 写下目标、受保护边界和可观察的完成条件。按实际发生的工作勾选，区分已通过、未验证、放弃及转交。转交要写明事项、接手方与待解决的条件。无人承接的未决事项保持开启。

计划结束后，把仍适用的约定写回各自专题，移入 `docs/archive/` 并修复入站链接。旧文件名和当时的结果可以作为历史事实保留。现行操作从当前专题进入。

## 验证文档

从贡献者入口或根指令查找改动的约定，核对实际消费者、操作前提、成功与失败条件。新命令或有变更的步骤通过对应的真实入口或合成输入验证。沿用有效证据时注明它覆盖的范围。发布凭据、对外写入和不可逆数据操作仍受任务授权约束。

从仓库根执行 `cargo xtask docs check` 检查现行文档。改动归档链接时用 `cargo xtask docs check --archives` 核对差量。治理或验证政策的专项测试和证据要求见[工程验收](quality.md#验证范围)。链接和 UTF-8 检查通过后，仍需确认文字准确保留原有义务和例外。
